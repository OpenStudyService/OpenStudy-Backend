> 기준: 2026-10-19 자료 / 개정: v1.1 / 상태: **검토용 제안** / 주 사용 위치 (제안): `openstudy-backend/codex/agent-execution-plan.md`
> 경고: 이 파일은 백로그 후보와 통합 규칙이다. 저장소 실물 확인과 사용자 범위 승인이 끝나기 전까지 모든 신규 Task는 CANDIDATE.

## 0. 읽기 전에 — 결론과 문서의 지위

**판단: 별도 실행 계획이 필요하다.** 단, 추가 요구사항 명세서나 새로운 마스터 WBS가 필요한 것은 아니다. Word v1.2는 *무엇을 왜 구현하는지*, Excel v1.2는 *상위
작업·요구사항·검증을 어떻게 추적하는지*에 답한다. 이 문서는 *코덱스 주 에이전트가 어떤 작업을 어떤 계약과 파일 경계 아래 위임하고 언제 통합할지*를 규정하는 **파생 실행 문서**다.

- 기준 자료: `OpenStudy_요구사항_명세서_v1.2.docx`와 `OpenStudy_요구조건_식별서_및_WBS_v1.2.xlsx`(2026-10-19 반영). 이 문서만으로 기존 두 자료를 대체하지 않는다.
- 현재 Excel: 요구사항 **128개**, 수용 검증 **24묶음**, 상위 WBS **50개 (W01~W50)**, `백엔드Task` 시트 **37개 (BE-001~BE-037)**. 모두 구현 완료로
  간주하지 않으며 세부 Task는 상위 WBS 공수에 중복 가산하지 않는다.
- 문서에서 **기존**이라고 적힌 BE-001~037은 Excel의 후보 ID/표현을 인용한 것이다. **신규 제안**으로 작성한 FE/BE/QA 작업은 아직 Excel에 승인·등록된 것이 아니며, 주 에이전트가
  실제 코드베이스를 점검한 다음 승인하고 등록해야 한다.
- 역할 범위: 직원·사장님용 백오피스만 구현한다. 사용자용 화면, 소셜 로그인, 실제 PG 결제, 고객 QR·출입문 연동, 일반 좌석 사전 예약, 부분 환불, 채팅 첨부, 무제한 AI 분석은 작업으로 슬쩍 추가하지
  않는다.
- 우선순위: 사용자 최신 확정 사항 → 요구사항 v1.2 정책/수용 기준 → Excel의 추적 관계 → 이 실행 계획 (파생 후보) → 실제 코드 구조 (충돌 시 수정 제안 후 승인). 화면은 승인된 목업의
  구조·3테마를 기준으로 한다.

> **중요:** 본 문서의 `예상 소유 영역`은 파일 경로가 아니다. 현재 첨부 자료에는 실제 저장소 트리·테스트 명령·원격 URL이 없으므로, 주 에이전트는 코드베이스를 확인하기 전까지 이 표를 근거로 '파일
> 소유 확정' 또는 '병렬 작업 준비 완료'를 선언할 수 없다.

## 1. 지금 병렬 분업을 바로 시작하면 안 되는 이유

현재 37개 후보에는 `BE-018`, `BE-032~034`처럼 **이름은 BE지만 프론트 파일을 다루는 작업**도 포함된다. 또한 일부는 마이그레이션·공통 보안·서버·UI와 연동되므로 무조건 병렬 처리하면
충돌하거나 통과할 수 없는 테스트가 생긴다.

**기존 계획의 제약:** WBS는 1인 직렬 추정 **307h (개발·검증 299h + 제출 8h)**, 당시 가정은 10/18 시작·11/11 개발 목표·11/14 제출 마감이었다. 11/11까지 매일 8h의
초기 25일 가용량 (200h) 기준 개발·검증 공수가 **99h 부족**하다. v1.1의 정책 보완/세부 분해 재추정 전 숫자이므로, **서브 에이전트 병렬 실행을 시간 단축의 확정 근거로 쓰면 안 된다**. 주
에이전트의 검수·재작업 시간도 필요하다. 마감이 고정이면 범위·실측 공수·시연 우선순위에 대해 사용자 결정을 받아야 한다.

이 문서는 실행 규칙과 후보 작업을 제공하지만 프로젝트 전체 범위·기한·리포 상태를 근거 없이 '확정'하지 않는다.

**설계 선택과 실제 확인을 혼동하지 않는다.** 파일 구조, API 상세 스키마, 마이그레이션 도구, 실메일 방식, 실제 DomainLens 버전/제공일, 인프라 접속 방식은 코드/담당자 확인 뒤 확정한다.
원장·DB 스키마 승인과 변경 관리는 주 개발 담당, 인프라 배포는 인프라 담당자와 분리한다.

2026-10-19 테스트 DB 결정 변경: Docker 전용 MySQL 8.4/InnoDB와 자동 테스트용 Testcontainers를 사용한다. 개발/시연 DB로 대체하지 않고 생성한 테스트 자원만 정리한다. 이미지/OS/digest를 기록하며 Debian 운영 환경 검수는 별도로 한다. V1 SQL 검증 외 자동 연동·테스트 프로필은 BE-005 후속이다. 이번 결정으로 공수·상태·병렬 실행 승인을 변경하지 않는다.

## 3. 에이전트 운영 프로토콜

### 3.1 역할

- **주 에이전트 (통합 책임자):** 범위 승인·계약 동결·WBS/요구 ID 연결·소유 경계 지정·작업 배포·검수·DB 스키마 승인·병합·실환경 검증·문서 반영. 공통 파일과 마이그레이션의 **단일 변경
  책임자**다.
- **백엔드 기능 에이전트:** 지정 모듈의 JPA/서비스/API 및 해당 모듈 테스트만 구현. 공통 보안·DB 구조 수정이 필요하면 제안 후 중단한다.
- **프론트 기능 에이전트:** 지정 화면과 컴포넌트/테스트만 구현. 확인된 OpenAPI/DTO 계약을 사용하고 임시 API 응답을 실제 정책으로 확정하지 않는다.
- **검증 에이전트:** 수용 기준별 테스트 및 실패 재현, 보안/회귀/실DB 확인. 코드 변경 없는 리뷰만 맡기거나 독립된 테스트 파일 소유로 제한한다.
- **문서/감사 에이전트:** 실제 실행 명령·설계 결정·검증 증거만 정리. 성공하지 않은 실메일/실모델/실DB를 통과로 표기하지 않는다.

### 3.3 작업 배정·파일 소유 규칙

1. **독립성 판단은 모듈 이름이 아니라 충돌 여부**다. 동일 migration/`build.gradle`/SecurityFilterChain/공통 DTO/API 스펙/공통 UI 레이아웃은 동시에 수정하지
   않는다.
2. 코드 작업은 가능하면 독립 브랜치/`git worktree`에서. 프론트·백엔드 레포는 각각 별도로 관리하며, 한 작업 카드에는 수정 가능 **repo + 실제 경로 glob + 제외 파일**을 명시한다.
3. 요청된 범위를 벗어나는 수정은 선행 제안으로 보고한다. 공통 설정·마이그레이션 수정, 권한 정책 완화, 대규모 리네임은 주 에이전트 사전 승인 없이는 금지한다.
4. 한 Task는 가능한 한 **관찰 가능한 결과 1개 + 테스트 1세트 + 단일 책임 파일 경계**로 나눈다. 0.5~1일 이상 걸리거나 2개 도메인 트랜잭션을 동시에 바꾼다면 다시 쪼갠다 (크기 기준은 운영
   제안, 확정 추정치가 아님).
5. Task가 공유 API를 요구하면 **먼저 계약 PR**을 합치고, **그 다음 구현 PR**을 병렬 처리한다. 기능 PR은 주 에이전트가 통합 테스트 후 병합한다.
6. 동일 작업을 여러 서브 에이전트에 중복 할당하지 않는다. 리뷰와 구현의 역할은 구분할 수 있으나 검사 근거/수정 권한이 충돌하면 직렬화한다.
7. 에이전트의 완료 메시지는 증거 목록일 뿐이다. **주 에이전트가 병합·실행·검증 기록한 후에만** Excel 상태를 갱신한다.

### 3.4 Task 상태

`CANDIDATE → READY → ASSIGNED → IMPLEMENTED → REVIEWED → VERIFIED → DONE` 또는 `BLOCKED / REWORK`. `IMPLEMENTED`는 코드·단위
테스트 상태, `VERIFIED`는 지정 수준의 실환경 검증, `DONE`은 AT/WBS에 필요한 완료 증거와 통합을 만족한 상태다. '사용자가 승인하지 않은 범위'는 계속 `CANDIDATE`다.

## 7. 실제 에이전트에게 넘길 1-Task 카드 템플릿

작업을 시작할 때 아래를 **Task ID당 하나씩** 채운다. 특히 `실제 소유 경로`, `API 계약`, `선행 병합 커밋`, `검증 명령`이 빈 채로 작업을 배정하지 않는다.

```yaml
id: BE-008                         # Excel 기존 또는 위 제안 중 하나
status: READY                     # 승인 이전에는 CANDIDATE
source:
  wbs: [W07]
  requirements: [OS-AUTH-001, OS-AUTH-002, OS-AUTH-006]
  acceptance: [AT-AUTH]
repo: backend                     # backend | frontend | openstudy-docs
objective: "안전한 비밀번호 검증과 승인 상태별 인증 거절"
prerequisites:
  merged_tasks: [BE-004, BE-006]
  decision_gate: G2
scope:
  allowed_paths: ["<실제 리포에서 확인한 auth 구현/테스트 경로>"]
  forbidden_paths: ["<공통 보안 설정, migration, 다른 모듈 등>"]
contracts:
  input: "<승인된 요청 및 사용자 식별/상태 조건>"
  output: "<승인된 응답·오류 코드/DTO>"
  consistency: "<트랜잭션·멱등·락 조건/해당없음>"
acceptance_tests:
  - "활성 계정의 올바른 자격 증명은 통과"
  - "오류 자격 증명 및 승인대기/제한/퇴사는 거절"
  - "평문 비밀번호·해시/비밀값이 응답과 로그에 노출되지 않음"
commands: ["<실제 빌드 명령>", "<해당 테스트 명령>"]
commit_policy: "할당 경로 외 수정/마이그레이션 필요 시 코드 작성 중단하고 보고"
output: "변경 파일 목록 + 커밋 + 테스트 로그 + 남은 위험/계약 요청"
```

### 7.1 최소 완료 조건 (Definition of Done)

- **관찰 결과:** 수용 기준의 정상 케이스 하나로 끝내지 않는다. 실패/권한·타 지점·동시성/멱등/시간·금액 경계 가운데 **관련 항목**을 연결해 검증한다.
- **코드:** 선언한 repo/파일 소유 안에서만 변경, DTO/엔티티 경계·모듈 의존 규칙 준수, 보안/민감 로그 없음, 필요한 마이그레이션은 주 에이전트가 소유.
- **검증:** 실제 실행한 명령/시간·환경·결과·실패 로그를 기록. 단위/더블, 실제 MySQL 두 연결·HTTP, 실SMTP, 실DomainLens를 명확히 구분.
- **통합:** 주 에이전트가 diff 검수 → 빌드/회귀 → 통합·충돌 해결 → **해당 AT의 전체 수용 기준**에 대한 증거 갱신.
- **기록:** Excel `작업계획`, `백엔드Task`(기존 또는 승인된 신규), `검증추적`, 필요 시 Word/Excel 버전·정책 연결을 동기화. 현행 보고 없는 'DONE' 금지.

### 7.2 비기능 교차 검사 (매 작업에 적용)

| 구분        | 최소 확인                                                                                  |
|-------------|--------------------------------------------------------------------------------------------|
| 인증/권한   | `OS-NFR-001` — 직접 API·현재 소속·역할·지점·행동 권한·CSRF. SSE와 저장 AI 결과도 회수 반영 |
| 원자성/멱등 | `OS-NFR-002` — InnoDB·동시 요청·재시도·감사/발송 대기의 일관성                             |
| 입력/비밀   | `OS-NFR-003` — allowlist, DTO 검증, 비밀번호·토큰·메일/모델 키 미노출                      |
| 감사        | `OS-NFR-004` — 성공 변경 주체/원본/이력; 거부 요청의 성공 기록 금지                        |
| 시간/금액   | `OS-NFR-007` — 저장 UTC, 기간/매출 KST, 금액 KRW·구매/이용/환불 지점 구분                  |

## 8. 첫 번째 실제 실행 라운드 — 주 에이전트 지시 순서

**계약 확정 전에는 리포를 무단 변경시키지 않는다.** 다음 라운드를 추천한다.

1. **주 에이전트 단독:** 두 레포와 공통 docs를 점검하고 `DOC-001`, `BE-001`, `DOC-002`의 결과물을 하나의 계약 기준선으로 병합한다. 수직 흐름 1개 (예:
   `최초 사장님 → 로그인 → 지점 권한 조회 → 권한 없는 지점 거절`)를 첫 시연 게이트로 사용자에게 승인받는다.
2. **G1 후 병렬로 맡길 수 있는 후보:** `BE-002`(빌드, 공유 설정의 단일 책임자), `FE-001`(정적 셸), `DOC-003`(외부 엔진 *공개 계약 조사*). **변경 경로가 겹치면 분리
   실행하지 않는다.**
3. **BE-002 병합 후:** `BE-003`(ArchUnit)과 `BE-004`(오류/검증), `BE-005`(Docker/MySQL·Testcontainers 테스트 격리) 중 실제 소유가 독립적인 작업만 병렬. `BE-006`(스키마)은
   DB 책임자 승인 후 순차 병합, 그 뒤 `BE-007` 시드.
4. **G2 후:** `BE-008 → BE-010 → BE-011 → BE-012/013 → BE-014/015 → BE-019` 계열의 핵심 선행을 지킨다. `BE-009` 최초 관리자 CLI는 `BE-008`
   을 선행으로 검토하며, 초기화/동시 실행을 별도 검증한다.
5. **첫 수직 흐름 합격:** `BE-020/023` 조회 API + 초기 로그인 화면/클라이언트 + 실MySQL/HTTP + 관리자/직원 2계정 타 지점 거절 증거까지 확보한 뒤 다음 범위로 확장한다.

**주의:** 위 흐름은 실행 예시다. 기존 `BE-001~037`의 Excel 선행 ID가 우선이며, 레포 구조를 확인한 주 에이전트가 수정·승인한 Task 카드를 따라야 한다. `BE-037`의 전체 M1 수용
검증을 단순히 `BE-020` 완료로 대신하지 않는다.

## 10. 막힘/변경 처리와 증거 기록

### 10.1 BLOCKED로 두어야 할 일

## 11. 착수 전 사용자 결정이 필요한 항목

1. **첫 배포/시연 컷라인:** 128개 요구사항 전체를 그대로 11/11 이전 필수로 볼지, 시연 핵심 수직 흐름에 우선순위를 둘지 결정. 임의 후속 이관 금지.
2. **리포 실제 경로·계약:** 현재 backend/frontend/docs와 승인 목업, API 명세, DB 마이그레이션 방식 확인 뒤 `G1`에서 실경로 확정.
3. **DomainLens:** 실제 공개 버전/제공일 및 사용자의 코어 참여 시간 확인 (미정이면 일정에서 빈칸 유지).
4. **실SMTP 및 인프라:** 테스트/운영 메일 발송과 호스팅·쿠키/CSRF·SSE·테스트/시연 DB 책임자 확인.
5. **인력/에이전트 한계:** 서브 에이전트 수가 많더라도 물리적으로 독립 작업에만 할당하고, 주 개발자 검수·병합 시간을 재산정.

이 결정을 마친 뒤 **M1 후보 BE-001~037 중 실제 READY 카드만 우선 배정**한다. 나머지 신규 후보는 요구·계약·파일 경계와 함께 순차 승인한다.
