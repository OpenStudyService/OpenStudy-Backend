# 통합 V1 개발 DB 전환

## 확정 방침 (2026-10-27)

사용자는 본인·팀원 로컬 및 공유 개발 DB의 데이터가 모두 재생성 가능한 테스트 데이터임을 확인했다. 이번 전환은 기존 데이터를 이관하지 않고 새 빈 DB에 통합 V1을 적용한다. 계정·지점·상품·초대·세션도 새로 만든다. 실제 업무 데이터가 생긴 이후의 일반적인 업그레이드 방침으로 확대하지 않는다.

기존 Backend V1~V3, Infra의 별도 V1, 채택 전 통합 V1을 적용한 DB는 파일 이름이나 최종 버전 숫자만으로 호환을 판단하지 않는다. 같은 코드의 Flyway validation을 기준으로 하며, 불일치하면 새 개발 DB로 전환한다. 이전 V1→V2→V3 이관 절차는 Git 이력에 보존하고 현재 실행 경로에서는 사용하지 않는다.

## 팀원 로컬

1. 팀 공통 기준 커밋을 안내하고 해당 코드를 받는다.
2. 로컬 앱과 DB에 쓰는 작업을 중지한다.
3. 관리 도구로 새 빈 개발 스키마를 준비하고 `.env`의 접속 대상을 바꾼다. 필요하면 기존 테스트 스키마를 잠시 남겨 확인용으로 사용한다.
4. [DB 관리 안내](README.md)에 따라 V1 적용, 별도 OWNER 초기화, 테스트 데이터 생성을 진행한다.
5. 재로그인과 앱 재시작을 확인한다. 이전 세션·식별자를 보관한 브라우저 상태는 초기화한다.

## 공유 개발 DB

1. 담당자·사용자·중단 시간을 정하고 모든 앱 인스턴스, worker 및 DB 쓰기 작업을 멈춘다.
2. 대상 RDS/스키마와 실제 Flyway 이력을 읽기 전용으로 확인한다. 자동 백업이 있다고 가정하지 않는다. 보관할 필요가 있는 테스트 자료는 별도로 내보낸다.
3. 기존 스키마와 다른 이름으로 빈 스키마를 준비한다. RDS 인스턴스 자체의 삭제·재생성은 필요하지 않다. 기존 스키마는 전환 검증이 끝날 때까지 유지한다.
4. Infra의 구형 V1 자동 적용이 새 스키마에 실행되지 않도록 인계를 먼저 완료한다. Backend 정본을 사용하는 한 경로로 V1을 적용한다.
5. 배포할 앱과 OWNER 명령의 코드 버전을 맞추고 새 DB로 연결한다. 별도 OWNER 초기화 후 최소 테스트 데이터를 만든다.
6. Flyway validate, 서버 재시작, 로그인·로그아웃, 지점·상품·초대의 주요 흐름을 확인하고 사용을 재개한다.
7. 검증 결과와 팀원 전환 여부를 기록한 뒤 기존 테스트 스키마 정리 시점을 담당자가 결정한다.

전환 실패 시 앱을 중지하고 이전 코드와 이전 스키마 연결을 함께 복원한다. 새 스키마의 데이터는 이전 스키마에 자동 병합하지 않는다. 검증이 끝난 후에도 이전/새 앱을 서로 다른 스키마에 연결한 채 동시에 운영하지 않는다.

## 적용 금지 경로

- 기존 DB 위에 통합 V1 또는 전체 구축 SQL을 덧붙여 실행하지 않는다.
- 체크섬 오류를 `repair`나 이력 UPDATE/DELETE로 무마하지 않는다.
- 기존 구형 스키마를 자동 `baseline`해 호환된 것으로 간주하지 않는다.
- Backend PR 병합을 실제 DB 전환 완료로 기록하지 않는다.

이 문서는 전환 계획이다. 실제 팀원·공유 DB 초기화와 AWS 변경은 아직 수행하지 않았다.
