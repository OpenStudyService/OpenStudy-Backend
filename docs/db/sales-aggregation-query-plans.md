# M9 대표 집계 실행 계획과 인덱스 (NFR-PERF-04)

- 이슈: [#89](https://github.com/OpenStudyService/OpenStudy-Backend/issues/89)
- 근거: [ADR-M9-001](ADR-M9-001.md) "원결제일 기준 환불 집계와 상품별 판매량에 인덱스가 부족하면 실행 계획을 확인한 뒤 인덱스만 추가한다", [aggregation-api.md](../design/foundation/aggregation-api.md) 남은 작업
- 결과: `payments (branch_id, approved_at)` 인덱스 1개를 V10으로 추가했다. 다른 인덱스와 쿼리는 바꾸지 않았다.
- 측정일: 2026-11-08, MySQL 8.4.11(Testcontainers, 테스트와 같은 이미지)

## 1. 측정 대상

측정한 SQL은 `SalesSourceRepository`가 실제로 보내는 문장이다. Hibernate의 statement inspector로 기록한 문장에 같은 값을 바인딩해 `EXPLAIN ANALYZE`를 실행했다. 직접 옮겨 적은 SQL은 쓰지 않았다.

| 집계 | API | 저장소 메서드 | SQL |
|---|---|---|---|
| 매출(처리일·원결제일 기준) | `GET /sales/revenue` | `totals` | 승인 1개 + 환불 1개 |
| 지점 비교 | `GET /sales/revenue/branches` | `totals`(매출과 같은 SQL) | 승인 1개 + 환불 1개 |
| 이용권 판매량·상품 순위 | `GET /sales/passes/volume`, `/sales/passes/products` | `passTotals(byDay=false)` | 승인 1개 + 환불 1개 |
| 추세(매출·이용권 수량) | `GET /sales/trend` | `dayTotals`, `passTotals(byDay=true)` | 승인 1개 + 환불 1개 |
| 최소 원장 | `GET /sales/ledger` | `totals` + `ledger` | 승인·환불 `UNION ALL` 1개 |

AI 매출 분석도 PR #187부터 같은 M9 서비스를 호출하므로 이 결과를 그대로 따른다.

## 3. 인덱스 추가 전 실행 계획

V1의 `ix_payments_1 (branch_id, status, approved_at)`은 집계 조건에 쓰이지 못했다. 집계는 `status`가 아니라 `approved_at IS NOT NULL`과 승인 시각 범위로 승인 결제를 고른다. 가운데 열 `status`에 조건이 없어서 `approved_at` 범위로 좁힐 수 없다. 옵티마이저는 이 인덱스 대신 `payments` 전체 탐색을 골랐다.

| 집계 | 승인 SQL | 환불 SQL |
|---|---|---|
| 매출 처리일 기준 | `payments` 전체 탐색(87,600행 읽고 1,074행 사용) | `ix_refunds_1` 범위 → `payments` PK |
| 매출 원결제일 기준 | `payments` 전체 탐색 | **`refunds` 전체 탐색**(4,419행) → `payments` PK 4,419회 |
| 이용권 판매량·순위 | `payments` 전체 탐색 → `uk_passes_1` | `ix_refunds_1` 범위 → `payments` PK → `uk_passes_1` |
| 추세 | `payments` 전체 탐색 | 처리일 기준이면 `ix_refunds_1` 또는 전체 탐색(아래 4절) |
| 최소 원장 | `payments` 전체 탐색 → `uk_passes_1` | 환불 SQL과 같음 |

ADR이 지목한 두 후보의 원인은 다음과 같았다.

- **원결제일 기준 환불**: `refunds`에는 결제 시각이 없다. 그래서 `refunds`를 모두 읽은 뒤 결제마다 PK로 조회해 시각을 확인했다.
- **상품별 판매량**: 이용권 쪽 조인(`uk_passes_1` 단건 조회)은 처음부터 문제가 없었다. 느린 원인은 앞단의 `payments` 전체 탐색이었다.

## 4. 결정: `ix_payments_branch_approved (branch_id, approved_at)`

[V10](../../src/main/resources/db/migration/V10__sales_aggregation_indexes.sql)으로 이 인덱스 하나만 추가했다.

### 검토한 후보

두 후보 모두 같은 시드로 측정했다.

| 후보 | 1개월·3지점 매출 | 1개월 원장 | 1년·10지점 지점 비교 | 판단 |
|---|---|---|---|---|
| 추가 전 | 19.4 ms | 37.1 ms | 40.5 ms | |
| **A: `(branch_id, approved_at)`** | 6.0 ms | 7.9 ms | 39.7 ms | **채택** |
| B: A + `purpose, amount_krw, issued_pass_quantity`(커버링) | 5.1 ms | 8.9 ms | 33.7 ms | 미채택 |

- B는 1년 집계에서만 15% 남짓 빨랐다. 1개월 집계는 A와 차이가 없었다.
- B는 인덱스 항목이 금액·수량 열만큼 넓다. 그 열을 집계 쿼리가 쓴다는 사실에 인덱스가 묶이기도 한다.
- 원장은 다른 열도 읽으므로 B로도 커버되지 않는다.
- 이득에 비해 유지 부담이 커서 A를 골랐다.

### 바꾸지 않은 것

- `ix_payments_1`은 지우거나 바꾸지 않았다. `branch_id` 외래 키와 결제 목록의 상태 조건이 이 인덱스를 쓴다. 그 사용처의 실행 계획 검토는 이 이슈의 범위 밖이다.
- 쿼리 문장(`SalesSourceRepository`)은 바꾸지 않았다. `status IN ('APPROVED','REFUNDED')` 조건을 붙여 기존 인덱스를 쓰게 하는 방법도 있다. 그러려면 "승인 결제 = `approved_at IS NOT NULL`"이라는 집계 정의를 상태 값과 다시 묶어야 한다. 그래서 택하지 않았다.

### 쓰기 비용

- `payments`의 쓰기는 결제 생성(INSERT) 1회와 승인·실패·환불 상태 변경 몇 회다.
- 새 인덱스 열 `branch_id`·`approved_at`은 승인 때 한 번 정해지고 바뀌지 않는다. 환불로 `status`가 바뀌어도 이 인덱스는 갱신되지 않는다.
- 결제당 보조 인덱스 항목 1개(약 30바이트)와 승인 시 1회 갱신이 추가된다. 지점의 결제 빈도(하루 수십~수백 건)에서는 무시할 수준으로 판단했다.
- 운영 환경에서 쓰기 지연을 측정하지는 않았다.

## 6. 남은 전체 탐색과 그 이유

| 표 | 남는 경우 | 이유 |
|---|---|---|
| `payments` | 10지점 전체 · 1년 조회(지점 비교·추세·원장·분류 필터 순위) | 모든 지점의 1년치는 이 시드에서 결제의 절반이다. 그 정도면 인덱스로 찾아 행마다 PK로 다시 읽는 것보다 표를 한 번 읽는 편이 싸다. 옵티마이저가 그렇게 판단했고, 측정에서도 인덱스 범위로 바뀐 경우가 없었다. 이력이 길어져 1년이 표의 작은 부분이 되면 같은 인덱스로 범위 탐색을 고를 수 있다. 이 경우는 측정하지 않았다. |
| `refunds` | 처리일 기준 · 1년 조회 | `ix_refunds_1 (refunded_at)`이 있다. 1년치가 환불의 절반이라 전체 탐색을 골랐다. 1개월 조회는 `ix_refunds_1` 범위를 쓴다. 처리일 기준은 지점 조건이 원결제의 `payments.branch_id`에 있다(M9-D05). 그래서 기간 안의 다른 지점 환불까지 읽고 버린다. 환불 수가 결제의 몇 %라 영향은 작다(1개월 3지점: 174행 읽고 50행 사용). |
| `passes` | 없음 | 모든 집계가 `uk_passes_1 (purchase_payment_id)` 단건 조회로 붙는다. |

전체 탐색이 아닌 나머지 비용은 다음과 같다.

- **임시 테이블 집계**: 모든 집계가 `GROUP BY`를 임시 테이블로 처리한다. 묶음 키가 계산식(Asia/Seoul 날짜)이거나, 이용권 스냅샷 열을 `utf8mb4_0900_bin`으로 바꾼 값이다. 그래서 인덱스 순서로 묶을 수 없다. 묶음 수는 작다(매출 ≤ 지점×용도, 추세 ≤ 일×지점×용도).
- **원장 정렬(filesort)**: 원장은 승인과 환불을 `UNION ALL`로 합친 뒤 `basis_at`으로 정렬한다. 두 원천을 합친 순서는 한 인덱스로 만들 수 없으므로, 조건에 맞는 모든 행을 정렬한 뒤 `LIMIT`을 적용한다. 1년·10지점 원장(약 4.5만 행)이 측정한 집계 중 가장 느렸다(약 150 ms, 29만 건 규모에서 약 460 ms). 페이지가 깊어져도(`OFFSET`) 같은 정렬을 반복한다.

## 7. 검증하지 않은 것

- 운영 DB의 실제 데이터 분포, 행 수, 버퍼 풀 크기에서의 실행 계획
- 이력이 2년보다 긴 경우 1년 조회가 인덱스 범위로 바뀌는지와 그때의 시간
- 운영 환경에서 인덱스 추가에 따른 결제 쓰기 지연
- 원장의 깊은 페이지(`OFFSET`이 큰 경우)의 시간
