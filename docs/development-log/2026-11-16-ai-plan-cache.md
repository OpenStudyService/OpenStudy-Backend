# 2026-11-16 AI 질문의 조회 계획 캐시

## 1. 배경 / 문제

- 사람들은 자주 쓰는 질문을 반복한다. 그런데 새 채팅에서 같은 질문을 하면 LLM(Qwen)이 매번 다시 호출된다.
- 같은 질문이면 저장된 조회 계획(QuerySpec·ViewSpec)을 재사용해 LLM 호출 비용을 줄이고자 한다.
- LLM을 부르는 곳은 두 군데다.
  1. **등록 분석 선택**: 키워드 규칙이 못 고른 질문을 10개 등록 분석 중 하나로 고른다.
  2. **생성 경로**: 등록 분석이 없는 질문의 SemanticPlan을 만들고, 서버가 QuerySpec·ViewSpec으로 컴파일한다.
- 엔진에 있던 `BoundedQueryCache`는 조회 결과(행) 캐시라서 이 목적과 다르다. 현재 어디에서도 쓰이지 않는다.

## 2. 검토한 선택지

사용자가 정책 세 가지를 정했다.

| 항목 | 선택지 | 결정 |
|---|---|---|
| 공유 범위 | 전체 사용자 공유 / 사용자별 | 전체 사용자 공유 |
| 같은 질문 판정 | 정규화한 문장 일치 / 의미 유사도 | 의미 유사도 |
| 무효화 | 30일 + 버전 변경 / 버전 변경만 / 7일 + 버전 변경 | 30일 + 버전 변경 |

## 3. 결정 및 이유

- **저장 대상은 계획뿐이다.** 결과 데이터는 저장하지 않는다.
  - 재사용할 때도 요청자의 권한과 지점 범위로 다시 검증하고 다시 실행한다. 그래서 전체 사용자가 공유해도 다른 사람의 데이터가 보이지 않는다.
  - 생성 경로의 계획은 지점 이름을 뺀 질문으로 만든다(`withoutBranchNames`). 그래서 지점이 달라도 같은 계획을 쓴다.
- **유사도만으로는 같은 질문으로 보지 않는다.** 로컬 임베딩(koen-e5-tiny-q8)으로 직접 재 보았다.

  | 질문 쌍 | 유사도 | 같은 질문? |
  |---|---|---|
  | 가장 많이 판매된 / 제일 많이 팔린 | 0.96 | 예 |
  | 가장 많이 판매된 / (띄어쓰기·어미 다름) | 0.935 | 예 |
  | 가장 많이 판매된 / 가장 **적게** 판매된 | **0.940** | 아니오 |
  | 이번 달 / **지난달** 가장 많이 판매된 | 0.92 | 아니오 |
  | 결제 금액 / 결제 **건수** 합계 | 0.89 | 아니오 |
  | 언제 가장 붐벼 / 가장 붐비는 시간대가 언제야 | 0.80 | 예 |

  - 뜻이 반대인 질문이 진짜 같은 질문보다 높게 나오기도 한다. 그래서 두 조건을 모두 만족할 때만 재사용한다.
    - 유사도 0.90 이상
    - 서버가 두 질문을 똑같이 읽음: 지표, 묶는 기준, 기간, 정렬, 언급된 기간, 숫자, "~별", 뜻을 바꾸는 단어(많/적, 평균, 제외/포함, 원결제일, 0원, 지금)
  - 이 때문에 "붐벼"(0.80)처럼 같은 뜻이어도 놓치는 경우가 있다. 잘못된 결과를 보여 주는 것보다 LLM을 한 번 더 부르는 편이 낫다고 판단했다.
- **유효 기간과 무효화**
  - 계획은 만든 시점부터 30일 동안 쓴다. 사용해도 기간은 늘어나지 않는다.
  - 버전 키가 바뀌면 이전 계획을 읽지 않는다. 버전 키는 형식 버전, 시맨틱 카탈로그 버전, 컴포넌트 카탈로그 버전, 모델 이름, 프롬프트로 만든다.
  - 등록 분석 선택 프롬프트는 문자열 해시가 자동으로 키에 들어간다. 생성 경로 프롬프트는 자동으로 들어가지 않으므로, 바꿀 때 `AiPlanCache.FORMAT`을 올려야 한다.
  - 종류별로 최대 500개를 두고, 넘치면 가장 오래 쓰지 않은 것부터 지운다.
- **캐시하지 않는 경우**
  - 후속 질문, 선택지 응답처럼 이전 대화 맥락을 쓰는 질문.
  - 되묻기·지원 안 함·실패 응답.

## 4. 구현 내용

- `V22__ai_plan_cache.sql`, `AiPlanCacheEntity`, `AiPlanCacheRepository`: 계획 캐시 테이블.
- `AiPlanCache`
  - `find`: 유사도와 서버 판독이 모두 맞는 가장 가까운 계획을 찾는다. 오류가 나면 캐시 없이 진행한다.
  - `storePick`, `storeGenerated`: 계획을 저장한다.
  - `reading`: 서버가 질문을 읽은 결과(위 비교 항목).
- `OpenStudyIntentAnalyzer.periodReadings`: 질문에 언급된 기간을 지금 기준 날짜 범위로 반환한다.
- `OpenStudyPlaybackGateway`: 등록 분석 선택 전에 캐시를 찾는다. LLM이 EXECUTE로 고른 분석은 저장한다. `PlanDecision.planCached`로 캐시 사용 여부를 전달한다.
- `AiWorkspaceService`
  - 생성 경로 전에 캐시를 찾는다. 찾으면 저장된 QuerySpec·ViewSpec을 다시 실행한다. 상대 기간(이번 달 등)은 지금 기준으로 다시 계산한다.
  - 저장된 계획이 더 이상 실행되지 않으면 LLM으로 다시 만든다.
  - 처리 과정에 "저장된 조회 계획 재사용 (LLM 호출 없음)"을, `securityGate.planCache`에 `HIT`를 남긴다.
- 테스트 정리: AI 테스트마다 `ai_plan_cache`를 비운다. 캐시는 전체 공유라서 테스트끼리 영향을 주기 때문이다.

## 5. 검증 결과

- `AiPlanCacheIntegrationTests` 통과(로컬 임베딩 모델 사용)
  - 같은 뜻은 같게, 많이/적게·이번 달/지난달·금액/건수·결제/환불·지점별/상품별·요일별/시간대별·7일/30일은 다르게 읽는지
  - 저장된 분석 선택을 같은 뜻의 질문으로만, 같은 버전 키로만 찾는지
  - 만료된 계획을 쓰지 않는지
- `AiGenerationPathIntegrationTests`에 추가한 테스트 통과
  - 새 대화에서 띄어쓰기·어미가 다른 같은 질문을 하면 모델 호출 없이 같은 결과가 나오는지
  - 기간이 다른 질문은 모델을 다시 호출하는지
  - 소유자가 만든 계획을 지점 하나만 가진 직원이 재사용하면 그 지점 합계만 나오는지
- 등록 분석 선택 캐시가 실제 Qwen 호출을 줄이는지는 live 모드 화면에서 확인한다(아래 결과 참고).
- 전체 백엔드 테스트(`./gradlew test`)는 실행하지 않았다. M11 마일스톤 테스트로 미뤘다.

## 6. 남은 작업 / 보류 사항

- 유사도 기준 0.90과 판독 항목은 이번 측정을 바탕으로 정했다. 실제 질문 기록이 쌓이면 적중률과 오적중을 다시 확인해야 한다.
- 캐시 비우기 관리 화면이나 API는 없다. 지금은 버전 키 변경, 30일 만료, 개수 상한으로만 정리된다.
