# 2026-11-04 룸 예약 취소·재예약과 이용 시작·완료 API

관련: Issue [#70](https://github.com/OpenStudyService/OpenStudy-Backend/issues/70), [계약 문서](../design/foundation/space-operations-api.md), [ADR-M6-001](../db/ADR-M6-001.md) M6-D04·D05, [M4 계약](../design/foundation/customer-sales-api.md), [예약 기록](2026-11-03-room-reservation-api.md).

## 1. 배경 / 문제

#69로 예약과 선결제가 들어왔지만 취소와 실제 이용 기록이 없었다. 취소는 환불 원장, 결제 상태, 예약 상태, 슬롯 해제가 함께 움직여야 한다. 하나만 남으면 돈과 시간 점유가 어긋난다. 재시도가 환불을 두 번 만들어서도 안 된다.

이용 시작·완료는 결제가 없는 현장 처리이고, 일반 직원도 할 수 있어야 한다. `room_usages`는 V1에 있었지만 쓰는 코드가 없어 응답의 `usage`가 항상 null이었다.

#69 기록의 확인 필요 항목도 여기서 풀어야 했다. 계약은 `완료`가 시간을 점유하지 않는다고 하면서 슬롯 삭제는 취소에만 적혀 있었다. 슬롯이 남으면 화면에 활성 예약이 없는데 `uk_room_reservation_slots_1`로 409가 날 수 있다.

## 2. 검토한 선택지

- **이용권 환불 재사용 여부**: `POST /payments/{id}/refund`의 `refund`는 멱등 처리, 이용권 환불, 목적 검사까지 묶여 있고 계약이 스터디룸 결제를 거절하도록 정했다. 호출 안쪽 부분만 나누는 대신, 예약 트랜잭션 안에서 부르는 `refundRoom`을 `chargeRoom`과 같은 모양으로 새로 두었다.
- **조기 완료 시 슬롯 처리**(사용자 승인 변경): 슬롯을 남기는 방안과 시작하지 않은 시간만 지우는 방안 중 후자로 정해졌다. 전자는 #69 기록의 문제가 그대로 남는다.
- **완료 경계**: 정각에 완료할 때 그 시간의 슬롯을 "진행 중"으로 볼지가 쟁점이었다. `슬롯 시작 > 처리 시각`만 지운다. 정각의 슬롯은 새 예약이 `startAt ≤ 현재`로 어차피 받지 못하므로 지워도 쓸 수 없고, 이미 시작한 시간을 남기는 쪽이 계약 문구와 맞는다.
- **겹침 판정 변경 여부**: 활성 상태 기준을 슬롯 기준으로 바꿀 필요가 있는지 확인했다. 아래 결정과 같이 바꾸지 않아도 일치한다.

## 3. 결정 및 이유

- **트랜잭션은 계약 표의 순서를 따른다.** 취소는 공통 guard → 권한 → 멱등 잠금 → 예약 행 잠금·검증 → 결제 행 잠금 → `refunds` → 결제·예약 갱신 → 슬롯 삭제 → 감사 → 이벤트 → 멱등 결과다.
- **겹침 판정은 그대로 활성 상태 기준이다.** 완료된 예약에 남는 슬롯은 처리 시각 이전에 시작한 시간뿐이고, 새 예약은 현재보다 뒤에 시작해야 한다(422 `RESERVATION_TIME_INVALID`). 따라서 남은 슬롯과 새 예약의 슬롯이 겹칠 수 없고, 슬롯 때문에 409가 나는 경우가 없다. 시험으로 확인했다.
- **멱등 재생은 version 검사보다 앞이다.** 처리된 취소의 재시도는 이미 지나간 version을 들고 오므로, 뒤에 두면 재시도가 항상 `VERSION_CONFLICT`가 된다. 트랜잭션 표의 순서이기도 하다.
- **요청 해시는 경로 ID·version·사유다.** 계약의 "허용 필드만 정규화한 본문과 path ID"를 따랐다. 같은 키에 다른 version이면 409 `IDEMPOTENCY_CONFLICT`다.
- **이용 시작의 룸 잠금은 쓰기 잠금이다.** 같은 룸의 두 시작을 직렬화해야 하는데 공유 잠금끼리는 서로 막지 않는다. Hibernate의 비관적 잠금은 version을 올리지 않으므로 룸 원장의 version은 그대로다. 시험으로 확인했다.
- **`branchOf`로 소속을 먼저 읽는다.** `RoomRepository`와 같은 이유다. 엔터티가 잠금 조회로 처음 적재되어야 항상 최신 값을 본다.
- **처리자 이름은 한 번에 조회한다.** `views`에서 `room_usages`와 직원 이름을 한 번씩만 읽는다. `started_by`·`ended_by`는 `ON DELETE SET NULL`이라 null일 수 있고 `names`의 `Set.copyOf`가 null을 받지 못하므로 먼저 걸러 낸다.
- **`RoomUsageRepository`와 `refundRoom`의 호출 방향**: 예약 → 결제 단방향을 유지했다. `ModuleBoundaryTests`가 순환을 금지한다.

계약이 정하지 않아 판단한 점:

- **입력 형식 검증 위치**: 취소 표는 404부터 시작하지만, M4 규칙("입력 형식 검증은 멱등 조회보다 먼저")과 기존 명령을 따라 422를 404·403보다 먼저 판정한다.
- **멱등 범위**: M4 환불과 같이 (요청자, operation, 대상 ID, 키)이고 대상은 예약 ID다. 다른 직원이 같은 키를 보내면 별개 요청이라 `VERSION_CONFLICT` 또는 `RESERVATION_NOT_CANCELLABLE`이다.
- **만료된 키 재사용**: #69와 같이 기록을 지우고 새로 처리한다. 예약이 이미 취소되어 있으므로 `VERSION_CONFLICT` 또는 `RESERVATION_NOT_CANCELLABLE`이고 환불은 생기지 않는다.
- **이용 시작 판정 순서**: 계약 표의 행 순서대로 version → 상태 → 지점 → 룸 → 다른 이용 중이다.
- **시작 전에 시작·완료한 경우**: 시작 시각과 비교하지 않으므로 14:00 예약을 13:00에 시작해 13:30에 완료할 수 있다. 이때 슬롯은 모두 "아직 시작하지 않은 시간"이라 전부 삭제된다.
- **조기 완료의 금액**: 환불하지 않는다. 부분 환불은 범위 밖이고 결제는 `승인`으로 남는다. 예약의 `startAt`·`endAt`도 바꾸지 않으므로, 달력에 `완료` 구간과 그 남은 시간의 새 `확정` 구간이 겹쳐 보일 수 있다.
- **달력의 `취소`**: 계약이 `결제 실패`만 제외하므로 취소도 달력에 그대로 나온다.
- **감사 값**: `action`은 예약 생성과 같이 결과 상태 이름(`CANCELLED`, `IN_USE`, `COMPLETED`)이다. 결제 쪽은 이용권 환불과 같은 `REFUNDED`다. 취소 사유는 `reason` 열, 완료의 해제 슬롯 수는 `after_json`의 `releasedSlots`다.
- **`IN_USE`인데 `room_usages`가 없는 행**: API로는 생기지 않는다. 완료 시 `IllegalStateException`으로 500이다.

## 4. 구현 내용

- 계약(5번, 사용자 승인): `space-operations-api.md`의 이용 시작·완료 절에 완료 시 슬롯 규칙과 예시, 트랜잭션 표에 `이용 완료` 행 추가. `openapi.json`의 `completeRoomUsage` 설명 보강. 그 밖의 변경은 구현 상태 표기뿐이다.
- `modules/reservation`: `RoomUsage` entity·저장소, 슬롯 삭제 쿼리 2개, `RoomReservationService.cancel`·`start`·`complete`, `views`의 `usage`, 컨트롤러 경로 3개
- `modules/payment`: `PaymentService.refundRoom`
- OpenAPI 3개 operation을 `implemented`로 변경. 마이그레이션은 없다.

## 5. 검증 결과

- `./gradlew test` 전체(29분 52초): 62개 suite, 722개 테스트, 실패·오류·건너뜀 0. Testcontainers MySQL 사용. 수치는 `build/test-results/test/*.xml`을 합산했다. 전체 실행은 코드 기준 1회로 첫 실행에서 통과했고, 그 뒤에는 이 기록만 바꿨다.
- 신규 `RoomCancelUsageIntegrationTests` 34개를 HTTP와 DB로 확인했다. `SpaceOperationsContractTests`는 구현 상태와 완료 규칙 문구 기준으로 고쳤다.
  - 취소 권한: 권한별 403, 범위 밖 404, 사유 누락·공백·501자, 키 누락, 금액 필드 거부
  - 시작 시각 경계: 1마이크로초 전 허용, 같은 시각과 이후 거절, `canCancel`의 같은 경계
  - 상태별 거부: 이용 중·완료·취소·결제 실패
  - 정합성: `refunds`(금액·처리 지점·처리자·사유·시각), 결제 `REFUNDED`와 금액·승인 시각 유지, 예약, 슬롯, `Payment.refund`, `canRefund`, 감사, 이벤트
  - 중간 실패: 슬롯 삭제에서 예외를 내면 취소·완료 모두 전부 롤백되고, 취소는 같은 키로 다시 성공
  - 재예약: 새 예약·새 결제, 원기록 유지, 결제당 환불 1건
  - 멱등: 같은 키 재시도의 같은 응답과 환불 1건, 다른 사유·version 409, 다른 직원, 거절의 미저장, 만료된 키
  - 이용: 일반 직원 포함 권한, 상태 전이, 예약 구간 비교 없음, 운영 중단 룸, 운영 중지 지점의 취소·완료 허용과 시작·예약 거부, 같은 룸 이용 중, 판정 순서, 룸 version 유지
  - 조기 완료: 계약 예시(15:30 완료 시 16:00 슬롯만 삭제), 정각·1마이크로초 전 경계, 시작 전 완료, 늦은 완료, 남은 시간 전부 재예약, 과거 시간은 422
  - 조회: 상태 4종의 목록·달력·상세 응답 일치와 상태 필터, `billing` 없는 직원에게도 `usage` 노출, 처리자가 null인 사용 기록
  - N+1: 6건 목록·달력에서 `names`와 `findByReservationIdIn`이 각 1회, 건별 조회 0회(spy로 호출 수 확인)
- **실제 동시 실행**(요청마다 스레드를 두고 래치로 동시에 출발): 전부 통과했다.
  - 같은 키 취소 8건 3회: 모두 200·같은 본문, 환불 1건, 감사 1건
  - 다른 키 취소 8건 3회(직원 2명): 1건 200, 나머지 `VERSION_CONFLICT`, 환불 1건, 결제 version 1
  - 취소와 이용 시작 10회: 항상 한쪽만 200, 다른 쪽 `VERSION_CONFLICT`. 전체 실행에서 취소가 이긴 경우 5회
  - 같은 룸 두 예약의 동시 시작 6회: 1건 200, 다른 쪽 `ROOM_IN_USE`, 이용 중 1건
  - 취소와 같은 시간 새 예약 8회: 취소는 항상 200, 환불 1건. 전체 실행에서 새 예약이 확정된 경우 4회, 나머지는 `ROOM_TIME_CONFLICT`이고 결제가 남지 않음

**한계와 실행하지 않은 것**

- 모든 명령이 공통 guard로 직렬화되므로 동시성 시험의 통과는 주로 guard의 효과다. guard 없이 행 잠금만으로 버티는지는 검증하지 않았다.
- 시각 고정은 시험에서 예약 서비스의 시계만 바꿔서 했다. 세션 만료는 실제 시각을 따른다.
- SSE로 이벤트가 실제 전달되는지는 시험하지 않았다. 아웃박스 행까지만 확인했다.
- 실제 서버 실행, Frontend 연결, 인프라 서버 검증, 부하 측정은 하지 않았다.

## 6. 남은 작업 / 보류 사항

- Frontend: `완료` 구간과 새 예약이 겹쳐 보이는 달력 표시를 확인해야 한다.
- `AuthorizedCommands` guard를 나누면 `ROOM_IN_USE`와 겹침 확인이 일반 읽기라는 점을 다시 봐야 한다. 이 트랜잭션의 스냅샷은 guard 직후의 `branchOf`에서 잡히므로, guard 없이는 룸 잠금 뒤에도 오래된 값을 볼 수 있다.
- 서버 시계가 뒤로 가면 `ended_at < started_at`가 되어 `ck_room_usages_1`로 500이 날 수 있다. 좌석 퇴실과 같이 별도로 막지 않았다.
- #69 기록의 `Payment` 스키마 설명 문구 문제는 그대로다.
- 사물함(#71), 타 지점 요약·이력(#72)은 범위 밖이다.
