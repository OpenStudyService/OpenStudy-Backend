# 생성된 Spring Boot 프로젝트에 디렉토리 골격 적용

작업일: 2026-10-18 KST.

## 배경과 문제

사용자가 IntelliJ에서 Spring Boot 프로젝트를 생성한 뒤, 이전에 정한 디렉토리 구조를 현재 빈 프로젝트에 적용하도록 요청했다. 이전 골격은 docs/directory-architecture에 보관되어 있고, 실제 src에는 실행 클래스·기본 컨텍스트 테스트·application.yaml만 있었다.

## 검토한 방법

보관된 골격의 src/scripts 중 디렉토리 보존 파일·패키지 책임 설명·안내 파일만 실제 경로에 복사했다. 보관본 전체를 복사하면 이전 README와 IDE 파일, 과거 상태가 현재 프로젝트에 섞이므로 필요한 파일만 선택했다.

## 결정과 이유

기존 20개 모듈과 각 모듈의 다섯 계층을 그대로 적용했다. Spring Boot 실행 클래스가 com.openstudy에 있어 모든 업무 패키지는 그 하위에 둔다. 하나의 Gradle 프로젝트를 유지하고 별도 서브프로젝트/실행 클래스를 만들지 않는다. 업무 구현·빌드/보안/DB 설정 변경은 이번 요청 범위에 포함하지 않는다.

## 반영 내용

bootstrap/shared/platform/modules와 대응 테스트 경로, workforce 내부 네 영역, migration/로컬 seed/fixture/scripts 위치를 만들었다. 새 README에는 실제 생성된 Java21·Boot4.1.1·Gradle9.8.1 구성과 경로를 기록했다. 새로 복사한 리소스/테스트 안내는 현재 프로젝트 상태에 맞게 갱신했다. 보관본과 기존 구조 설계·개발 기록은 수정하지 않았다.

## 검증 결과

- 실제 소스 경로의 업무 모듈 20개, 계층 디렉토리 100개, 모듈별 테스트 위치 20개를 확인했다.
- 새 package-info.java 20개와 기존 실행 클래스의 패키지 선언/경로가 일치한다.
- 기존 파일 201개의 SHA-256이 모두 유지된다. build.gradle/settings.gradle/Gradle Wrapper/application.yaml/실행·기본 테스트 클래스/기존 문서/보관본이 포함된다. IDE·Gradle 캐시·빌드 출력은 해시 비교 범위에서 제외했다.
- 새 README의 상대 링크 2개는 실제 대상과 일치한다.
- 업무 코드·SQL·새 테스트를 추가하지 않은 구조 변경이므로 Gradle 빌드/서버/DB 테스트는 실행하지 않았다. 컴파일·기동·실DB 연결의 성공을 주장하지 않는다.

## 남은 작업

MySQL 개발/테스트 DB 접속 설정, 실제 빌드/기동, ArchUnit과 경계 검사, 마이그레이션/시드, 업무 구현은 별도 작업이다. 작업 시점에 backend는 Git 저장소가 아니므로 상위 AGENTS.md의 작업 브랜치 규칙을 적용할 저장소가 없었다. 새 Git 저장소를 생성하거나 커밋하지 않았다.
