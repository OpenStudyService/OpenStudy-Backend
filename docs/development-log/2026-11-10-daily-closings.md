# 2026-11-10 일별 마감·정산과 마감 후 조정 이력 (#115)

## 1. 배경 / 문제

- M13 계약(#111)의 일별 마감을 구현한다(FR-PAY-14, ADR-M13-001 M13-D04·D08·D11).
- 지점 MANAGER 이상이 끝난 날 하나를 한 번 마감하고, 그날의 M9 매출을 두 환불 기준으로 저장한다.
- 마감은 아무 업무도 막지 않는다. 마감된 날 승인된 결제가 나중에 환불되면 그 환불이 조정 이력으로 남는다. 마감 상세는 마감 금액, 조정, 현재 금액을 보여 준다.

## 2. 검토한 선택지

- **마감과 조정 기록의 위치**: 마감은 M9 집계를 쓰므로 매출(sales) 모듈에 둔다. 조정은 환불 트랜잭션이 남겨야 하는데, 환불은 결제(payment) 모듈에 있다.
  - 결제 모듈이 매출 모듈 서비스를 부르는 방법: 지금은 두 모듈이 서로 의존하지 않아 가능하지만, 결제가 매출에 의존하게 된다.
  - 결제 모듈이 조정 행을 테이블로 직접 쓰는 방법: 모듈 의존이 생기지 않는다.
  - 후자를 택했다. 환불 저장 직후 `INSERT ... SELECT` 한 문장으로, 원결제의 승인일(Asia/Seoul)·지점에 마감이 있을 때만 행을 만든다.
  - 금액·처리자·시각은 방금 저장한 환불 행에서 복사한다. 네이티브 질의의 시각 바인딩에서 생길 수 있는 시간대 문제를 피하기 위해서다. 사유는 복사하지 않고 `refunds.reason`을 참조한다(계약).
- **스냅샷 계산**: 마감 전용 질의를 새로 쓰는 방법과 `GET /sales/revenue`의 서비스(`SalesRevenueService`)를 그대로 부르는 방법을 비교했다. 인수 조건 "마감 스냅샷이 같은 조건의 M9 집계와 일치"를 구조적으로 보장하는 후자를 택했다. M9 응답에 없는 결제 수단별 소계만 따로 계산한다.

## 3. 결정 및 이유

- **권한**: 마감 생성은 지점 MANAGER 이상 + `sales:read`다. 이를 위해 `BranchAction.CLOSE_SALES`를 더했다(계약). 조회는 지점의 `sales:read`이고, 보이지 않는 지점의 마감은 404, 보이지만 `sales:read`가 없으면 403이다.
- **마감 시점**: `businessDate` < 오늘(Asia/Seoul)만 마감한다(M13-D11). 같은 지점·날짜는 유일 키와 사전 조회로 한 번만이다(409 `CLOSING_EXISTS`, `closingId`).
- **스냅샷**: 처리일·원결제일 기준 각각의 합계, 용도별 소계, 결제 수단별 소계를 JSON으로 저장한다. 수단별 소계에서 환불은 원결제 수단으로 나눈다.
- **조정 대상**: 처리일 기준으로는 지난날 수치가 바뀌지 않는다. 결제 승인과 환불은 항상 처리 시각(오늘)에 들어가기 때문이다. 그래서 조정은 원결제일 기준의 변화이고, `difference = 현재 원결제일 합계 − 스냅샷 원결제일 합계 = Σ조정`이다(인수 조건 "마감 금액 + 조정 합계 = 현재 금액").
- **동시성**: 마감 생성과 환불은 모두 공통 잠금 순서에서 지점 행 전체를 잠근다. 같은 지점의 마감과 환불은 차례로 처리된다.
- **조정 사유 노출**: 원결제 지점의 `payments:read`가 있을 때만 `reason`을 준다(계약).
- **목록 기본 기간**: 계약이 정하지 않아 "지난달 1일부터 오늘까지"로 정하고 계약 문서·OpenAPI에 적었다.

## 5. 검증 결과

- `DailyClosingIntegrationTests` 3개 통과(HTTP·MySQL). 마감은 끝난 날만 되므로, 테스트는 API로 만든 결제·환불의 시각을 DB에서 어제로 옮겨 시나리오를 만든다. 인수 조건별로 다음을 확인했다.
  1. **권한과 1회 마감**
     - 일반 직원, `sales:read` 없는 매니저는 403이다. 오늘·미래는 422 `CLOSING_DATE_OPEN`, 형식 오류와 키 누락은 422다.
     - 같은 키는 재생하고, 두 번째 마감은 409 `CLOSING_EXISTS`(`closingId`)다.
     - 조회는 `sales:read`가 필요하다. 다른 지점 마감은 404, 다른 지점 목록은 403이다.
  2. **스냅샷 = M9**
     - 어제 승인 2건(카드·현금)과 어제 처리된 환불 2건(어제 결제 1건, 그제 결제 1건)으로 두 환불 기준의 합계·용도별 소계가 `GET /sales/revenue`와 같다.
     - 수단별 소계 합이 합계와 같다.
     - 처리일 기준 순매출은 0이고, 원결제일 기준 순매출은 10,000원이다.
  3. **마감 후 환불**: 마감된 날 결제의 환불은 처리되고, 조정 이력에 금액 −10,000원, 사유, 처리자가 남는다. 오늘 결제의 환불은 조정을 만들지 않는다.
  4. **등식**: 스냅샷(원결제일) 20,000원 + 조정 −10,000원 = 현재 10,000원이다. 처리일 기준 스냅샷은 M9와 계속 같다.
  5. **사유 노출과 목록**: `payments:read` 없는 매니저에게 사유는 null이다. 목록의 조정 수가 맞다.
  - 응답 필드가 계약 schema와 같다.
- 전체 `./gradlew test`(15분 54초): 1,098개 실행, 실패 0, 건너뜀 26.
