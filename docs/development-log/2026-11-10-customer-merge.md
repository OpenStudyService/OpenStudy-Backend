# 2026-11-10 중복 고객 확인과 수동 병합 (#114)

## 1. 배경 / 문제

- M13 계약(#111)의 중복 고객 확인·병합을 구현한다(FR-MEM-08, ADR-M13-001 M13-D03·D07·D13).
- 중복 의심은 같은 숫자 연락처의 병합되지 않은 고객 묶음이다(M13-D13). 병합은 OWNER만 하고 되돌리지 않는다(M13-D03).
- 흡수된 고객은 삭제하지 않고 `병합됨` 상태와 대상 고객 참조를 남긴다. 기존 결제·이용권·이용 기록의 고객 참조는 바꾸지 않는다. 대신 대상 고객의 상세·이력이 흡수 고객의 기록을 함께 보여 준다(M13-D07).
- 계약의 `x-planned-changes` 중 #114 항목을 본 정의로 옮긴다.

## 2. 검토한 선택지

- **대상 고객 기록의 범위 확장 방법**
  - 결제·이용권·좌석 이용·예약·사물함 목록은 각 모듈의 검색 저장소가 `customerId`로 거른다.
  - 모듈마다 필터 타입을 ID 목록으로 바꾸는 방법과, 각 질의의 고객 조건을 "이 고객 또는 이 고객으로 병합된 고객"(`customers` 하위 질의)으로 넓히는 방법을 비교했다.
  - 서비스·DTO를 바꾸지 않고 조건 한 줄만 바뀌는 후자를 택했다. 모든 모듈이 이미 고객 모듈에 의존하므로 순환은 생기지 않는다.
- **흡수 고객의 남은 이용권**: 구현 중 계약이 정하지 않은 문제를 발견해 사용자에게 물었다.
  - 흡수 고객은 입실할 수 없고(계약), 입실은 "이용권이 입실하는 고객의 것"인지 확인한다. 그대로 두면 흡수 고객의 남은 이용권은 아무도 쓸 수 없다.
  - 선택지는 세 가지였다: 대상 고객이 사용, 남은 이용권이 있으면 병합 거부, 그대로 두기.
- **병합 이력의 처리자 이름**: 고객 모듈이 직원 모듈에 의존하지 않도록, 이름은 JPQL 엔터티 이름(`Employee`)으로 읽었다(#112·#113과 같은 방식).

## 3. 결정 및 이유

- **흡수 고객의 이용권: 대상 고객이 사용(2026-11-10 사용자 결정, 추천안)**
  - 입실에서 이용권 소유 확인을 "입실 고객 또는 입실 고객으로 병합된 고객"으로 넓혔다.
  - 입실 조회의 사용 가능 이용권도 대상 고객 후보에 함께 나온다.
  - 이용권·결제의 고객 참조는 그대로이고, 좌석 이용 기록에는 입실한 대상 고객이 남는다.
  - 계약 문서와 M13 결정 표에 적었다.
- **연쇄 병합**: 이미 다른 고객을 흡수한 고객이 흡수되면, 그 고객들도 새 대상으로 옮긴다. 병합 대상은 항상 병합되지 않은 고객 하나다. 옮긴 고객마다 이력 행을 남기고 `via`에 이전 대상을 적는다.
- **대상 고객의 조회 범위(M4-D05)**: 대상 또는 흡수 고객의 등록 지점·결제 지점이 scope에 있으면 보인다. 흡수 고객이 보이던 지점에서 대상 고객을 찾을 수 있게 한다.
- **흡수 고객에게 오는 명령**
  - 판매·예약·사물함 배정·입실은 409 `CUSTOMER_NOT_ACTIVE`에 `mergedIntoCustomerId`를 담아 대상 고객으로 안내한다(인수 조건 "대상 고객으로 안내").
  - 이 응답을 담도록 입실과 사물함 배정의 409 schema를 `OperationsConflictError`로 바꿨다.
  - 수정·상태 변경은 409 `CUSTOMER_ALREADY_MERGED`다. 상태 변경으로 `병합됨`을 지정하면 422다.
- **검사 순서**: 형식(422) → OWNER(403) → 자기 자신(422 `CUSTOMER_MERGE_SELF`) → 없음(404) → 병합됨(409) → 두 version(409). 계약 표는 OWNER를 첫 줄에 두었지만, 본문 형식 검사를 명령 밖에서 먼저 하는 기존 구현 관례에 맞춰 표를 고쳤다.
- **동시 병합**: OWNER 명령은 공통 가드를 먼저 잠그므로 두 병합은 차례로 처리된다. 같은 고객을 두 대상으로 동시에 병합하면 하나만 성공하고, 다른 쪽은 409다.
- **대상 고객의 version**: 병합으로 대상 고객이 보여 주는 내용이 바뀌므로 대상 행이 변하지 않아도 version을 올린다. 화면이 다시 읽게 한다.
- **목록**: 기본 고객 목록은 `병합됨`을 빼고, `status=병합됨`으로 따로 본다. 정확 일치 입실 조회는 흡수 고객 대신 대상 고객을 한 번만 돌려준다.

## 4. 구현 내용

- **V14**
  - `customers.status`에 `MERGED`, `merged_into_customer_id`(외래 키, 인덱스)를 추가했다. `MERGED`와 대상 참조가 함께 있도록 CHECK를 걸었다.
  - 이력 테이블 `customer_merges`(대상·흡수·중간 고객, 처리자, 시각, 사유, 자기 병합 CHECK)를 추가했다.
  - 자기 참조 CHECK는 MySQL이 AUTO_INCREMENT 칼럼 CHECK를 허용하지 않아 서비스에서 막는다.
- **고객 모듈**
  - `CustomerMergeService`(중복 묶음·병합·이력), `CustomerMergeController`(operation 3개)
  - `CustomerMerge` 엔터티·저장소
  - 고객 상세의 `mergedInto`·`absorbedCustomerCount`
  - 목록 제외, 조회 범위 확장, 판매·입실 거부와 대상 안내, 정확 일치 조회의 대상 치환
- **다른 모듈의 고객 조건**: 결제·이용권·좌석 이용·예약·사물함 검색, 이용권 이력(`ledgers`), 공간 이력(`ofCustomer`), 타 지점 요약의 보유 이용권, 입실 조회의 사용 가능 이용권, 입실의 이용권 소유 확인
- **계약**
  - OpenAPI: #114 `x-planned-changes`를 본 정의로 옮겼다. `Customer`·`CustomerListItem`의 `병합됨`, 목록 `status`, 각 목록 설명을 고쳤고, 입실·사물함 배정·고객 수정·상태 변경의 409를 `OperationsConflictError`로 바꿨다. operation 3개를 `implemented`로 바꿨다.
  - 문서: M13 계약, M4·M5·M6 계약의 오류 설명
- **DB 문서**: `schema-full.sql` V14 재추출, ERD, DB 안내(75개 테이블)
- **기존 테스트 조정**: 마이그레이션 번호·테이블 수 고정 테스트, V13 테스트를 V13까지만 적용, V14 마이그레이션 테스트 추가, M13 계약 테스트

## 5. 검증 결과

- `CustomerMergeIntegrationTests` 4개 통과(HTTP·MySQL). 인수 조건별로 다음을 확인했다.
  1. **OWNER만**: 지점 관리자는 중복 묶음·병합 모두 403이다.
  2. **병합 전 비교**: 중복 묶음에 두 고객과 결제 수·마지막 활동이 나온다. 병합 전 두 고객 각각의 결제·이용권 이력을 조회할 수 있다.
  3. **참조 보존**: 흡수 고객은 `병합됨`과 `mergedInto`를 가진다. 흡수 고객의 결제·이용권의 `customer_id`는 그대로다.
  4. **대상 고객 조회·합계**
     - 대상 고객의 결제·이용권 목록과 이용권 이력에 흡수 고객의 기록이 함께 나오고, 각 행의 고객은 원래 고객이다.
     - 흡수 고객이 결제한 지점의 직원이 대상 고객을 볼 수 있다.
     - 병합 전후 매출 합계(`/sales/revenue`)가 같다.
     - 목록은 `병합됨`을 빼고 따로 보여 준다. 묶음에서 사라진다.
  5. **이력**: 대상·흡수·처리자·시각·사유가 남고 두 고객 모두에서 조회된다. 감사 기록이 남는다.
  6. **거부**
     - 자기 병합 422, 없는 고객 404, 낡은 version 409, 사유 누락 422
     - 같은 고객을 두 대상으로 동시에 병합하면 하나만 200이고 이력은 1행이다.
     - 재병합·병합된 고객으로의 병합은 409 `CUSTOMER_ALREADY_MERGED`(`mergedIntoCustomerId`)다.
     - 병합된 고객의 수정은 409, `병합됨` 상태 지정은 422다.
     - 연쇄 병합은 이전에 흡수된 고객을 새 대상으로 옮기고 `via`를 남긴다.
  7. **흡수 고객 판매·입실**
     - 판매·입실은 409 `CUSTOMER_NOT_ACTIVE`이고 `mergedIntoCustomerId`로 대상을 알려 준다.
     - 정확 일치 조회는 대상 고객만 돌려주고, 흡수 고객의 이용권을 후보로 담는다.
     - 대상 고객이 그 이용권으로 입실하고, 이용권의 고객은 그대로다.
- 관련 모듈(고객·결제·이용권·좌석·예약·사물함·이용권 이력·고객 이력·문의)·아키텍처·마이그레이션 테스트: 537개 실행, 실패 0.
- 전체 `./gradlew test`(19분 9초): 1,094개 실행, 실패 0, 건너뜀 26.
