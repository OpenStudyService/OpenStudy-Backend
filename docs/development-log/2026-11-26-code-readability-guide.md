# 2026-11-26 코드 가독성 규칙 문서 공개

## 1. 배경 / 문제

`docs/architecture/code-readability.md`는 직접 정리한 두 작업(auth 모듈, 비밀번호 재설정 메일)의 패턴을 뽑아 만든 규칙이다. 처음에는 저장소에 올리지 않는 로컬 문서로 두었다(`.git/info/exclude`).

#250(모듈 단위 가독성 정리)을 진행하면서 다음 문제가 드러났다.

- PR과 개발 기록이 "규칙 문서 8장"처럼 이 문서를 근거로 들지만, 리뷰어는 문서를 볼 수 없었다.
  - 컨트롤러 경로 규칙을 잘못 적용한 일(#263으로 되돌림)도 리뷰에서 규칙 원문을 함께 볼 수 있었다면 더 빨리 잡혔을 것이다.
- 규칙이 작업 중에 계속 보완되는데(8장 기준, builder 기준) 변경 이력이 남지 않았다.
- 이 체크아웃 밖(다른 워크트리, 다른 작업자)에서는 참조할 수 없었다.

## 2. 검토한 선택지

- 로컬 문서로 유지하고 #250 이슈 본문에 핵심만 요약: 원문과 요약이 따로 놀고, 이력도 남지 않는다.
- 저장소에 올리고 README·AGENTS.md에서 연결: 리뷰 근거가 저장소에 남고 변경 이력이 추적된다. 이 방법을 택했다.

## 3. 결정 및 이유

- 문서를 저장소에 올리고 `.git/info/exclude` 항목을 지웠다.
- 공유 문서로 다듬으면서 특정 커밋에 기대던 서술(커밋 해시를 근거로 든 부분)은 출처 한 줄로 줄였다.
- #250에서 정한 기준을 규칙으로 보탰다.
  - 메서드 이름 접두사 표(`find`·`to`·`require`·`is` 등)와 이름이 동작과 다르면 바로잡는다는 원칙
  - builder 사용 기준(2.2): 같은 모양의 생성이 반복되고, 빈 칸이나 같은 타입 인자 연속이 있을 때 쓴다. 한 곳에서 모든 칸을 채우는 변환 생성자는 생성자로 둔다.
  - 엔티티의 Lombok 사용법, 120자 줄 길이, 한 줄에 문장 하나, 필드 어노테이션 배치
  - `@Query`의 text block 작성(토큰 유지)
  - 컨트롤러 공통 접두사 기준(8.1, #263에서 확인)과 operationId 이름 규칙(8.2)
  - boolean으로 조건을 나눌 때 단락 평가로 건너뛰던 부수 효과 호출을 유지하는 원칙
  - 다른 모듈이 쓰는 public 이름은 모듈 단위 정리에서 바꾸지 않는 원칙
- "아직 정하지 않은 항목"은 import 순서와 와일드카드 import만 남겼다.
  - builder 결과의 `var`는 #252에서 정리되어 2.1 규칙에 흡수했다.
- README의 아키텍처 상세 링크와 AGENTS.md의 "코드 작성 규칙" 절에서 문서를 연결했다.

## 4. 구현 내용

- `docs/architecture/code-readability.md` 추가(정리본)
- `README.md`: 아키텍처 상세 링크에 "코드 가독성 규칙" 추가
- `AGENTS.md`: "코드 작성 규칙" 절 추가(규칙 문서를 따르고, 규칙을 바꾸면 문서와 개발 기록을 함께 고친다)

## 5. 검증 결과

- 문서 변경만 있어 테스트는 실행하지 않았다.
- 문서 안의 상대 링크(개발 기록 두 개)가 저장소에 있는 파일을 가리키는 것을 확인했다.

## 6. 남은 작업 / 보류 사항

- import 순서와 와일드카드 import 허용 여부는 아직 정하지 않았다(#250 "결정 필요").
- 규칙의 자동 검사(Checkstyle 등)는 #250 범위에서 제외했다. 필요하면 별도 이슈로 다룬다.
