# 2026-11-02 채널·참여자 관리와 메시지·스레드·과거 조회·읽음·재전송 API

관련: Issue [#76](https://github.com/OpenStudyService/OpenStudy-Backend/issues/76), [계약 문서](../design/foundation/collaboration-api.md), [ADR-M7-001](../db/ADR-M7-001.md) M7-D04·D07과 변경 이력(2026-11-01), [공지 API 기록](2026-11-02-notice-api.md).

## 1. 배경 / 문제

채널 화면이 로컬 샘플로만 동작했다. `modules/chat`이 비어 있었기 때문이다. #74 계약이 병합되어 채널·메시지 operation 13개를 구현할 수 있게 됐다. 범위 밖은 DM, 실시간 전송(M14), 업무 카드(#77)다.

M7에서 가장 큰 이슈이고 다른 협업 기능과 다른 점이 세 가지 있다.

- **접근 기준이 지점 권한이 아니라 참여다.** 관리자도 참여하지 않으면 메시지를 볼 수 없고, 없는 채널과 구분되지 않아야 한다.
- **권한 회수가 다른 모듈에서 일어난다.** 소속 회수와 계정 상태 변경이 채널 참여를 같은 트랜잭션에서 끝내야 한다(M7-D07). "후속 범위로 미루지 않는다"가 ADR의 조건이다.
- **메시지 경계가 많다.** 재전송 멱등, 커서 페이지 경계, 스레드 깊이, 앞으로만 가는 읽음 위치가 모두 인수 조건이다.

스키마는 계약이 승인한 `conversations.description`·`version` 두 열만 추가했다.

## 2. 검토한 선택지

- **소속 회수·계정 변경에서 채널 참여 끝내기**
  - 직접 호출: `EmployeeManagementService`가 채팅 서비스를 부른다. 채팅은 직원 이름·자격 조회를 위해 이미 `employee`를 참조하므로 모듈 순환이 되고 `ModuleBoundaryTests`가 거부한다.
  - 동기 이벤트: `employee`가 `EmployeeAccessReduced`를 발행하고 채팅이 듣는다. `@EventListener`는 호출 스레드·트랜잭션에서 돌므로 같은 트랜잭션 조건을 지키고, 의존 방향이 그대로다. 이것을 골랐다. 리스너에 `Propagation.MANDATORY`를 걸어 트랜잭션 밖 호출을 막았다.
- **무엇을 끝낼지 판단하는 방식**
  - 변경 내용에서 추론: "지점 A 회수 → A 채널 종료" 식이다. 전체 채널은 다른 소속이 남았는지 따로 따져야 하고 경로마다 규칙이 갈라진다.
  - 자격을 다시 계산: 요청자의 열린 참여 전체를 돌며 현재 자격을 확인한다. 소속 회수와 계정 상태가 같은 코드로 처리되고, 자격 규칙이 후보 조회·참여자 검증과 같은 SQL을 쓴다. 이것을 골랐다.
- **메시지 전송·읽음의 잠금**
  - 공통 가드(`AuthorizedCommands`): 소속 회수·참여자 변경도 같은 가드를 지나므로 전송과의 경합이 사라진다. 대신 전송이 모든 명령과 직렬화된다.
  - 참여 행 잠금만 사용: 동시성은 높지만 ID 순서와 커밋 순서가 어긋날 수 있다. 큰 ID가 먼저 커밋되면 그 위치까지 읽은 사용자에게 작은 ID 메시지가 읽음으로 계산되고, 커서로는 다시 나오지 않는다.
  - 가드를 골랐다. 주석의 "split only after contention measurements" 방침과 같고, 측정 없이 잠금을 나누면 위 문제를 새로 풀어야 한다. 처리량은 측정하지 않았다(6절).
- **새 진입점**: 기존 `AuthorizedCommands` 메서드는 지점 권한을 먼저 검사해 403을 낸다. 채널은 참여 여부에 따라 404가 먼저여야 하므로 `activeEmployee`(가드·잠금 순서는 같고 계정 활성만 확인)를 추가하고 판단은 콜백에서 잠긴 행으로 한다.

## 3. 결정 및 이유

- **접근 판단을 `ChannelAccess` 한 곳에 모았다.** 참여자는 "열린 행 + 지금 자격"이다. 행만 믿지 않으므로 어떤 이유로 행이 남아도 접근이 열리지 않는다. DM은 이 클래스가 채널이 아닌 것으로 처리해 모든 API가 404다.
- **판단 순서**: 보임(404) → 관리 권한(403) → 입력·version(422·409) → 자격(422). 메시지는 참여(404)를 입력 검사보다 먼저 한다. 비참여자는 `before=abc`나 빈 본문을 보내도 404라 응답으로 알 수 있는 것이 없다. 공지·업무는 입력을 먼저 검사하지만, 채널은 "참여자가 아니면 모두 404"가 인수 조건이라 순서를 바꿨다. `before`·`limit`을 컨트롤러에서 문자열로 받는 이유도 같다.
- **자동 종료도 채널 version을 올린다.** 계약이 "참여자 변경이 같은 version을 쓴다"고 정했고, 참여자가 바뀌었는데 version이 같으면 관리자가 옛 목록을 덮어쓸 수 있다.
- **`clientMessageKey`의 동등 판단은 DB에 맡겼다.** 조회가 같은 열 정렬 규칙을 쓰므로 `uk_messages_1`과 항상 일치한다. 열이 `utf8mb4_0900_ai_ci`라 대소문자만 다른 키는 같은 키가 된다. UUID를 쓰는 클라이언트에는 영향이 없고, 다른 본문이면 409라 메시지가 조용히 합쳐지지 않는다.
- **동시 재전송**: 가드 아래에서는 재요청이 저장된 행을 찾는다. 그래도 유일 제약에 걸리면 롤백 뒤 한 번 더 시도해 저장된 행으로 같은 규칙을 적용한다. 가드를 나누어도 안전하도록 남겼다.
- **본문은 변환하지 않는다.** strip도 하지 않으며 비었는지만 판단한다. 짝 없는 서러게이트는 JDBC가 `?`로 바꿔 "그대로 저장"을 깰 수 있고, 같은 입력의 재전송이 충돌하게 되므로 422로 거부한다. 길이는 UTF-16 단위가 아니라 문자 수로 센다.
- **업무 카드 행**은 `kind=업무 카드`, `task=null`로 읽는다. `related_task_id`는 내보내지 않고, `unreadCount`에 포함하며 답글을 달 수 있다. 같은 키의 텍스트는 카드와 다른 입력이므로 409다.

## 4. 구현 내용

- **마이그레이션 `V3__channel_description_and_version.sql`**: `conversations`에 `description varchar(500) NULL`, `version bigint unsigned NOT NULL DEFAULT 0`을 추가했다. 버전 번호는 병합 직전 규칙을 따른다. `docs/db/erd.mmd`를 함께 갱신했다. `schema-full.sql`은 통합 V1 시점의 추출본이라 V2 때처럼 바꾸지 않았고, `database.md`에는 이 표의 설명이 없어 바꾸지 않았다.
- **`modules/chat`**
  - `ChannelController`: operation 13개. `POST /channels/{id}/task-cards`는 #77 범위라 없다.
  - `ChannelAccess`: 참여·자격·관리 판단.
  - `ChannelService`: 채널 목록·관리 목록·후보·상세·생성·수정·참여자 교체. 생성은 `Idempotency-Key`, 수정은 `version`.
  - `MessageService`: 원문·답글 목록, 단건, 전송, 읽음.
  - `ChannelParticipationEnding`: `EmployeeAccessReduced` 수신. DM 참여는 건드리지 않는다.
- **다른 모듈**
  - `AuthorizedCommands.activeEmployee` 추가.
  - `EmployeeManagementService`가 소속 회수와 계정 비활성·이용 제한에서 이벤트를 발행한다.
  - `EmployeeAccountService.channelCandidates`·`channelEligible`이 자격 SQL을 제공한다.
- **문서·샘플**: 13개 operation을 `implemented`로 바꾸고 `collaboration-api.md`의 구현 상태를 갱신했다. `LocalPreviewController`의 목록 경로에서 `channels`를 뺐다. `/api/local-preview/lookups`의 샘플 키는 샘플 화면 전용이라 두었다. `/chat/*`는 서버에 없다. 변경 알림은 추가하지 않았다(`WorkspaceEvent`에 `channels`·`messages` 없음, 채팅 실시간은 M14).

## 5. 검증 결과

- 전체 시험 `./gradlew test`: **58개 suite, 612개 시험, 통과 612, 실패 0, 건너뜀 0**(`build/test-results/test/*.xml` 집계, BUILD SUCCESSFUL, 22분 31초). Testcontainers MySQL에서 실행했다.
- 이번에 추가한 시험은 `ChannelIntegrationTests` 29개, `MessageIntegrationTests` 25개, `MessageDuplicateKeyTests` 2개이고, `FoundationMigrationTests`에 V3 적용 시험을 더했다. 최신 버전 기대값은 3으로 갱신했다.
- **마이그레이션**: V2까지 적용한 DB에 V3를 적용해 기존 채널의 `description`이 NULL, `version`이 0인지와 열 형식·500자 제한을 확인했다. Hibernate `validate`로 엔티티 매핑도 확인됐다.
- **실제 동시 실행**(HTTP 요청 경쟁, MySQL)
  - 같은 키 동시 6건: 201 한 건·200 다섯 건, 행 1개.
  - 4명이 5건씩 동시 전송: 20건 모두 201, 페이지를 끝까지 넘겨도 중복·누락 없음, ID 순서와 `sent_at` 순서 일치.
  - 전송과 참여자 제거 경합 6회, 전송과 소속 회수 경합 4회: 201이면 행이 있고 404면 행이 없다. 어느 쪽이 이겼는지는 회차마다 달라 두 결과가 모두 나왔다고 보장하지는 못한다.
  - 동시 읽음 6건: 최종 위치는 가장 뒤 메시지이고, 어떤 요청도 자기 값보다 앞선 위치를 답받지 않았다.
  - 같은 version의 참여자 변경: 200 한 건·409 한 건, version 1회 증가, 감사 1행.
  - 같은 `Idempotency-Key`의 채널 동시 생성 4건: 채널 1개.
- **유일 제약 경로**: 가드가 동시 전송을 직렬화하므로 실제 경합으로는 `uk_messages_1`에 닿지 않는다. 조회를 한 번 비우는 시험(`MessageDuplicateKeyTests`)으로 이 경로를 강제해 저장된 행 응답과 409를 확인했다. 실제 동시 실행으로 이 경로를 지난 것은 아니다.
- **미검증**: 처리량·지연 측정, 실제 공유 DB의 V3 적용, Frontend 연동. OWNER는 스키마상 한 명이고 마지막 관리자라 OWNER 계정 비활성은 409로 실패하므로, OWNER의 참여 종료는 실패 시 롤백만 확인했다.

## 6. 남은 작업 / 보류 사항

- **처리량 미측정**: 전송과 읽음이 공통 가드로 직렬화된다. 전송이 늘어나는 M14에서 측정하고 잠금 분리를 결정해야 한다. 나누면 ID와 커밋 순서가 어긋나는 문제를 함께 풀어야 한다.
- **참여자 변경 후 version**: `PUT members` 응답에는 새 `version`이 없다(계약의 `ChannelMemberList`). 클라이언트는 채널 상세를 다시 읽어야 다음 수정을 보낼 수 있다.
- **DM 참여의 자동 종료**: M14가 DM을 정의할 때 정한다. 지금은 건드리지 않는다.
- **새 참여자의 읽음 위치**: 계약대로 위치가 없으면 채널의 기존 메시지가 모두 읽지 않음이다. 화면에서 과하다면 계약을 조정해야 한다.
- **Frontend 연동(#26~#28)과 실제 공유 DB의 V3 적용**은 이 작업에서 확인하지 않았다.
- 병합 직전에 main의 최대 마이그레이션 번호를 확인해 V3가 겹치면 번호를 올려야 한다.
