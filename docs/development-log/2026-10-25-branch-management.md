# B05 지점 운영 API

## 배경 / 문제

지점 API는 local preview의 조회용 샘플에 머물러 실제 등록·변경·운영시간 저장을 제공하지 않았다. 이슈 #11과 foundation OpenAPI에 맞춰 운영 DB를 사용하는 지점 관리가 필요했다.

## 검토한 선택지

기존 B03의 공개 인가 서비스와 쓰기 가드를 재사용하는 방법을 검토했다. 별도 잠금이나 모듈 간 repository 직접 접근을 추가하면 현재 권한 검증과 변경 사이에 경합 또는 모듈 순환이 생기므로 기존 가드를 사용했다. 감사/outbox를 B06과 공통 서비스로 추출하는 방안도 논의했으나 병렬 PR의 선행 의존성을 늘리지 않도록 각 업무 repository에서 동일 DB 계약을 사용하기로 했다.

## 결정 및 이유

branch 모듈이 authorization의 공개 service/DTO만 호출한다. 기존 auth → branch 방향에 반대되는 auth 의존성을 만들지 않는다. 모든 쓰기는 AuthorizedCommands의 guard → 직원 → 지점 잠금 안에서 현재 권한을 확인한 뒤 진행한다. OWNER만 등록하고, 관리자 역할과 operations:write를 함께 가진 지점 관리자는 자기 지점의 운영정보·상태를 변경한다. 운영 중지 상태에서도 기존 정보 조회와 운영 설정 복구는 허용하며 신규 거래 제한은 B03 BranchAction 공개 계약을 유지한다.

## 구현 내용

- `/api/branches` 목록·등록, `/{id}` 상세·PATCH, `/{id}/status` POST를 정본 계약에 맞춰 구현했다.
- 허용 지점 안에서만 검색·상태 필터·안정 정렬·total을 계산한다. 상세·변경의 명시적 선택 scope와 실제 대상도 일치시킨다.
- 7요일을 중복 없이 검사하고 휴무 null, 24시간, 익일 종료를 분 단위로 저장한다. 기존 일정이 없는 지점은 미설정 요일을 휴무로 표시하며 임의 영업을 추정하지 않는다.
- PATCH의 누락 필드는 유지하고 명시 null·허용하지 않은 필드는 거부한다. version 충돌은 현재 버전과 reloadUrl을 반환한다.
- 등록 요청의 정규화 입력 SHA-256과 응답을 영속 멱등 테이블에 저장한다. 현재 OWNER 권한 재검사 후 동일 키·동일 입력은 원래 응답을 반환하고 다른 입력은 409를 반환한다. 24시간 보존 만료 시각을 기록하며 만료 레코드 정리 worker는 이번 범위에서 추가하지 않았다.
- 지점·시간표·감사 snapshot/requestId·workspace outbox·멱등 결과는 같은 트랜잭션으로 저장한다. 삭제 API나 스키마 변경은 추가하지 않았다.

## 검증 결과

Java 21과 기존 고정 MySQL 8.4.11 Testcontainers 이미지에서 `test --tests '*BranchIntegrationTests' --tests '*ModuleBoundaryTests' bootJar`를 통과했다. 통합 테스트 4개와 모듈 경계 테스트 1개, 실패·오류·건너뜀 0개다. 최종 선택 scope·명시 null·권한 회수 검증을 추가한 뒤 재실행했다.

실제 HTTP 로그인·CSRF·3역할 거부, 지점 밖 상세/변경 거부, 빈 검색·빈 허용 지점 목록, 현재 version 409, 운영 중지 후 조회, 24시간·익일·잘못된 요일, 동일 키 동시 등록 1건, 다른 입력409, 감사 requestId와 전체 rollback을 확인했다. 기존 B03 테스트는 후속 거래의 중지 지점 제한 계약을 검증한다. 이 작업 단독 실행에서는 전체 suite와 브라우저·프론트 live 연동을 실행하지 않았다.

## 남은 작업 / 보류 사항

B04의 main 누락 복구, B06과의 전체 결합 테스트 및 F02 live 브라우저 검증은 부모 작업에서 수행한다. outbox dispatch/SSE와 운영 프록시 검증은 B11/V01 후속 범위다. 원격 main 변경·PR 병합은 사용자가 수행한다.
