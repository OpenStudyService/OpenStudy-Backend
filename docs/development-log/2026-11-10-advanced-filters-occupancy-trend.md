# 2026-11-10 결제·집계 고급 필터, 이용 지점 사용량, 좌석 점유 추이 (#116)

## 1. 배경 / 문제

- M13 계약(#111)의 마지막 구현 이슈다(FR-PAY-13, FR-AGG-15, FR-SEAT-16, ADR-M13-001 M13-D09·D10·D12).
  - 결제 목록과 M9 집계에 같은 고급 필터(결제 수단, 상품 유형, 분류, 처리자, 환불 처리 지점)를 적용한다.
  - 이용 지점별 이용권 사용량을 매출과 따로 보여 준다.
  - 시간·일 구간별 좌석 점유 추이를 원천 기록으로 다시 계산할 수 있게 한다.
- 이슈 본문은 계약 결정(M13-D12) 전의 문구("이용 지점 필터")였다. 작업 전에 인수 조건 2와 제외 범위를 고치고 이전 문구를 본문에 남겼다(이슈 댓글로 기록).

## 2. 검토한 선택지

- **고급 필터의 위치**: M9 질의는 승인·환불 `WHERE` 조각(`approvals`, `refunds`)을 합계·일별·이용권·원장이 모두 공유한다. 이 두 조각에 조건을 더하면 모든 집계와 원장에 같은 조건이 걸리고, M9의 정합성 규칙(원장 합 = 합계)이 그대로 유지된다. 연산마다 따로 넣는 방법은 검토하다 버렸다.
- **조건 객체 확장**: `AggregationCondition`에 고급 필터 묶음(`AdvancedFilter`)을 아홉째 요소로 더했다. 기존 8개 인자 생성자는 남겨 M9·M10·마감 코드와 기존 테스트가 그대로 동작한다.
- **결제 목록의 의미**: 목록의 행은 결제 하나다. 처리자는 결제 처리자(`created_by`)로 고르고, 환불 처리 지점은 `환불` 상태 행만 그 환불의 처리 지점으로 좁힌다. 집계의 "승인은 결제 처리자, 환불은 환불 처리자"와 맞추려면 한 행을 두 번 셀 수밖에 없어, 행 단위의 자연스러운 의미를 택하고 계약에 적었다.
- **모듈 의존**: 결제 모듈은 매출 모듈을 가져오지 않고 자체 입력 처리(라벨 → 저장 값)를 둔다. 사용량은 좌석·이용권 테이블을 네이티브 질의로 읽어, 매출 모듈이 좌석·이용권 모듈에 의존하지 않는다.

## 3. 결정 및 이유

- **매출 연산의 분류·상품 유형**: M9에서는 매출 연산에 분류 조건을 받지 않았다(422). M13-D10에 따라 이제 받는다. 이용권 결제만 남고 `condition.purpose`가 `이용권`이 되며 `PASS_ONLY` 안내가 붙는다. 이용권 외 용도와 함께 보내면 422다.
- **환불 처리 지점**: 요청자가 볼 수 있는 지점이어야 하고, 아니면 403이다. 환불 항목에만 적용한다.
- **안내 문구(`conditionNotes`)**: 처리 지점, 처리자, 결제 수단, 이용권만 집계라는 네 경우와 사용량의 `USAGE_NOT_REVENUE`를 계약 문구대로 담는다.
- **사용량**
  - 입실 수는 좌석 이용의 실제 입실 시각으로 센다.
  - 차감은 좌석 이용에 연결된 `USE`와 이용 정정에 연결된 행을 원장 시각으로 센다. 이용 지점은 연결된 좌석 이용의 지점이다.
  - `sales:read`가 없는 판매 지점은 "다른 지점" 한 줄로 합친다. 보이는 판매 지점의 `label`은 null로 정했다.
  - 응답의 `refundBasis`는 null이다.
- **점유 추이**
  - 머무름은 `[실제 입실, 실제 퇴실 또는 asOf)`이다. 구간마다 초 단위로 더한 뒤 분으로 내린다.
  - 좌석 수는 구간 끝 전에 등록된 좌석이다.
  - 시간 단위 라벨은 `YYYY-MM-DD HH:00`(Asia/Seoul)으로 정했다.
  - `asOf` 뒤만 있는 구간은 분모가 0이라 "해당 없음"이다.

## 4. 구현 내용

- **매출 모듈**
  - `AdvancedFilter`, `ConditionNote`
  - `AggregationCondition`·`AggregationScope`·`SourceFilter` 확장, `AggregationConditions`의 검증과 처리 지점 권한
  - `SalesSourceRepository.advanced`(공유 `WHERE` 조각)
  - `AggregationMetas`의 적용 필터·안내, `SalesController`의 반복 query 파싱
  - `PassUsageService`와 `GET /api/sales/passes/usage`
- **결제 모듈**: `PaymentSearchRepository`의 고급 필터와 상태별 합계, `PaymentPage`(`filter`, `summary`), 컨트롤러 입력 처리
- **좌석 모듈**: `SeatOccupancyTrendService`와 `GET /api/seats/occupancy-trend`
- **계약**
  - OpenAPI: 남은 `x-planned-changes`(#116)를 모두 본 정의로 옮겼다. 결제 목록·집계 7개 operation의 고급 필터 parameter, `AggregationCondition`·`AggregationMeta`·`PaymentPage`의 필드다.
  - 이제 OpenAPI에 `x-planned-changes`가 없다. M13 operation 12개가 모두 `implemented`다.
  - 문서: M13 계약(구현 표시와 정한 것)
- **테스트**: M13 계약 테스트를 "모두 구현됨, 남은 계획 없음"으로 바꿨다.

## 5. 검증 결과

- `AdvancedFilterIntegrationTests` 3개 통과(HTTP·MySQL). 인수 조건별로 다음을 확인했다.
  1. **목록 = 집계**
     - 결제 수단, 처리자, 상품 유형, 수단+유형 네 조건마다 결제 목록 `summary`의 (승인 + 환불) 금액·건수가 같은 조건의 `/sales/revenue` 승인액·건수와 같다.
     - 원장 합·건수가 합계·`sourceRowCount`와 같다.
     - 적용 필터와 안내가 응답에 담긴다. 중복·잘못된 값은 422다.
  2. **이용 지점 사용량**
     - 첫 지점에서 판 시간권을 둘째 지점에서 90분 쓴 기록이 둘째 지점 사용량(입실 1, 90분, 판매 지점 = 첫 지점)으로 나온다.
     - 둘째 지점의 매출은 0이다.
     - `refundBasis`는 null이고 `USAGE_NOT_REVENUE` 안내가 붙는다.
     - 판매 지점을 볼 수 없는 사용자에게는 "다른 지점"으로 합쳐 나온다.
  3. **환불 유형**: 다른 처리 지점 조건이면 환불액 0, 승인액은 그대로다. 처리 지점·원결제일 기준을 함께 쓸 수 있다. 목록은 환불 행만 좁혀진다.
  4. **점유 재계산**: 시간 구간 3개의 점유 분이 `seat_sessions`로 직접 계산한 값과 같다. 10시 구간은 90분/120분 = 75.0%, 일 단위는 120분이다.
  5. **좌석 없는 지점**: 점유율이 `notApplicable`이고 percent는 null이다.
  6. **권한**: 볼 수 없는 지점의 사용량·점유 추이는 403이다. 시간 단위 31일 초과는 422 `PERIOD_TOO_LONG`, 잘못된 단위는 422다.
  - 응답 필드가 계약 schema와 같다.
- 전체 `./gradlew test` 1차(17분 43초): 1,101개 중 5개가 실패했다. 모두 이번 계약 변경을 아직 반영하지 않은 기존 테스트이거나 구조 규칙 위반이었다.
  - M9 메타 필드 고정 테스트에 `conditionNotes`가 없었다 → 계약대로 추가했다.
  - 매출·추세에서 분류 조건만 보내면 422를 기대하던 두 테스트 → M13-D10으로 허용되므로, 여전히 422인 "분류 + 이용권 외 용도" 조합으로 바꿨다.
  - 원장 응답 전체에 `method` 글자가 없어야 한다는 테스트 → 원장 항목·합계·페이지 정보만 검사하게 좁혔다. 적용 조건의 `methods` 필드가 걸렸다.
  - 네이티브 SQL은 저장소에만 둔다는 구조 규칙 → 사용량·점유 추이 질의를 `PassUsageRepository`, `SeatOccupancyRepository`로 옮겼다.
- 전체 `./gradlew test` 2차(15분 39초): 1,101개 중 1개 실패. M9 계약 테스트가 메타 필수 필드 수(10)와 적용 조건 필드 목록도 고정하고 있었다. 11개와 고급 필터 네 필드로 고쳤다.
- 고친 뒤 아키텍처 테스트 97개를 다시 실행해 실패 0이다. 전체 테스트는 3차로 다시 돌리지 않았다. 2차에서 나머지 1,100개는 통과했고, 고친 것은 이 계약 테스트 한 파일이다.

### 검증하지 못한 항목

- 사용량 테스트는 좌석 이용·차감 원장을 DB에 직접 넣었다. 실제 입실·퇴실 API가 만든 원장으로 계산하는 경로는 따로 실행하지 않았다. 질의는 같은 테이블을 읽는다.
- 실제 운영 환경과 Frontend 연동(Frontend #42)은 확인하지 않았다.
