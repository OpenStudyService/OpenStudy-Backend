# 검토 완료 SRS 범위의 1차 DB·API 설계

작성일: 2026-10-23. 작업 브랜치: `docs/foundation-db-api`. 설계 결과와 구현 결과를 구분한다.

## 1. 배경 / 문제

사용자가 SRS의 관리자 중분류(지점 관리, 직원·권한 관리, 이용권 상품 관리, 직원 초대·승인)와 공통 중분류(인증·세션, 지점 선택, 초대 수락·대기, 공통 업무 규칙)의 검토를 완료했다. 전체 SRS와 WBS 확정 전에 이 8개 분류로 DB·API를 설계해 개발 이슈로 연결하도록 요청했다.

현재 V1에는 기본 테이블이 있지만 초대 이름·반려 사유, 상품 판매 지점·분류·변경 이력 등이 없다. 기존 전체 API 문서는 구 요구사항 ID·범용 폼 계약을 사용하며 현재 로그인 구현과도 차이가 있다. 검토된 범위를 추적 가능한 계약으로 분리할 필요가 있었다.

## 2. 검토한 선택지

- 기존 V1을 기준으로 부족한 부분을 확장하는 방식과 기존 정의를 다시 쓰는 방식을 비교했다. 이미 기동한 DB의 checksum·식별자·구매 참조를 유지하려면 후속 migration이 적합하다.
- 기존 상품 amount/days 범용 필드를 유지하는 방식과 유형별 분·일·원화·nullable 유효기간을 명시하는 방식을 비교했다. 후자는 프론트 수정이 필요하지만 다른 유형 필드 혼용과 무기한/0일 혼동을 명확히 차단할 수 있다.
- 승인 대기 세션, 기존 직원의 추가 초대, 기간권 날짜 결정 시점, 다지점 직원 전역 수정에는 SRS 해석의 여지가 있었다. 무조건 확정하지 않고 세 가지 질문으로 묶어 권장안과 대안을 정리했다.

## 3. 결정 및 이유

- 검토 완료 61개만 1차 설계 대상으로 고정하고 기존 SRS·확정 결정·V1·프론트 계약을 대조했다. 미검토 결제·발급·예약의 업무 규칙을 이번 설계로 확정하지 않는다.
- 기존 JDBC 세션, 60분/12시간, 이메일 불변, 지점별 권한 저장·프리셋 복사, 토큰 해시만 보관·자동 재시도 TTL 유지 등 사용자 결정은 유지했다.
- API의 ID 문자열·DB+1 version·한국어 상태/role 표기는 유지하고 상품 조건, 초대 토큰 전달, 지점별 소속 수정 계약의 변경점을 명시했다.
- 운영 코드를 수정하는 대신 DB 데이터 사전·확장 순서와 OpenAPI를 작성했다. 3개 정책 가정은 사용자 응답 전까지 확인 필요로 유지했다.
- 공통 문서 정본의 별도 저장소 운영 결정을 변경하지 않았다. 현재 작업 가능한 백엔드 저장소에서 구현 연결 설계를 관리하고 정본 저장소 동기화는 후속으로 남겼다.

## 4. 구현 내용

`docs/design/foundation/`에 다음을 추가했다.

- 범위·자료 위치·현재 구현과 목표의 차이를 설명하는 README.
- ERD, 1차 관련 테이블/컬럼/제약/인덱스, 기존 데이터 backfill, 트랜잭션·잠금 순서와 후속 migration 계획.
- 31개 경로·39개 operation·57개 schema의 OpenAPI 3.0.3, 보안·지점 범위·버전·멱등·SSE·호환성 설명.
- 원본 workbook SHA-256과 셀 행을 포함하는 61개 요구사항 사본 및 요구사항별 DB/API/인수 기준 추적표.
- 마일스톤 3개와 backend11개·frontend4개·통합검증1개, 총16개 이슈 초안. GitHub 이슈·마일스톤을 실제 생성하지 않았다.

`scripts/validate_foundation_design.py`는 로컬 참조·추적 누락·operation 중복·CSRF 선언·등록 멱등성 선언·응답 비밀 필드·문서 링크·SRS 원본 해시를 검사한다. OpenAPI 표준 검사나 서버 테스트를 대체하지 않는다. 백엔드 README에 설계 진입점을 연결했다.

## 5. 검증 결과

- `@apidevtools/swagger-cli@4.0.4 validate docs/design/foundation/openapi.json`: OpenAPI 문서 유효성 검사 통과.
- `scripts/validate_foundation_design.py`: 요구사항61·중분류8·operation39·schema57·내부 참조531·이슈16 연결 검사 통과.
- 기존 V1·애플리케이션 코드·설정 변경 없음. 설계 작업이므로 서버 빌드·DB DDL 적용·Testcontainers·브라우저 업무 테스트는 실행하지 않았다.
- 이번 검증은 명세 구조·프로젝트 추적의 정합성 검사다. 승인·상품·권한 경합 등 제안 동작의 실행 성공을 의미하지 않는다.

## 6. 남은 작업 / 보류 사항

- Q1 승인 확인용 제한 세션과 기존 직원 추가 지점 대기, Q2 기간권 날짜 결정 시점, Q3 직원 공통 수정 권한에 사용자 답변 반영. 해당 설계 가정에 의존하는 구현 이슈는 정책 확정 뒤 착수한다.
- 기존 데이터에 알 수 없는 판매 지점·초대 이름 등의 명시 매핑을 준비하고 실제 새 migration을 작성·검증한다.
- API·프론트 타입·화면의 변경점을 같은 계약 버전으로 동기화한다. 기존 실제 로그인 구현을 보완하고 운영 초기화 명령을 구현한다.
- 본문 이슈 초안을 검토해 실제 저장소 마일스톤·이슈로 등록한다. 현재는 미등록이다.
- 단일 인스턴스 SSE 이후 다중 ECS fan-out, 운영 SMTP·HTTPS 프록시·cookie/SSE 환경 검수는 별도 구현·검증 대상이다.
