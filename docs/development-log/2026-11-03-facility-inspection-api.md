# 2026-11-03 시설 점검 항목·점검 완료·다음 점검일 API

관련: Issue [#78](https://github.com/OpenStudyService/OpenStudy-Backend/issues/78), [계약 문서](../design/foundation/collaboration-api.md), [ADR-M7-001](../db/ADR-M7-001.md) M7-D03·D05·D06, [업무 API 기록](2026-11-01-task-management-api.md).

## 1. 배경 / 문제

시설 화면은 로컬 샘플로만 동작하고 저장은 501로 끝났다. `modules/facility`가 비어 있었기 때문이다. #74 계약이 병합되고 업무(#75)가 구현되어, 시설 유형 2개와 시설 6개 operation을 구현할 수 있게 됐다.

계약의 어려운 부분은 다음 네 가지다.

- 시설 상태(정상·점검 필요·고장·사용 중지)와 처리 상태(대기·진행 중)가 서로 다른 값이며, 후자와 담당자는 시설이 아니라 열린 점검 작업에 있다.
- 시설마다 열린 점검 작업이 항상 하나여야 하는데, DB에 이를 막는 유일 제약이 없다.
- 다음 점검일은 저장하지 않고 조회할 때 계산하며, 목록의 필터·정렬·페이지와 수치가 같은 기준이어야 한다.
- 점검 완료는 작업 닫기, 시설 갱신, 다음 작업 열기, 감사가 한 번에 일어나야 한다.

## 2. 검토한 선택지

- **열린 작업 하나를 보장하는 방법**
  - DB 유일 제약: 마이그레이션이 필요하고 이번 범위의 전제(스키마 변경 없음, ADR-M7-001)와 맞지 않는다.
  - 시설 행을 잠그고 서비스가 보장한다: 계약이 정한 방식이다. 이쪽을 택했다. 모든 명령이 먼저 공통 guard 잠금을 잡고, 이어서 시설 행을 잠근 뒤 열린 작업을 읽는다.
- **다음 점검일의 SQL 계산**
  - 등록일을 계산하는 `CONVERT_TZ(created_at, '+00:00', 'Asia/Seoul')`: 서버에 시간대 표가 없으면 NULL이 나온다. 쓰지 않았다.
  - 요청 시각의 Asia/Seoul UTC 오프셋(`+09:00`)을 바인딩해 `CONVERT_TZ`에 넘긴다: 시간대 표가 필요 없고 서버 시간대에 의존하지 않는다. 이쪽을 택했다.
  - 같은 식을 Java(`FacilityService.nextInspectionOn`)에서도 계산해 응답에 쓰므로, 목록 필터·정렬과 표시값이 같은 규칙에서 나오는지 테스트로 확인했다.
- **목록 조인 방식**: 시설과 열린 작업을 한 쿼리에서 걸러야 담당자·처리 상태 필터가 페이지 수와 맞는다. `facility_works`를 `MAX(id)`로 고른 한 행에 LEFT JOIN 했다. 서비스가 열린 작업을 읽을 때도 같은 규칙(가장 최근 id)을 쓴다.
- **시설 변경 이력**: 시설에는 이력 표가 없어 계약대로 `audit_events`에 전후 값을 남겼다. 점검 결과는 `facility_works`에, 변경은 감사에 남는 구조다.
- **version 증가**: 담당자·처리 상태만 바뀌면 시설 행이 dirty가 아니라 `@Version`이 오르지 않는다. 업무 체크 항목과 같은 JPQL 증가(`incrementVersion`)를 썼다. 점검 완료에서 상태와 날짜가 그대로여도 작업이 닫히므로 같은 방식으로 올린다.
- **샘플 경로**: `LocalPreviewController`에서 `facilities`를 빼고, 샘플 테스트가 쓰던 자원을 스터디룸(`rooms`)으로 바꿨다. M5·M7 구현 대상이 아니고, 지점마다 1건이라 기존 기대값(지점별 1건, 상세와 범위 밖 404)이 그대로 맞는다.

## 3. 결정 및 이유

- **권한**: 등록·수정은 `facilities:write`, 점검 완료는 그 작업의 담당자 또는 `facilities:write`이며 둘 다 지점의 유효 소속이어야 한다. MANAGER 역할만으로는 쓰기가 되지 않는다(계약: 행위 권한은 명시한 곳에서만).
- **시설 유형**: 지점 구분이 없는 전역 코드표다. OWNER만 등록하고(공통 guard 아래 직렬화), 이름 중복은 컬럼 collation 그대로 확인해 대소문자 차이도 중복으로 본다.
- **명령 순서**: 입력 검증 → 범위(404) → 잠금 → 권한(403) → (완료는 멱등 재생) → version(409) → 날짜 규칙(422). 권한 없는 사용자에게 version 충돌 정보가 나가지 않게 하기 위해서다. 멱등 재생은 version 확인 앞에 둬서, 성공한 완료를 같은 키로 다시 보내면 409가 아니라 저장된 응답이 온다.
- **다음 점검일**: 마지막 점검일이 없으면 등록일(Asia/Seoul)이고, 있으면 마지막 점검일 + 주기다. 점검 이력이 없는 시설은 주기를 더하지 않는다(M7-D06). `inspectionDue`는 다음 점검일 ≤ 오늘(Asia/Seoul)이고 사용 중지가 아닌 시설이다.
- **수치**: 목록과 수치가 `FacilitySearchRepository`의 같은 WHERE·같은 due 식을 쓴다. 지점별 수치는 scope의 모든 지점을 0 포함해 돌려준다.
- **같은 값의 수정**: 변경이 없으면 version·감사·알림을 만들지 않고 현재 값을 돌려준다.
- **열린 작업이 없는 시설**: 명령으로는 생기지 않는다. 손으로 고친 데이터에서 만나면 쓰기 명령이 작업을 하나 열고 진행한다.

## 4. 구현 내용

- `modules/facility`: entity 6개(시설·작업·유형·enum 3), repository 5개(`FacilitySearchRepository` 포함), `FacilityService`, `FacilityTypeService`, `FacilityInputs`, `FacilityFilters`, `FacilityController`, 응답 DTO
- 등록은 시설과 첫 `OPEN` 점검 작업을 한 트랜잭션에서 만든다. 마지막 점검일과 결과를 함께 주면 완료된 작업(`DONE`)도 같이 저장한다.
- 점검 완료는 한 트랜잭션에서 작업을 `DONE`으로 닫고(결과·완료자·완료 시각) 시설의 상태·마지막 점검일을 갱신한 뒤, 같은 담당자의 새 `OPEN` 작업을 만들고 감사(`INSPECTION_COMPLETED`)를 남긴다.
- 수정(`PATCH`)은 시설 정보·담당자·처리 상태를 함께 받는다. 감사(`UPDATED`)에는 바뀐 항목의 전후 값만 남는다.
- `WorkspaceEventService`: `facilities` 알림 매핑. 시설 유형 등록 알림은 시설 id가 아니므로 `entityId` 없이 `facilities`를 다시 읽으라는 신호만 보낸다.
- `LocalPreviewController`와 `LocalPreviewIntegrationTests`: 샘플 경로에서 facilities 제거, 테스트의 샘플 자원을 `rooms`로 변경
- 계약 문서: 시설 operation 8개를 `implemented`로 변경하고 구현 상태 문장을 갱신. 계약 내용은 바꾸지 않았다.

마이그레이션은 없다.

## 5. 검증 결과

- `./gradlew test` 전체: 53개 suite, 506개 테스트 통과(실패·오류·건너뜀 0). Testcontainers MySQL 사용. 전체 테스트 로그에 메일 발송 관련 내용은 없다.
- 신규 `FacilityIntegrationTests` 30개를 HTTP와 MySQL로 확인했다.
  - 권한: 시설 유형 등록은 OWNER만, 시설 등록·수정은 `facilities:write`(MANAGER 역할만으로는 거부, 다른 지점 보유자는 거부·404), 완료는 담당자·`facilities:write`·OWNER만, 일반 직원 403, 범위 밖 404, 소속 회수 후 404
  - 등록: 시설과 첫 작업이 함께 생성, 유형 기본 주기, 선택 입력(마지막 점검일·결과)의 완료 작업 저장, 잘못된 담당자·유형·입력 거부 시 행이 남지 않음
  - 점검 완료: 결과 누락·공백·길이 초과 거부, 오늘 이후·마지막 점검일 이전 날짜 거부, 작업 닫힘·시설 갱신·같은 담당자의 새 작업·감사, 상태와 날짜가 그대로여도 version 증가
  - 다음 점검일: 마지막 점검일 없음(등록일), Asia/Seoul 날짜 경계(UTC 14:59:59와 15:00:00), 주기 수정·완료 후 재계산
  - `inspectionDue`: 오늘 도래·내일 도래·사용 중지 제외·고장 포함·등록일 경계, 목록 필터·페이지·정렬이 같은 기준임
  - 수치: 상태별·`inspectionDue`·지점별 수치가 같은 필터의 목록 total과 일치(필터 11종)
  - 버전 충돌(최신 version·reloadUrl), 멱등 재요청(재생·다른 입력 409), 수정 감사의 작업자와 바뀐 항목의 전후 값
  - 실제 동시 실행: 같은 시설을 6명이 동시에 완료(3라운드, 매번 1건만 성공·열린 작업 1개 유지), 새 version으로 4명이 반복 완료(성공 수와 `DONE` 작업 수·version 일치), 같은 멱등 키 5건 동시 완료(1회 적용), 완료와 수정의 경합 4라운드(성공 1·충돌 1, 열린 작업 1개), 같은 version의 동시 수정 3건(1건 적용), 같은 키의 동시 등록 5건(시설 1개)
- 샘플 테스트(`LocalPreviewIntegrationTests`)는 `rooms`로 바꾼 뒤에도 통과한다.

**실행하지 않은 것**

- `GET /workspace/events`로 시설 알림이 실제로 전달되는지의 SSE 확인. 알림 행(outbox)이 같은 트랜잭션에 쌓이는 것까지만 확인했고, 스트림 매핑은 업무와 같은 구조의 코드만 추가했다.
- 실제 서버 실행과 Frontend 연결.
- 동시 요청은 공통 guard 잠금 아래 직렬화되므로, 시설 행 잠금만 단독으로 경합시키는 테스트는 만들지 않았다.
- 인프라 서버 검증.

## 6. 남은 작업 / 보류 사항

- Frontend #26~#28: 시설 화면을 이 API에 연결한다. 현재 화면은 샘플 모양(`title`, `cycleDays` 등)이다.
- 계약이 정하지 않아 정한 동작은 PR 본문과 이슈에 적는다: 목록 `q`는 시설명·위치만 찾는다, 기본 정렬 방향은 `nextInspectionOn`·`name`이 오름차순이고 `createdAt`이 내림차순이다, 시설 유형을 지우거나 고치는 API는 없다, `lastInspection.completedOn`은 시설의 마지막 점검일을 쓴다.
- 홈(M9)의 시설 수치는 아직 샘플이다. 이 API의 summary를 재사용한다.
- 소속 행이 없는 OWNER는 담당자가 될 수 없다(업무와 같음).
