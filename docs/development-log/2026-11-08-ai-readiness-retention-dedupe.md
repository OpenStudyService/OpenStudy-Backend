# 2026-11-08 AI 준비 상태·질문 원문 30일 삭제·중복 제출 방지 (M10 #93·#96)

## 1. 배경 / 문제

- M10 #93~#96 대조(ADR-M10-003)에서 남은 세 가지를 구현했다.
  - **#93 준비 상태**: `GET /ai/catalog/readiness`가 항상 `ready: true`를 돌려줬다. 준비 안 됨일 때 질문을 거부하는 장치도 없었다.
  - **#96·M10-D04 질문 원문 30일 삭제**: 진단 로그 테이블에 `question_expires_at`는 있지만 지우는 작업이 없었다. 주석만 있었다.
  - **#96 중복 제출 방지**: 질문 요청에 클라이언트 요청 키가 없었다.
- 이 작업은 PR #184(등록 분석 확정) 위에서 진행했다.

## 2. 검토한 선택지

- **"지표가 M9 지표 정의와 연결"(#93)의 판정 기준**
  - OpenAPI의 `x-metric-definitions`와 대조: 문서 파일이라 실행 중에는 읽지 않는다.
  - 카탈로그 지표가 등록 분석과 연결되는지 확인(선택): ADR-M10-003에서 등록 분석이 M9 집계 서비스로 계산한다고 정했으므로, 지표→등록 분석 연결이 곧 M9 연결이다.
- **임베딩 모델이 없을 때**
  - 준비 안 됨으로 처리: 모델 파일이 없는 개발·테스트 환경에서 AI 전체가 막힌다.
  - 경고로 처리(선택): 의미 검색 후보만 빠지고 질문 판정은 동작한다.
- **같은 키 재제출의 응답**
  - 409 오류: 화면이 다시 결과를 얻으려면 별도 조회가 필요하다.
  - 저장된 질문을 다시 실행해 돌려주기(선택): 대화 다시 열기와 같은 방식이다. 모델을 부르지 않고 현재 권한을 다시 확인한다.
- **동시 제출 경합**
  - 직원별 잠금
  - 유일 키 + 경합에서 진 요청은 저장된 질문을 받기(선택): DB가 보장하고 코드가 작다.

## 3. 결정 및 이유

- 준비 상태는 카탈로그 전체가 일관될 때만 `ready`다. 하나라도 어긋나면 이유를 모두 돌려주고 전체를 준비 안 됨으로 둔다(#93 "일부만 활성화하지 않는다").
  - 모든 지표가 등록 분석과 연결
  - 모든 등록 분석에 지표가 있음
  - 지표 원천이 카탈로그에 있음
  - 금지 원천(고객·세션·초대·문의·팀 채팅 테이블)이 없음
- 준비 안 됨이면 질문은 503 `AI_NOT_READY`다. 다시 열기는 질문마다 사유를 주고, 실행 다시 조회도 503이다.
- 질문 원문 삭제는 매일 03:30(Asia/Seoul)에 `question_expires_at`이 지난 행의 원문만 지운다. 나머지 진단 기록은 남긴다(M10-D04).
- 중복 제출 키는 직원별로 유일하다. 키 없이 보낸 질문은 기존처럼 매번 새로 실행한다.

## 4. 구현 내용

- `AiReadiness`(신규): 위 네 조건을 확인한다. 임베딩 모델이 없으면 `warnings`에 적는다.
- `AiWorkspaceService`
  - 준비 상태 응답에 `reasons`·`warnings`를 더했다.
  - 질문, 다시 열기, 실행 다시 조회에서 준비 상태를 확인한다.
  - `clientRequestKey`를 검증하고, 같은 키면 `REPLAY`로 돌려준다. 키를 실행 기록에 저장한다.
- `AiWorkspaceController`: 대화별 질문에도 `clientRequestKey`를 받는다. 유일 키 충돌(경합)이면 저장된 질문을 돌려준다.
- `AiTraceRetention`(신규): 매일 만료된 질문 원문을 지운다(`openstudy.ai.trace-retention.enabled`·`cron`).
  - 지금까지 `@EnableScheduling`은 초대 메일이 켜졌을 때만 있었다. 이 설정에서 스케줄링을 켠다.
- `AiTraceRepository.clearExpiredQuestions`, `AiExecutionRepository.findByEmployeeIdAndClientRequestKey`
- `V9__ai_execution_client_request_key.sql`: `ai_executions.client_request_key`와 `(employee_id, client_request_key)` 유일 키
- `ApiException.unavailable`(503)
- 계약: `nl-analysis-api.md`에 준비 상태·중복 제출·원문 삭제 절, `openapi.json`에 `reasons`·`warnings`·`NOT_READY`·`clientRequestKey`·`AI_NOT_READY`를 더했다.
- 테스트
  - `AiLifecycleIntegrationTests`(3개)
    - 실제 카탈로그는 준비됨이다. 연결이 끊긴 지표·지표 없는 등록 분석은 이유로 나온다.
    - 만료된 원문만 지워지고 다른 진단 기록은 남는다.
    - 같은 키 재제출은 같은 실행 ID와 `REPLAY`를 돌려주고 실행 수가 늘지 않는다. 다른 키는 새 실행이고, 형식이 틀린 키는 422다. 다른 직원의 같은 키는 별개다.
  - `AiNotReadyIntegrationTests`(1개): 준비 안 됨이면 질문 503, 다시 열기 사유, 실행 다시 조회 503, 준비 상태에 이유가 나온다.
