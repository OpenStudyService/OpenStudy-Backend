# 2026-11-10 지점 휴무일 관리와 룸 예약 차단 (#112)

## 1. 배경 / 문제

- M13 계약(#111, PR #200)의 지점 휴무일을 구현한다(FR-BR-09, ADR-M13-001 M13-D01·D05).
- 휴무일은 Asia/Seoul 하루 전체이고 지점 MANAGER 이상이 관리한다. 그날 시작하는 스터디룸 신규 예약만 막고, 판매·입실·출근·근무 등록은 막지 않는다.
- 등록할 때 그날 시작하는 기존 예약을 경고로 돌려주고, 자동으로 취소하지는 않는다.
- 계약은 이미 구현된 operation(룸 예약 등록, 달력, 홈 요약)에 더할 내용을 OpenAPI `x-planned-changes`에 두었다. 이번 구현에서 본 정의로 옮긴다.

## 2. 검토한 선택지

- **휴무일 서비스의 위치**: 지점 모듈과 예약 모듈 중 어디에 둘지 검토했다.
  - 예약이 휴무일을 확인해야 하므로 `reservation → branch` 의존이 생긴다.
  - 휴무일 등록의 기존 예약 경고는 예약 정보를 읽어야 한다. 지점 모듈이 예약 모듈 서비스를 부르면 모듈 순환이 되고, `ModuleBoundaryTests`가 순환을 막는다.
  - 그래서 휴무일은 지점 모듈에 두고, 경고용 예약 조회는 JPQL 엔터티 이름(`RoomReservation`, `Room`)으로 읽어 예약 모듈의 클래스를 가져오지 않게 했다.
- **409 대상 정보 전달**: M12처럼 컨트롤러 안에 예외 처리기를 두는 방법과, 공통 예외 처리기에 처리기를 두는 방법을 비교했다.
  - M13의 409는 이 이슈에서 예약 등록(예약 모듈), 이후 결제(#113)·병합(#114)·마감(#115)에서도 같은 본문(`OperationsConflictError`)을 쓴다.
  - 그래서 공통 예외 `OperationsConflict`와 전역 처리기를 두었다. `ApiException`을 상속하지 않아 기존 처리기와 겹치지 않는다(M12에서 겪은 처리기 우선순위 문제를 피한다).
- **권한 행위**: 기존 `MANAGE_SHIFTS`·`MANAGE_COLLABORATION`도 "MANAGER 역할만"이지만 의미가 다르다. 휴무일 전용 `MANAGE_CLOSURES`(역할만, 운영 중지 지점도 통과)를 더했다.

## 3. 결정 및 이유

- **동시성**: 모든 명령은 공통 잠금 순서에서 지점 행 전체를 `FOR UPDATE`로 잠근다. 휴무일 등록과 같은 지점의 예약 등록은 이미 차례로 처리되므로 별도 잠금을 더하지 않았다. 예약이 먼저 커밋되면 휴무일 응답의 경고에 나오고, 휴무일이 먼저면 예약이 409를 받는다.
- **검사 위치**: 예약의 휴무일 검사는 시간 규칙(422) 뒤, 정원·고객·시간 충돌 앞이다. 입력 오류가 먼저 나오고, 그다음 다른 데이터와의 관계를 본다(M8·M12와 같은 구분). M6 계약 문서의 검사 표에도 같은 위치로 적었다.
- **구현하면서 계약을 고친 것**
  - 경고 예약의 상태 표기를 계약 초안의 `예약`·`이용 중`에서 기존 예약 응답 표기인 `확정`·`이용 중`으로 맞췄다.
  - 지점 경로(`/branches/{id}/closures`)에서 접근할 수 없는 지점은 404가 아니라 403이다. 기존 지점 상세(`GET /branches/{id}`)가 존재 여부를 알리지 않으려고 403을 쓰는 것과 맞췄다. 휴무일 ID 경로(`/branch-closures/{id}`)는 계약대로 볼 수 없으면 404, 볼 수 있지만 권한이 없으면 403이다.
- **삭제 검사 순서**: 상태(오늘·지난 휴무일 409 `CLOSURE_ALREADY_STARTED`) → version이다. M12의 "상태 → version" 순서와 같다.

## 4. 구현 내용

- **V12 `branch_closures`**: 지점·날짜 유일 키, 지점·작성자 외래 키, version.
- **지점 모듈**
  - `BranchClosure` 엔터티와 `BranchClosureRepository`
  - `BranchClosureService`: 목록·등록·수정·삭제, 다른 기능용 조회 `closed`, `closedDates`, `upcoming`
  - `BranchClosureController`: operation 4개
  - `BranchAction.MANAGE_CLOSURES`
- **공통**: `OperationsConflict`와 전역 처리기. 본문은 `code`, `message`, `requestId`와 대상 정보 필드다.
- **예약**: 시작 날짜가 휴무일이면 409 `BRANCH_CLOSED_DAY`(`closedDate`). 달력 응답에 `closedDates`.
- **홈**: `closures`(scope 지점의 오늘부터 7일 뒤까지).
- **계약**
  - OpenAPI: #112 `x-planned-changes`를 본 정의로 옮겼다(달력 `closedDates`, 홈 `closures`, 예약 409 `BRANCH_CLOSED_DAY`·`OperationsConflictError`). 휴무일 operation 4개를 `implemented`로 바꿨다.
  - 문서: M13 계약 문서의 구현 표시·정정, M6 계약의 예약 검사 표, M9 계약의 홈 절에 한 줄씩 더했다.
- **DB 문서**: `schema-full.sql`을 V12 기준으로 다시 추출했다(`FoundationMigrationTests -PfoundationExportDir`). ERD에 `branch_closures`를 더했다. ERD 생성 도구가 저장소에 없어 기존 형식대로 직접 고쳤다. DB 안내의 버전·테이블 수(74개)를 고쳤다.
- **기존 테스트 조정**
  - 마이그레이션 번호·테이블 수를 고정한 테스트 3개를 V12·74개로 올렸다.
  - V11 마이그레이션 테스트는 최신까지 적용하던 것을 V11까지만 적용하게 했다.
  - 홈 응답 필드를 고정한 계약·통합 테스트에 `closures`를 더했다.

## 5. 검증 결과

- `BranchClosureIntegrationTests` 5개 통과(HTTP·MySQL). 인수 조건별로 다음을 확인했다.
  1. **권한·입력**: 일반 직원·다른 지점 관리자 403, 날짜 형식·허용 외 필드 422, 지난 날짜·366일 초과 422 `CLOSURE_DATE_INVALID`, 같은 키 재생과 다른 입력 409 `IDEMPOTENCY_CONFLICT`, 같은 날 중복 409 `BRANCH_CLOSURE_EXISTS`(`closureId`), 수정은 문구만(날짜 필드 422)·version 충돌 409·null로 지우기, 미래 휴무일만 삭제(오늘은 409 `CLOSURE_ALREADY_STARTED`), 감사 기록 순서.
  2. **예약 거부**: 휴무일에 시작하는 신규 예약 409 `BRANCH_CLOSED_DAY`(`closedDate`)이고 결제가 남지 않는다. 시간 형식 오류는 그대로 422다. 전날 23시에 시작해 휴무일 0시에 끝나는 예약은 허용된다. 다음 날 예약도 허용된다.
  3. **기존 예약 경고**: 그날 시작하는 예약 2건만 경고하고(다음 날 예약 제외), 고객 정보는 담지 않는다. 기존 예약 3건은 모두 확정 상태 그대로다.
  4. **다른 업무 비차단**: 오늘·내일 휴무일에도 이용권 판매, 출근, 내일 근무 등록이 성공한다. 좌석 입실은 휴무일 검사를 넣지 않은 코드 경로라 따로 실행하지 않았다.
  5. **조회 범위**: 접근할 수 없는 지점의 휴무일 목록은 403이다. 홈은 요청자 scope 지점의 오늘~7일 뒤만 보여 준다(8일 뒤 제외).
  - 응답 필드가 계약 schema와 정확히 같다.
- 마이그레이션·DB 초기화·아키텍처·예약·홈·지점 테스트: 227개 중 실패 2개(테이블 수와 홈 필드 고정값)를 고친 뒤 다시 실행했다.
- 전체 `./gradlew test`(16분 29초): 1,082개 실행, 실패 0, 건너뜀 26(기존과 같은 건너뜀 수).
