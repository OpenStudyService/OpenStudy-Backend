# 직원 관리·지점 소속·권한 프리셋 API (B06, #12)

## 배경 / 문제

F02 화면은 정본 DTO를 사용하지만 운영 직원 관리 API가 없어 실제 지점별 권한 저장과 계정 제한을 검증할 수 없었다. B03의 현재 DB 인가와 관리자 잠금 경계를 재사용해 업무 API를 구현한다. 이 작업 브랜치는 main에서 생성했으며 사용자 작업 트리의 다른 변경은 포함하지 않는다.

## 검토한 선택지

- 프리셋을 소속에 동적으로 연결하면 프리셋 수정이 기존 직원의 권한을 바꾸므로 확정 정책과 맞지 않는다. 프리셋은 복사 출처만 검증하고 요청의 최종 권한 집합을 소속에 저장한다.
- 병렬 B05 작업과 감사/outbox 공통 도우미를 만들지 논의했으나, 두 PR의 코드 의존을 늘리지 않도록 각 모듈 저장소가 기존 테이블에 같은 트랜잭션으로 기록한다.

## 결정 및 이유

`employee → authorization`의 공개 서비스/DTO 호출만 추가한다. authorization은 employee 저장소를 참조하지 않아 순환을 만들지 않는다. 기존 `AuthorizedCommands`가 guard → 직원 → 지점 → 소속 순서로 잠그며, 계정/소속 버전 검사와 변경·감사·outbox는 그 트랜잭션 안에서 수행한다. 프리셋 변경·복사도 같은 guard로 직렬화한다.

## 구현 내용

- `/api/employees` 목록·상세는 관리할 수 있는 지점으로 직원·소속·total을 함께 제한한다. OWNER의 all 조회에만 미배정 계정을 포함한다. 응답에는 자격증명이 없다.
- OWNER만 이름·전역 상태를 수정한다. 이메일/owner/memberships 등 미허용 필드는 422이며, 승인 대기 계정의 직접 활성화를 거부한다. 계정 제한·퇴사 시 해당 principal의 JDBC 세션을 삭제한다.
- 단일 지점 PUT은 employeeVersion과 membership version을 함께 검사하고 다른 지점의 소속은 보존한다. MANAGER는 본인 외 STAFF만 수정하며 관리자 강등 우회·승격·자기 변경을 거부한다. PENDING/REVOKED 소속은 직접 활성화할 수 없다.
- `/api/permissions` 사전, 프리셋 목록·생성·수정을 구현했다. STAFF 관리자 전용 권한과 알 수 없는 권한, 중복 권한을 거부한다. 시스템 프리셋은 수정할 수 없다. 생성은 `Idempotency-Key` 16~128자와 정규화 요청 해시로 동일 응답 재생·다른 입력 409를 제공한다.
- 감사는 actor/requestId와 자격증명 없는 전후 DTO를 기록한다. 권한 변경 대상 이벤트 및 목록 invalidate를 outbox에 남긴다. 열린 SSE 전달/종료는 B11의 범위다.

## 검증 결과

- Java 21, Testcontainers MySQL 8.4.11 고정 digest의 독립 테스트 DB에서 HTTP/MySQL 통합 테스트 10개와 모듈 경계 검사 1개를 통과했다. 실패·오류·건너뜀 0.
- 실제 HTTP 로그인·CSRF·3역할 인가, 타 지점 query/path 조작, 자격증명 미노출, 계정 제한 후 세션 401 및 JDBC 삭제, 프리셋 HTTP 생성·동일 키 재생·다른 입력 409·키 누락 422를 검증했다.
- 직원/소속 두 버전, 다른 지점 보존, 미승인/회수 복구 거부, 시스템 기본 STAFF 빈 권한·MANAGER 9종, 프리셋 변경의 비소급, 동시 소속 저장의 1성공/1충돌, 프리셋 변경/복사 경합, 마지막 OWNER 제한의 감사/outbox 롤백을 검증했다.
- `bootJar` 성공. 변경한 API의 전용 검사만 실행했으며 전체 회귀 및 B04/B05 결합 검증은 별도로 수행한다.

## 남은 작업 / 보류 사항

- main에서 빠져 있던 B04 세션 변경의 복원 PR #24와 B05 지점 관리 작업을 결합해 실제 F02 M1 브라우저 흐름을 추가 검증해야 한다.
- 열린 SSE 스트림의 즉시 종료·두 브라우저 invalidate, 운영 프록시/TLS 환경은 B11/V01에서 확인한다. outbox 기록만으로 전달 완료를 표시하지 않는다.
- 브랜치 push와 PR 준비 후 main 병합은 사용자에게 맡긴다. 이 기록만으로 #12 전체를 종료하지 않는다.
