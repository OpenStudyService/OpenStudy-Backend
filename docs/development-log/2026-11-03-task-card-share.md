# 2026-11-03 업무 카드 채널 공유 API

관련: Issue [#77](https://github.com/OpenStudyService/OpenStudy-Backend/issues/77), [계약 문서](../design/foundation/collaboration-api.md)의 메시지·업무 카드 절, [ADR-M7-001](../db/ADR-M7-001.md) M7-D07, [채널·메시지 API 기록](2026-11-03-channel-message-api.md).

## 1. 배경 / 문제

#76이 채널·메시지 operation을 구현하면서 `kind=업무 카드` 행은 읽을 수만 있게 두었다. 카드를 만드는 `POST /channels/{id}/task-cards`와, 읽을 때 채워야 하는 `task`(`TaskCard`)는 #77 범위였다. 이 이슈로 M7의 마지막 operation이 구현된다.

핵심 위험은 카드가 업무 접근 권한을 넓히는 것이다. 업무는 지점 소속자만 열 수 있는데, 카드는 채널 참여자 전체가 본다. 전체 채널에는 다른 지점 직원이 있고, 공유 뒤에 소속이 회수될 수도 있다. 그래서 카드는 공유 시점의 내용을 복사하지 않고, 읽는 사람과 읽는 시점을 기준으로 매번 만들어야 한다. 카드에서 업무를 직접 수정하는 것은 범위 밖이다.

## 2. 검토한 선택지

- **카드 내용을 만드는 위치**
  - 채팅 모듈이 업무 엔티티·저장소를 직접 읽는다: `ModuleBoundaryTests`가 다른 모듈의 `entity`·`repository` 접근을 거부한다.
  - 업무 모듈이 공개 서비스(`TaskCardService`)와 DTO(`TaskCardView`)를 내놓고 채팅이 부른다: 의존 방향이 chat → task 한 방향이고 task는 chat을 참조하지 않아 순환이 없다. 이것을 골랐다.
- **접근 규칙**
  - 카드용 규칙을 새로 정의한다: 업무 화면과 어긋날 여지가 생긴다.
  - 업무 화면(`GET /tasks/{id}`)이 쓰는 규칙을 그대로 쓴다(업무 지점에 대한 READ 가능한 유효 소속, OWNER 포함): 카드가 업무 화면보다 더 보여 줄 수 없다. 이것을 골랐다.
- **카드 응답을 만드는 시점**
  - 저장 시 만든 응답을 재생한다: 재전송에서 과거 상태가 나간다.
  - 읽을 때마다 업무 행에서 만든다: 이것을 골랐다. 목록은 업무 ID를 모아 한 번에 조회한다.

## 3. 결정 및 이유

- **저장은 `related_task_id`만 한다.** 상태·제목·담당자를 복사하지 않는다. 선택 `text`만 본문으로 저장한다. 기존 열(`messages.related_task_id`, `ck_messages_1`)로 충분해 마이그레이션은 없다.
- **접근 불가 카드는 필드를 지운다.** `accessible=false`이면 업무 ID·지점 ID를 포함해 나머지가 모두 null이다. 업무 ID가 있으면 `GET /tasks/{id}` 404와 비교해 존재를 알아낼 수 있어서다. 존재하지 않는 업무 ID가 들어와도 같은 모양으로 답한다(저장된 카드에서는 FK 때문에 생기지 않는다).
- **공유 시 판단 순서**: 참여(404) → 입력 형식(422) → 업무 접근(404) → 부모 메시지(404·422) → 키 확인. 참여 확인이 입력 검사보다 앞서는 규칙은 텍스트 메시지와 같다. 업무 접근을 키 확인보다 앞에 둔 것은 계약이 정하지 않아 판단한 부분이다(6절).
- **메시지 키는 텍스트와 같은 경로를 쓴다.** 같은 입력은 종류(카드/텍스트), 업무, 본문, 답글 대상이 모두 같은 경우다. 종류가 다르면 본문이 같아도 다른 입력이라 409다. 전송 경로를 둘로 나누면 키·부모·동시 재전송 규칙이 갈라질 수 있어 한 경로(`store`)에 카드 여부만 넘긴다.
- **읽는 사람의 상태는 요청마다 새로 얻는다.** 목록·단건·답글은 `policy.current`, 전송·재전송은 가드 아래에서 잠금으로 읽은 상태를 쓴다. 소속 회수와 전송이 같은 가드로 직렬화되므로 회수가 먼저면 공유가 404, 나중이면 카드가 접근 불가로 읽힌다.
- **쿼리 수는 고정한다.** 한 페이지의 업무는 `findAllById` 한 번, 담당자 이름은 한 번에 조회한다. 지점 권한은 이미 읽어 둔 요청자 상태로 메모리에서 판단한다.
- **새 경로를 만들지 않는다.** 카드에서 상세와 이력을 열 때는 기존 `GET /tasks/{id}`, `GET /tasks/{id}/events`를 쓴다. 같은 권한과 같은 이력이 적용된다.

## 4. 구현 내용

- **`modules/task`**: `TaskCardService`(`accessible`, `cards`)와 응답 DTO `TaskCardView`를 추가했다. 라벨은 업무 화면과 같은 `TaskInputs`를 쓴다.
- **`modules/chat`**
  - `MessageService`: `shareTaskCard` 추가. `send`와 `shareTaskCard`가 `store`/`attempt`를 공유하고, 동등 입력 판단(`sameInput`)이 종류·업무·본문·부모를 비교한다. 모든 조회·응답 생성(`views`)이 읽는 사람의 상태를 받아 `task`를 채운다. 재전송 응답도 같은 경로로 만들어 현재 업무 상태가 나간다.
  - `ChannelController`: `POST /channels/{id}/task-cards`(201 `Location` 포함, 재전송 200).
  - `Message.taskCard` 팩토리 추가. `MessageView.task`를 `TaskCardView`로 바꿨다.
- **문서**: `shareTaskCard`의 `x-implementation-status`를 `implemented`로 바꾸고 OpenAPI 설명과 `collaboration-api.md`의 구현 상태 문장을 갱신했다. 계약 내용은 바꾸지 않았다.
- **기존 시험 수정**: #76의 "카드 행은 `task=null`" 시험은 #77까지의 임시 기대였다. 카드가 `accessible=true`와 현재 제목을 주는 것으로 고쳤다. 시험 정리에 업무 이력·체크리스트 삭제를 더했다.

## 5. 검증 결과

- 전체 시험 `./gradlew test`: **59개 suite, 630개 시험, 통과 630, 실패 0, 건너뜀 0**(`build/test-results/test/*.xml` 집계, BUILD SUCCESSFUL, 24분 26초). Testcontainers MySQL에서 실행했다. `ModuleBoundaryTests`와 `CollaborationContractTests`도 통과했다.
- 이번에 추가한 시험은 `TaskCardIntegrationTests` 18개다. #76 이후 612개에서 630개로 늘었다.
- **실제 동시 실행**(HTTP 요청 경쟁, MySQL)
  - 같은 키로 카드 동시 공유 6건: 201 한 건·200 다섯 건, 행 1개, 모두 같은 메시지 ID.
  - 공유와 소속 회수 경합: 공유가 201이면 행이 있고 404면 행이 없으며, 행이 있으면 회수 뒤 카드는 접근 불가. 한 차례만 실행했으므로 두 결과가 모두 나왔다고 보장하지는 못한다.
- **쿼리 수**: Hibernate 통계로 카드 2개 채널과 40개 채널의 메시지 목록 요청이 준비한 문장 수가 같다. 접근 불가 독자도 이보다 많지 않다. JDBC 템플릿을 쓰는 세션·인증 조회는 이 수치에 들어가지 않는다.
- **미검증**: 실제 공유 DB·Frontend 연동, 카드 수천 건 규모의 성능, 한 업무에 대한 카드 수가 많을 때의 지연.

## 6. 남은 작업 / 보류 사항

계약이 정하지 않아 판단한 점이다. 바꿔야 한다면 계약에 먼저 적어야 한다.

- **재전송에서도 업무 접근을 먼저 확인한다.** 같은 키로 재전송하면 원래 메시지를 주지만, 그 사이 요청자가 업무 접근을 잃었다면 404다. 접근을 잃은 사람이 업무 ID로 다른 응답을 받지 않게 하려는 선택이고, 저장된 메시지는 그대로 남는다. 접근 불가 카드로 200을 주는 쪽도 정보 노출은 없지만 응답 코드가 복잡해져 택하지 않았다.
- **`text`가 명시적 null이면 422다.** 스키마에서 `text`는 nullable이 아니므로 생략만 허용한다.
- **업무 지점의 운영 중단**: 업무 화면과 같이 READ 권한만 보므로, 운영이 중단된 지점의 카드도 열린다.
- 카드 공유로 업무 쪽 이력(`task_events`)이나 알림은 남기지 않는다. 계약에 없다.
- 채널 목록의 마지막 메시지·미읽음 계산은 카드를 이전과 같이 한 건의 메시지로 센다.
- 실제 공유 DB와 Frontend 연동은 이 작업에서 확인하지 않았다.
