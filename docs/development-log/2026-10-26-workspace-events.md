# 기반 lookups·커밋 후 SSE·권한 회수 (#17)

## 배경 / 문제

지점·직원·인증은 병합됐지만 운영 `/api/lookups`와 SSE 전송기가 없어, 기존 브라우저 기록에 공통 정보 미제공과 열린 연결의 권한 회수 검증이 남아 있었다. [#17](https://github.com/OpenStudyService/OpenStudy-Backend/issues/17)의 전체 SSE 통합은 M3이지만 권한 회수·열린 세션 차단·민감 캐시 정리는 M1 종료 전 조건이다.

실제 이슈, main의 공통·인가·세션·직원·지점 구현, 병합 PR #26 및 기존 조직 결합 검증 기록을 확인했다. 원래 체크아웃의 사용자 변경을 보존하기 위해 최신 main `63f8af4` 기반 분리 작업 공간의 `feature/workspace-events`에서 작업했다. 지점·직원 API와 세션 경계를 다시 구현하지 않았다.

## 검토한 선택지

- 관리용 직원 DTO를 선택 데이터로 재사용하면 이메일·상태·소속·권한이 노출된다. 직원 저장소의 공개 서비스에 별도 `{id,name}` 읽기 모델을 추가했다.
- 최대 outbox ID를 cursor로 보관하면 먼저 발급된 작은 ID가 늦게 커밋될 때 영구 누락된다. 미발행 행을 읽고 처리한 행에만 published_at을 기록한다.
- 업무 트랜잭션에서 직접 전송하면 롤백된 변경이 보이거나 네트워크 때문에 관리자 잠금을 오래 유지한다. 기존 outbox를 재사용하고 dispatch의 업무 트랜잭션을 중지해 커밋된 행만 읽는다.
- 스트림 최초 인증만 믿으면 로그아웃·시간 만료·권한 회수가 열린 연결에 반영되지 않는다. 저장된 JDBC 세션·현재 계정·소속·역할·grants를 주기적으로, 그리고 전달 직전에 다시 검사한다.

## 결정 및 이유

새 workspace 모듈은 auth·authorization·branch·employee의 공개 서비스/DTO만 호출하며 다른 모듈 저장소나 엔티티를 참조하지 않는다. 기존 모듈에서 workspace로 역호출하지 않아 순환이 생기지 않는다. 권한은 현재 DB가 원본이며 세션에는 별도 권한 snapshot을 보관하지 않는다.

이벤트는 개인정보 없는 무효화 신호다. 범위가 있는 사건은 현재 허용 지점에서만 전달하고, 전역/개인 신호는 필요한 경우 식별자를 null로 지운다. 해당 직원의 권한 변경은 대상에게만 scope 없는 authorization.changed 후 종료한다. 세션 만료·로그아웃·계정 제한은 본문 없이 종료한다.

## 구현 내용

- `GET /api/lookups`는 현재 허용 지점·최소 활성 직원 이름·권한 사전·관리 권한별 프리셋과 정상 빈 배열을 반환한다. 승인 대기·제한 계정·타 지점 직원과 관리용 직원 정보는 노출하지 않는다. 상품·분류는 관련 운영 API가 구현되기 전까지 빈 배열이다.
- 같은 경로에 있던 로컬 샘플 선택 데이터를 `/api/local-preview/lookups`로 구분하고 기존 샘플 회귀 시험을 해당 경로로 유지했다. 운영 경로는 local 프로필에서도 실제 최소 계약이다.
- `GET /api/workspace/events`는 모든 연결에 resync를 보낸다. 기존 invalidate/authorization.changed/resync의 명명·현재 사용자/선택 데이터 재조회 계약을 따른다. cursor/Last-Event-ID 재생과 다중 인스턴스 fan-out을 제공하지 않는다.
- 기존 outbox의 지점 사건·대상 직원 사건·전역 직원/프리셋 사건을 구분한다. 타 직원에게 대상 ID를 전송하지 않으며, 직원 목록 무효화는 관계있는 지점에 식별자 없이 전달한다. 일반 직원은 관리자 프리셋 사건을 받지 않는다.
- 기본 재검사 대기 500ms, heartbeat 15초 및 연결 상한 512를 구현 설정으로 제공했다. heartbeat는 comment이며 Spring Session을 조회만 하고 활동 시각을 연장하지 않는다.
- 열린 세션의 유휴/최대 수명·현재 계정 상태·현재 권한을 재검사한다. ASYNC 완료 dispatch는 이미 시작한 스트림에 JSON 인증 오류를 추가하지 않고 지속 인가는 스트림 서비스가 담당한다.
- OpenAPI `0.1.4-workspace`와 [구현 계약](../design/foundation/workspace-api.md)을 갱신했다. 같은 JSON으로 API 엑셀과 프론트 정본 타입을 동기화하고 실제 브라우저 검증을 연결했다.

## 검증 결과

- Java 21·전용 Testcontainers MySQL 8.4.11에서 `gradlew.bat test bootJar` 전체 17개 suite, 121개 시험과 실행 JAR 빌드가 통과했다. 실패·오류·건너뜀 0.
- 최소·범위별 lookups와 일반 직원 프리셋 비노출, 정상 빈 배열, 미인증·제한 세션·잘못된 scope, 커밋/롤백 전달 경계, 대상/지점 누출 차단, 열린 소속 회수, 로그아웃·계정 제한, heartbeat 활동 미연장 및 60분/12시간 경계를 실제 스트림으로 확인했다. 종료된 SSE에 인증 JSON이 추가되지 않았다.
- 작은 outbox ID의 늦은 커밋이 앞서 처리된 큰 ID 뒤에도 전달됨을 추가로 확인했다. 마지막으로 최초 resync가 poll보다 먼저 대기열에 들어가도록 순서를 정리한 뒤 workspace 8개와 모듈 경계 1개 시험 및 bootJar를 다시 통과했다.
- `graphify update .`로 AST 그래프를 갱신했다. SQL parser 미설치·Gradle AST 경고는 탐색 그래프 제한이며 실제 Java·MySQL 실행과 구분한다. 원래 커밋된 backend 그래프가 없었으므로 새 산출물은 로컬 탐색 자료로 보관한다.

## 남은 작업 / 보류 사항

- 실제 두 브라우저의 권한 회수·세션 차단과 서버 재시작 재연결은 아래 결합 검증으로 확인했다.
- 운영 TLS/프록시의 buffering·heartbeat 연결 유지, 다중 ECS fan-out 및 이벤트 재생은 이번 로컬 결과에 포함하지 않는다. 단일 인스턴스 발행 표시를 모든 서버 수신 완료로 해석하지 않는다.
- 초대·상품·메일 및 전체 통합 검증 #18은 이 PR로 완료 처리하지 않는다. 구현되지 않은 상품·분류 선택 데이터는 빈 배열이라는 한계를 명시한다.
- 커밋·push·PR은 부모 작업에서 검토 후 준비하며 main 반영·병합·자동 병합은 사용자가 수행한다.


## 실제 서버·브라우저 결합 검증

- MSW를 끈 Chrome의 독립 OWNER/MANAGER 세션과 전용 MySQL 8.4.11에서 검증했다. 사용자 DB 대신 빈 DB migration과 기존 offline OWNER bootstrap을 사용했으며, 추가 계정·소속은 격리된 시험 fixture로 준비했다. 초대·승인 흐름을 수행한 것으로 해석하지 않는다.
- 현재 지점 lookups의 직원 필드가 정확히 ID·이름이며 타 지점·승인 대기·회수·퇴사 계정이 제외됨을 확인했다. 실제 응답으로 업무 폼의 직원 선택과 주간 근무표 이름 렌더링을 확인했다. 미구현 업무·근태 API의 404 안내는 별도이며 해당 업무 저장 성공을 주장하지 않는다.
- OWNER가 실제 직원 API로 MANAGER의 관리 grants를 제거하자, 열린 직원 상세와 관리 메뉴가 제거되고 권한 안내가 표시됐다. 관리 grants 복원 후 관리 화면이 회복됐다. 이어 현재 지점 소속 회수 후 접근 차단, 다른 허용 지점의 설정 화면에서 계정 제한 후 로그인 이동을 확인했다. 스트림에 타 지점 ID·이메일·직원 이름이 포함되지 않았다.
- 브라우저 offline 에뮬레이션은 이미 열린 SSE를 끊지 않아 재연결 근거로 사용하지 않았다. 권한 복원 직후 누적 resync 증가는 복원에 따른 재연결일 수 있어 서버 재시작 증거로 제외했다. 안정된 별도 연결에서 실제 서버 재시작을 시험하자 로컬 Vite 프록시가 중단을 브라우저에 전달하지 않는 경계가 관찰되어 Frontend 동반 수정에서 확인했다. 보완 후 안정된 OWNER 연결의 서버 재시작에서 error → 재시도 → 새 open/resync(1→2)와 닉네임 설정 화면 유지를 확인했다. 권한 복원과 분리한 시험이며 재연결 시도 5회가 관찰됐다.

## 계약 산출물 동기화

- OpenAPI `0.1.4-workspace` SHA-256 `b9d4752fef7c0fa165dbc5ca11fe7427c4236b16130706b2c99d786678474da7`에서 기존 생성 방식으로 API 엑셀 8개 시트를 갱신했다. 40개 operation·61개 schema, 수식 오류 검색 0건이며 변경된 lookups/SSE 행을 렌더링해 확인했다. main 정책 변경으로 제거된 상품 물리 삭제 계약도 이 정본을 따라 반영된다.
- Frontend 동반 브랜치에서 같은 JSON으로 `foundation.generated.ts`를 재생성했다. 최소 lookup 소비자 보완과 함께 TypeScript·ESLint·125개 시험 및 live 빌드를 통과했다. 정본 계약의 주석·cursor 힌트와 이전 상품 삭제 operation 제거도 동기화된다.

## 최종 리뷰 후 직원 식별자 비노출 보완

- 전역 직원 이벤트는 식별자를 지웠지만, 기존 직원 명령이 기록하는 지점별 목록 무효화에는 대상 직원 ID가 남는 분기를 발견했다. 같은 지점의 일반 직원은 최소 선택 데이터에서 이미 제외된 회수 직원을 관리 API로 조회할 권한이 없으므로 해당 ID도 전송하지 않기로 했다.
- 지점별 직원 이벤트의 entityId를 항상 null로 지우고 현재 수신자에게 허용된 branchId와 자원 무효화 신호는 유지했다. 전역·개인 신호의 식별자 제거 정책과 인가·세션 검사 경계는 유지한다. 정본 스키마와 OpenAPI SHA-256은 바뀌지 않았다.
- OWNER의 실제 HTTP 소속 회수 PUT 뒤 STAFF의 열린 SSE를 읽는 회귀 시험으로 수정 전 대상 ID 노출을 재현했다. 수정 후 식별자가 null이고, 회수 대상이 실제 lookups에서 제외되며, 일반 직원의 관리 API 조회는 403임을 확인했다.
- 보완 후 workspace 9개·모듈 경계 1개 시험과 bootJar를 통과했고 `graphify update .`를 다시 실행했다. 기존 브라우저·계약 산출물 검증 기록은 보존했다.
- 마지막 `gradlew.bat test bootJar` 전체 재실행은 4분 20초에 성공했다. 최종 17개 suite·122개 시험, 실패·오류·건너뜀 0이며 privacy 수정이 포함된 실행 JAR를 생성했다.

## 최종 결합 재검증 및 정리

직원 ID 비노출 최종 JAR로 MSW 없는 Chrome 두 세션의 최소 목록·직원 선택·주간 이름, 관리 grants 제거/복원, 지점 소속 회수, 계정 제한 후 로그인 이동을 다시 통과했다. 재시작 재연결은 개인정보 보완 직전의 동일 스트림 연결 코드로 독립 검증했으며, 최종 개인정보 보완은 실제 HTTP/SSE 회귀 시험과 전체 122개 시험으로 확인했다. Frontend 동반 PR은 #16이며 125개 시험·live 빌드를 통과했다. 직접 만든 Backend·Vite 서버와 일회용 MySQL을 종료했고 18917/5178 포트가 닫혔음을 확인했다. 원래 체크아웃의 사용자 변경과 DB는 보존했다.
