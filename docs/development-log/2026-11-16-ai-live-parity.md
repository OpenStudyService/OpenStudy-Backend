# 2026-11-16 실제 모델 수치 대조와 단계별 지연 측정 (#97)

## 1. 배경 / 문제

- #97 인수 조건: 실제 엔진·모델로 대표 질문과 추가 조합을 실행해 정형 매출 API와 수치·단위가 같은지 확인하고, 단계별 지연 p95로 제한값을 제안한다.
- 지금까지의 확인은 녹화 응답(playback)과 정형 API 대조(`AiSalesEquivalenceIntegrationTests`), 실제 Qwen 1~2회 단발 확인뿐이었다.
- 응답의 단계별 소요 시간 가운데 질문 접수(2ms), 카탈로그 검색(6ms), 검증(3ms), 화면 구성(2ms), 생성 경로의 검증·실행(1ms)은 측정값이 아니라 고정값이었다. 이 값으로는 단계별 p95를 낼 수 없다.

## 2. 검토한 선택지

- **대조 기준 조건**: 질문마다 기대 기간을 시험에 적어 그 기간으로 API를 부르는 방법과, 답변이 "적용했다"고 밝힌 조건(기간)으로 API를 부르는 방법을 검토했다. 뒤의 방법을 택하고, 적용 기간이 질문의 기대 기간과 같은지는 별도 항목으로 확인했다. 수치 계산 오류와 기간 해석 오류를 구분해 볼 수 있기 때문이다.
- **단계 시간**: 생성 경로는 DomainLens 파이프라인이 이미 단계 전환을 알리는 관찰자(`observing`)를 갖고 있어 이를 썼다. 등록 분석 경로는 계획 호출 전후 시각을 재고, 그 시간에서 모델 호출 시간을 뺀 값을 검색 단계로 기록했다. 계획 메서드의 반환 레코드를 바꾸는 방법은 생성 지점이 10곳이 넘어 택하지 않았다.

## 3. 결정 및 이유

- 실제 Qwen 호출은 사용자 확인 뒤 **1회만** 실행했다. 사용 중인 키가 팀원 계정 키이기 때문이다. 그래서 p95 인수 조건은 이번에 충족하지 못했다(5절).
- 실측에서 드러난 수치 오류 1건과 기간 해석 오류 1건은 이 작업에서 고쳤다. 대조가 인수 조건의 핵심이기 때문이다. 상품 지정 질문과 불필요한 모델 호출은 동작 범위를 바꾸는 일이라 후속으로 남겼다(6절).

## 4. 구현 내용

- **단계별 실제 시간** (`AiWorkspaceService`, `AiGenerationService`)
  - 등록 분석: 접수·검색·검증·화면 구성을 고정값 대신 측정값으로 기록한다. 규칙으로만 정한 질문의 생성 단계는 0ms다.
  - 생성 경로: 검색·계획 생성·검증·실행을 파이프라인 단계별로 기록한다. 이전에는 생성 전체 시간을 "생성" 단계 하나에 넣었다.
  - `securityGate`: 생성 경로의 시간과 토큰을 `generationLlmDurationMs`·`generationDurationMs`·`generationTotalTokens`로 따로 둔다. 이전에는 등록 분석 선택기의 `llmDurationMs`를 덮어썼다.
- **결제 승인액·결제 건수 지표 수정** (`OpenStudyCatalogConfiguration.APPROVED_PAYMENT`)
  - `status = APPROVED` → `status IN (APPROVED, REFUNDED)`.
  - M9 정형 API는 승인 시각이 있는 결제를 모두 승인으로 세고, 환불은 별도 항목으로 뺀다. 이전 필터는 승인 후 환불된 결제를 승인액·건수에서 빠뜨렸다.
  - 생성 경로 시험 2개에 환불된 결제를 추가하고, 기대값 계산도 같은 기준(`approved_at`)으로 바꿨다.
- **연도 없는 달 해석** (`OpenStudyIntentAnalyzer.MONTH_ONLY`)
  - "11월에"를 기간 없음으로 읽어 기본 기간(이번 달)을 쓰던 문제다. 연도가 없는 달은 지금까지의 가장 최근 그 달로 읽는다(12월에 묻는 "11월"은 올해, 2월에 묻는 "11월"은 작년).
  - "2026년 11월"(연도 있음), "11월 3일"(날짜), "3개월"(기간 길이)은 이 규칙에 걸리지 않는다.
- **실측 시험** (`AiLiveParityIntegrationTests`, opt-in)
  - `OPENSTUDY_AI_LIVE_TESTS=true`와 Qwen 설정이 있을 때만 실행한다. `OPENSTUDY_AI_PARITY_REPEATS`로 반복 횟수를 정한다.
  - 기존 매출 계산 예시 픽스처(10~12월, 환불, 실패 결제, 스터디룸·사물함)를 쓰고, AI 기준 시각은 2026-12-10 12:00(KST)이다.
  - 질문 12개(등록 분석 8, 생성 경로 4)의 결과를 같은 조건의 정형 API와 대조하고, `build/ai-live-parity.md`에 대조표와 단계별 p50·p95를 남긴다.

### 제한값 제안 (잠정, 1회 측정 근거)

- 모델 시간 제한 60초와 화면 대기 60초는 관측 최대(약 8초)보다 충분히 커서 유지를 제안한다.
- 요청 빈도 제한(사용자별 동시 10, 분당 120)은 모델 호출 1~2회·약 3천~4천 토큰인 생성 경로 기준으로 비용 상한 역할이 약하다. 반복 측정 뒤 분당 한도를 낮출지 판단하기를 제안한다. 근거가 1회 측정이라 이번에는 바꾸지 않았다.

## 6. 남은 작업 / 보류 사항

- **p95 반복 측정**: `OPENSTUDY_AI_PARITY_REPEATS=5` 이상으로 실행해야 한다(약 16만 토큰 예상). 사용할 키와 비용 확인이 필요하다. 수정한 G1·G2·R3도 이때 실제 모델로 재확인한다.
- **상품을 지정한 질문(R7)**: 등록 분석이 질문 속 상품명을 상품 조건으로 읽지 않는다. 화면의 "조건 변경"으로는 상품을 고를 수 있다. 질문에서 상품을 읽을지는 별도 판단이 필요하다.
- **규칙으로 정해진 질문에도 모델 호출**: live 모드에서는 키워드 규칙이 등록 분석을 찾은 질문(R1·R2)에도 등록 분석 선택기를 부른다. 결과는 규칙이 이기므로 호출이 쓸모없다(약 2.2초, 약 780토큰). 건너뛰면 지연과 비용이 줄지만, 선택기 응답의 다른 값(의도 영역 등)에 기대는 곳이 있는지 확인이 필요하다.
- M10-D14 대체 ADR 작성은 이번 범위에 넣지 않았다.
