# 2026-11-10 상품 판매 기간·판매 한도 (#113)

## 1. 배경 / 문제

- M13 계약(#111)의 상품 판매 기간·한도를 구현한다(FR-PROD-10, ADR-M13-001 M13-D02·D06).
- 판매 기간과 한도는 선택 값이다. 비어 있으면 제한하지 않는다.
- 판매 가능 여부는 판매 상태 → 판매 기간 → 남은 한도 순서로 확인하고, 사유마다 다른 코드로 거부한다.
- 한도는 상품 하나에 모든 판매 지점을 합친 수량이다. 승인된 판매만 세고, 환불하면 다시 팔 수 있다. 동시 판매에서도 한도를 넘지 않아야 한다.
- 계약은 기존 상품·결제 operation에 더할 내용을 `x-planned-changes`에 두었다. 이번에 본 정의로 옮긴다.

## 2. 검토한 선택지

- **판매 수 계산**: 상품에 카운터 칼럼을 두는 방법과 결제 상태를 직접 세는 방법을 비교했다.
  - 카운터는 판매·환불마다 갱신해야 하고, 원거래와 어긋날 수 있다.
  - 계약대로 `승인` 상태 결제 수를 직접 센다. 환불은 결제를 `환불`로 바꾸므로 자연히 수가 줄고, 실패 결제는 처음부터 세지 않는다. `payments (product_id, approved_at)` 인덱스로 상품별 범위 탐색이 된다.
- **판매 수 조회 위치**: 상품(ticket) 모듈이 결제 모듈 서비스를 부르면 모듈 순환이 된다(결제가 이미 상품을 부른다). 그래서 JPQL 엔터티 이름(`Payment`)으로 읽어 결제 모듈 클래스를 가져오지 않았다(#112와 같은 방식).
- **잠금 방식**: 계약은 한도가 있는 상품만 `FOR UPDATE`, 없는 상품은 기존 공유 잠금이다.
  - 처음에는 한도를 잠그지 않고 읽은 뒤 잠금 방식을 정하면, 그 사이 한도가 생기는 경쟁이 걱정이었다.
  - 확인해 보니 모든 명령이 공통 가드 행(`administration_guard`)을 먼저 `FOR UPDATE`로 잠근다. 명령끼리는 이미 차례로 실행되므로 그 사이에 한도가 바뀌지 않는다. 계약 그대로 구현했다.
- **변경 이력의 칼럼**: 계약 스키마 영향 표는 `product_revisions`에도 칼럼을 더한다고 적었다. 하지만 이력은 `snapshot_json`에 상품 전체 스냅샷을 담으므로 칼럼이 필요 없다. 스냅샷에 세 필드를 넣고 `schemaVersion`을 2로 올렸다.

## 3. 결정 및 이유

- **판정 순서**: 판매 중지 → 판매 지점 → 판매 기간 → 남은 한도. 기존 순서(판매 중지 → 판매 지점)를 유지하고 ADR 순서를 그 뒤에 붙였다(계약).
- **판매 기간**: 처리 시각(서버 시각)이 `[salesStartsAt, salesEndsAt)` 안이어야 한다. 시각은 오프셋을 받고 초 단위까지만 받는다(초 미만 422).
- **실패 결제**: `mockOutcome=FAILED`도 같은 판정을 거친다. 한도를 다 판 상품의 실패 결제는 남지 않는다. 판정을 통과한 실패 결제는 판매 수에 들어가지 않는다.
- **한도를 판매 수보다 낮게**: 허용한다. 이미 판 결제는 그대로이고 `remainingQuantity`는 0, `saleAvailability`는 `한도 소진`이다(계약).
- **PATCH**: 필드를 빼면 그대로 두고, null이면 제한을 없앤다. 값이 같으면 변경이 아니다(version·이력·감사 없음, 기존 규칙과 같다).
- **스냅샷 필수 필드**: #113 이전에 저장된 버전 1 스냅샷에는 세 필드가 없다. 그래서 OpenAPI `ProductSnapshot`에서 세 필드를 필수로 두지 않고 `schemaVersion` 최대값만 2로 올렸다.
- **409 대상 정보의 형식**: #112의 공통 예외 `OperationsConflict`가 모든 값을 문자열로 바꾸고 있었다. `salesLimit`·`soldQuantity`는 schema상 정수라 값을 주어진 형식 그대로 쓰게 고쳤다(ID와 날짜는 호출 쪽에서 문자열로 넘긴다). null인 대상 정보는 본문에서 뺀다(판매 시작만 있는 상품의 `salesEndsAt` 등).

## 4. 구현 내용

- **V13**: `products`에 `sales_starts_at`, `sales_ends_at`, `sales_limit`과 기간 순서·한도 범위 CHECK를 추가했다.
- **상품**
  - 엔터티 `changeSales`
  - `ProductRecord.Sales`
  - 응답 `Product`의 판매 기간·한도·`soldQuantity`·`remainingQuantity`·`saleAvailability`
  - `ProductSnapshot` 버전 2
  - 목록 `availability` 필터. 판매 수는 목록 전체를 한 번의 GROUP BY로 센다.
  - 등록·수정의 입력 처리(`SalesInput`)
- **판매(`sellable`)**: 한도 유무로 잠금 방식을 정한 뒤 판매 중지 → 판매 지점 → 판매 기간 → 한도를 판정한다. 기간·한도는 `OperationsConflict`로 대상 정보를 담는다.
- **계약**
  - OpenAPI: #113 `x-planned-changes`를 본 정의로 옮겼다(`Product`, `ProductCreate`, `ProductUpdate`, `ProductSnapshot`, 목록 `availability`, 결제 409·오류 코드).
  - 문서: M13 계약의 구현 표시·정정, M4 결제 검사 표, 상품 API 문서
- **DB 문서**: `schema-full.sql` V13 재추출, ERD `products` 칼럼, DB 안내 버전
- **기존 테스트 조정**: 마이그레이션 번호 고정 테스트 3개(V13), V12 테스트를 V12까지만 적용하게 변경, V13 마이그레이션 테스트 추가, M13 계약 테스트

## 5. 검증 결과

- `ProductSaleLimitIntegrationTests` 6개 통과(HTTP·MySQL, 시계를 고정해 경계를 확인). 인수 조건별로 다음을 확인했다.
  1. **제한 없음**: 기간·한도가 없으면 기존처럼 판매된다. 응답은 `판매 가능`이고 남은 수량은 null이다. 응답 필드가 schema와 같다.
  2. **판정 순서**
     - 시작 1초 전은 `PRODUCT_NOT_IN_SALE_PERIOD`(대상 정보 포함), 시작 시각은 판매된다.
     - 한도를 다 팔면 `PRODUCT_SALE_LIMIT_REACHED`(`salesLimit`, `soldQuantity`)다.
     - 종료 시각에는 한도 초과여도 기간이 먼저다.
     - 판매 중지가 기간보다 먼저이고, 판매 지점이 기간보다 먼저다.
  3. **동시 판매**: 남은 한도 1에서 두 지점의 동시 판매 2건 중 1건만 201이고 나머지는 409 `PRODUCT_SALE_LIMIT_REACHED`다. 환불로 1개를 되돌리며 3번 반복했다.
  4. **환불·실패 결제**: 실패 결제는 남은 수량을 쓰지 않는다. 환불하면 남은 수량이 다시 1이 되고 다시 판매된다. 한도를 다 판 상품의 실패 결제 요청은 409이고 행이 남지 않는다.
  5. **한도 낮추기**: 판매 수 3인 상품의 한도를 2로 낮추면 허용되고 `한도 소진`이며, 기존 결제 3건은 그대로다. 한도를 지우면 다시 판매된다. 목록 `availability` 필터가 동작한다.
  6. **이력·입력**: 기간·한도 변경은 새 revision이고 스냅샷 버전 2에 이전·이후 값이 남는다. 같은 값은 revision을 만들지 않는다. 종료 ≤ 시작, 초 미만, 한도 0·1,000,001·소수는 422다.
- 상품·결제·아키텍처·지점·예약 테스트 247개, 마이그레이션·DB 초기화 테스트 39개가 통과했다.
- 전체 `./gradlew test`(16분 54초): 1,089개 실행, 실패 0, 건너뜀 26.
