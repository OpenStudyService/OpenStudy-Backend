# 2026-10-29 마이그레이션 버전 번호를 병합 직전에 정하는 규칙

## 1. 배경 / 문제

M4~M15 이슈를 등록하면서 새 마이그레이션이 필요한 이슈가 10개 이상 생겼다(#55, #68, #89, #96, #100, #108, #112~#115, #119). 이 이슈들은 마일스톤 순서와 다르게 병행·병합될 수 있다. 일부 이슈에는 "V2는 M4, V3는 M8 예약" 같은 번호 예약 문구가 있었는데, M8은 스키마 변경이 없어 V3 예약이 이미 의미를 잃었다.

Flyway는 기본 설정에서 이미 적용된 버전보다 낮은 새 버전을 적용하지 않는다. 번호를 미리 고정하면 뒤 번호가 먼저 병합되었을 때 앞 번호가 적용되지 않는다.

## 2. 검토한 선택지

| 선택지 | 내용 |
| --- | --- |
| 병합 직전에 다음 번호 | 작업 중에는 임시 번호, 병합 직전 main 최대 + 1로 맞춘다. Flyway 기본 설정 유지 |
| 지금 이슈별로 고정 | 번호가 미리 보이지만 병합 순서를 번호에 맞추거나 순서 어긋남 허용이 필요 |
| 타임스탬프 버전 | 번호 충돌은 없지만 오래된 PR이 늦게 병합되면 순서 어긋남 허용이 필요 |

## 3. 결정 및 이유

사용자가 "병합 직전에 다음 번호"를 골랐다. 버전 순서가 병합 순서와 같아져 Flyway의 `outOfOrder`를 켜지 않아도 되고, 운영의 Infra Flyway 실행 방식도 바꿀 필요가 없다.

## 4. 구현 내용

- `src/main/resources/db/migration/README.md`에 버전 번호 규칙을 추가했다.
- `MigrationVersionTests`를 추가했다. 마이그레이션 파일 이름 형식과, 버전이 1부터 빠짐·중복 없이 이어지는지 확인한다.
- 마이그레이션이 필요한 이슈 본문의 번호 예약 문구를 이 규칙으로 바꿨다(GitHub 이슈, 저장소 밖).

## 5. 검증 결과

- `./gradlew test --tests com.openstudy.architecture.MigrationVersionTests`: 1개 시험 통과(현재 V1만 존재).
- 임시로 `V3__gap_check.sql`을 만들어 V2가 빠진 상태를 만들었을 때 시험이 실패하는 것을 확인하고 파일을 지웠다.
- 전체 시험은 실행하지 않았다. 앱 코드 변경은 없다.

## 6. 남은 작업 / 보류 사항

- 같은 번호의 두 PR이 동시에 병합 대기 중이면, 늦게 병합하는 쪽이 번호를 다시 올려야 한다. 병합은 사용자가 하므로 PR 설명에 이 확인을 넣는다.
