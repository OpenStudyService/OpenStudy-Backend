# 2026-11-03 고객 문의 대리 등록·담당자·답변·미처리 수치 API

관련: Issue [#79](https://github.com/OpenStudyService/OpenStudy-Backend/issues/79), [계약 문서](../design/foundation/collaboration-api.md), [ADR-M7-001](../db/ADR-M7-001.md) M7-D02, [ADR-M4-002](../db/ADR-M4-002.md) M4-D05, [정확 일치 조회 계약](../design/foundation/seat-usage-api.md), [시설 API 기록](2026-11-03-facility-inspection-api.md).

## 1. 배경 / 문제

전화·현장으로 받은 고객 문의를 등록하고 담당자 배정과 답변을 거쳐 끝까지 추적하는 화면이 로컬 샘플로만 동작했다. `modules/inquiry`가 비어 있었기 때문이다. #74 계약이 병합되고 업무(#75)·시설(#78)이 구현되어 문의 operation 8개를 구현할 수 있게 됐다.

이번 작업에서 가장 조심한 부분은 **대상 고객 검증**이다. 문의 응답은 고객의 ID·회원번호·이름을 담는다. 대상 고객을 검증하지 않으면 임의의 고객 ID를 넣어 이름을 알아낼 수 있다. 일반 고객 조회는 지점 범위(M4-D05) 안에서만 열리므로, 문의가 그 범위를 우회하는 통로가 되면 안 된다.

## 2. 검토한 선택지

- **정확 일치 조회로 찾았다는 증명**
  - 요청에 "조회로 찾았다"는 표시(플래그, 토큰)를 받는다: 클라이언트의 주장을 믿게 되므로 쓰지 않았다. 계약도 이를 금지한다.
  - `customer_service_interactions`(조회 근거 기록)를 서버가 확인한다: 계약이 정한 방식이다. 이쪽을 택했다. 기록은 고객·지점·직원 세 값이 모두 일치해야 인정한다.
- **고객 확인을 어느 모듈에 둘지**: 기록 표와 일반 조회 범위(`CustomerSearchRepository`)는 customer 모듈 소유다. 문의 모듈이 그 repository에 직접 접근하지 않도록 `CustomerService.requireInquiryTarget`을 새 진입점으로 열었다. 기존 `requireVisible`은 정확 일치 조회를 인정하지 않는 것이 의도라 그대로 두었다.
- **담당자 FK**: `inquiries.assigned_employee_id`는 `employees`를 참조한다(업무와 달리 지점 소속 FK가 아니다). 스키마를 바꾸지 않고, 업무와 같은 `EmployeeAccountService.assignable`로 "같은 지점의 활성 직원"을 서비스에서 검사한다.
- **이력의 상태 값**: `inquiry_events.old_status/new_status`는 `varchar(30)`이다. 문의 상태 enum 이름(`RECEIVED` 등)을 저장하고 응답에서 한글 표기로 바꾼다. 문의 행의 상태와 같은 표현이라 질의가 쉽다.
- **수치 집계**: 업무·시설과 같이 목록과 수치가 한 repository의 같은 WHERE 조립 코드를 쓰게 했다. 문의에는 `status`를 뺀 필터만 수치가 받는다.

## 3. 결정 및 이유

- **대상 고객**(등록 시에만 확인한다. 응답의 고객은 `CustomerSummary`뿐이다)
  - 요청자의 일반 고객 조회 범위(scope=all) 안이거나, **같은 지점에서 요청자 본인**이 정확 일치 조회로 찾은 기록이 있어야 한다. 둘 다 없으면 404이고, 존재하지 않는 ID도 같은 404라 존재 여부를 알 수 없다.
  - 일반 조회 범위는 요청의 `scope`가 아니라 요청자의 전체 범위(`all`)로 본다. 요청의 `scope`는 범위를 좁히기만 하는 값이라 문의 대상 판단에 쓰지 않는다.
  - 소속 행이 없는 OWNER는 조회 근거 기록이 남지 않는다(기록 표가 지점 소속을 참조). 대신 OWNER의 범위가 모든 고객을 포함하므로 범위 검사로 통과한다. 존재하지 않는 ID는 OWNER도 404다.
  - 문의를 등록해도 고객의 일반 조회 범위는 바뀌지 않는다. 문의 모듈은 어떤 기록도 쓰지 않는다.
- **명령 순서**: 입력 검증 → 범위(404) → 잠금 → 권한(403) → version(409) → 담당자 자격(422). 등록은 지점 소속 확인(403) 뒤에 고객을 확인하므로 지점 소속이 아닌 사람은 고객이 있는지 알 수 없다. 멱등 키 재생은 고객 확인 **뒤에** 둬서, 접근 근거를 잃은 요청자가 같은 키로 이전 응답(고객 이름)을 다시 받지 못하게 했다.
- **권한**: 목록·상세·이력·등록·답변·상태 변경은 문의 지점의 유효 소속이면 누구나 한다. 담당자 변경은 현재 담당자 또는 해당 지점 MANAGER 이상이며, 담당자가 없으면 MANAGER 이상만 한다. 담당자를 해제(`null`)하는 것도 같은 권한이다. 담당자가 바뀌면 이전 담당자의 변경 권한은 사라진다.
- **답변**: 답변·답변자·시각을 저장하고 상태를 `답변 완료`로 바꾼다. 다시 답변하면 답변을 교체하며 **이전 답변 원문**을 새 이력 행의 `message`에 남긴다. 첫 답변은 `message`가 null이다.
- **상태 변경**: `접수`·`처리 중`만 받고 `답변 완료`는 422다. 답변 완료에서 처리 중·접수로 돌려도 답변·답변자·시각은 유지한다. 같은 상태 요청은 version·이력 없이 현재 값을 돌려준다(업무와 같은 규칙).
- **이력**: 등록(`oldStatus` null), 상태 변경, 답변, 담당자 변경마다 한 행이다. 담당자 변경은 두 상태가 같고 `message`가 `담당자: 이전 → 새 담당자`(없으면 `없음`)다. 이름은 변경 시점 값을 문장으로 남긴다. 담당자가 이미 그 사람이면 이력을 만들지 않는다.
- **version**: 모든 명령이 문의 행을 잠근 뒤 version을 확인한다. 같은 version으로 경합한 명령은 하나만 성공한다.
- **`version` 외 항목 없는 수정**: 문의의 수정 operation(담당자·답변·상태)은 각각 필수 항목(`assigneeId`, `answer`, `status`)이 있고 제목·내용 수정 API가 없다. 필수 항목이 없거나 알 수 없는 필드가 있으면 기존 모듈과 같이 422(`VALIDATION_FAILED`)다. 업무의 `IMMUTABLE_FIELD` 규칙은 이 operation들에 해당하는 변경 대상이 없어 쓰지 않았다.
- **샘플 경로**: `LocalPreviewController`의 `inquiries` 샘플 경로(목록·상세·쓰기 거부)를 뺐다. 실제 컨트롤러와 경로가 겹쳐 모호한 매핑이 된다. 홈 샘플 데이터의 `inquiries` 자원 이름은 M9 홈이 아직 샘플이라 그대로 뒀다.

## 4. 구현 내용

- `modules/inquiry`: entity 4개(`Inquiry`, `InquiryEvent`, 상태·경로 enum), repository 3개(`InquirySearchRepository` 포함), `InquiryService`, `InquiryInputs`, `InquiryFilters`, `InquiryController`, 응답 DTO 5개
- `CustomerService.requireInquiryTarget`과 `CustomerServiceInteractionRepository.existsByCustomerIdAndBranchIdAndEmployeeId`: 문의 대상 고객 확인 진입점. 조회 근거 기록 문구와 `recordLookup`은 바꾸지 않았다.
- `WorkspaceEventService`: `inquiries` 알림 매핑. 쓰기마다 같은 트랜잭션에서 outbox 행을 쌓는다.
- `LocalPreviewController`: `inquiries` 샘플 경로 제거
- 계약 문서: 문의 operation 8개를 `implemented`로 바꾸고 구현 상태 문장을 갱신했다. 계약 내용은 바꾸지 않았다.
- 감사(`audit_events`)는 남기지 않았다. 문의 변경은 `inquiry_events`가 작업자·전후 상태를 모두 담는다.

마이그레이션은 없다.

## 5. 검증 결과

- 신규 `InquiryIntegrationTests` 24개를 HTTP와 MySQL(Testcontainers)로 실행해 모두 통과했다. 정확 일치 조회는 실제 `POST /api/customer-lookups/check-in`으로 기록을 만들어 확인했다.
  - 등록·답변: 지점 직원이 등록하고 다른 직원이 답변, 응답에 연락처·이메일·메모가 없고 고객은 `id`·`memberNo`·`name`만 있음(등록·상세·목록·이력 원문 검사)
  - 범위: 다른 지점은 목록·수치에 없고 상세·이력·답변·상태·담당자 변경이 404, 범위 밖 지점을 지정하면 403, 소속 회수 직후 404
  - 대상 고객: 조회 범위 안(허용), 정확 일치 기록 있음(허용, 이후에도 고객 상세·목록은 404), 둘 다 없음(404, 행·멱등 기록 없음), **다른 직원의 기록으로는 404**, **다른 지점에서 한 조회로는 404**, 소속 없는 OWNER(허용)와 존재하지 않는 ID(404)
  - 담당자: 담당자 없음(일반 직원·등록자 403, MANAGER·OWNER 허용), 담당자 있음(담당자 허용·다른 직원 403·이전 담당자 403), 해제, 다른 지점·소속 없는 OWNER·없는 ID·소속 회수·계정 정지는 422 `INVALID_ASSIGNEE`(등록 때도 동일)
  - 답변: 상태 변경·답변자·시각 저장, 재답변 시 교체와 이전 답변 원문 보존, 처리 중으로 되돌려도 답변 유지, 다시 답변하면 그 답변도 이력에 보존
  - 상태: `답변 완료` 요청 422, 같은 상태는 이력 없음, 처리 중·접수 전이
  - 이력: 등록·상태·담당자·답변이 최신순으로 쌓이고 담당자 변경은 두 상태가 같음, 페이지
  - 수치: 지점 범위 3종 × 필터 7종(담당자·고객·검색어 등)에서 전체·접수·처리 중·답변 완료·미처리가 같은 필터 목록 total과 일치하고 지점별 합이 합계와 같음
  - 버전 충돌(`latestVersion`·`reloadUrl`, 저장 안 됨, 권한 오류가 충돌보다 먼저), 멱등 재요청(재생·다른 입력 409), 입력 검증
  - 실제 동시 실행: 같은 version으로 6명이 동시에 답변(1건 성공·5건 409, 이력 1건 추가), 답변과 담당자 변경의 경합(1건 성공·1건 409, 진 쪽은 다시 읽어 성공), 같은 키로 6건 동시 등록(문의 1개·이력 1개·멱등 기록 1개)
- 변경 검증: 정확 일치 확인을 일시적으로 항상 통과하게 바꾸면 대상 고객 테스트 4개가 실패함을 확인한 뒤 원래대로 되돌렸다.
- `./gradlew test` 전체 결과: 54개 suite, 530개 테스트 통과(실패·오류·건너뜀 0). 이전 전체 506개에 이번 문의 테스트 24개가 더해진 수치다.

## 6. 남은 작업 / 보류 사항

- Frontend #26~#28: 문의 화면을 이 API에 연결한다. 현재 화면은 샘플 모양(`title`, `memberId` 등)이다.
- 계약이 정하지 않아 정한 동작(PR 본문에도 적는다)
  - 조회 근거 기록에는 유효 기간이 없다. 한 번 찾은 고객은 같은 지점·같은 직원이 계속 문의 대상으로 지정할 수 있다. 기간 제한이 필요하면 별도 결정이 필요하다.
  - 일반 조회 범위 판정은 요청 `scope`가 아니라 요청자의 전체 범위로 한다.
  - 첫 답변은 이력 `message`가 null, 등록 이력의 `message`는 접수 경로와 담당자를 설명하는 문장이다. 상태 변경 이력의 `message`는 null이다.
  - 같은 담당자·같은 상태로의 요청은 no-op이며, `답변 완료` → `접수`로 되돌리는 것도 허용한다. 계약의 `INVALID_STATE`(409)는 이 operation에서 쓸 전이가 없어 발생하지 않는다.
  - 목록 `q`는 제목과 고객 이름을 찾는다(내용은 찾지 않는다).
- 홈(M9)의 미처리 문의 수치는 아직 샘플이다. 이 API의 summary를 재사용한다.
- 소속 행이 없는 OWNER는 담당자가 될 수 없다(업무·시설과 같음).
