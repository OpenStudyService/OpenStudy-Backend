# 2026-11-06 남은 Backend 이슈의 task 파일 분해

관련: [`docs/tasks/`](../tasks/README.md)

## 1. 배경 / 문제

OpenStudy-Backend에는 열린 이슈가 41개 있다. M1~M3의 잔여 운영 검증, M9~M10의 남은 구현, M11 릴리스 준비, M12~M15 확장 기능이 섞여 있다. 이슈마다 선행 관계가 본문 「의존성」·「선행 이슈」 섹션에 흩어져 있어서 지금 무엇부터 착수할 수 있는지, 이슈별로 실제로 남은 일이 무엇인지 한 번에 보기 어려웠다.

사용자는 Tasks.md 한 파일에 모두 적지 말고 작업을 분해해 개별 task 파일로 만들되, 위치는 `docs/tasks/`, 정리 기준은 착수 순서로 해 달라고 요청했다.

## 2. 검토한 선택지

- **파일 단위**
  - 이슈를 더 잘게 쪼개 여러 task 파일로 나누는 안: 이슈가 이미 PR 하나로 끝낼 수 있는 단위로 나뉘어 있어서, 더 쪼개면 이슈·PR과 task의 대응이 흐려진다.
  - 열린 이슈 1개 = task 파일 1개, 파일 안에서 작업 단계를 분해하는 안: 이슈·PR·task가 1:1로 대응한다. 이쪽을 택했다.
- **인수 조건 체크리스트**
  - task 파일에 복사하는 안: 이슈와 task가 따로 갱신되면서 어긋날 위험이 있다. AGENTS.md도 기존 문서와 중복되는 상세 내용은 링크로 연결하라고 정한다.
  - 이슈 링크와 진행 수치(완료 / 전체, 조회 날짜)만 두는 안: 이쪽을 택했다. 이슈를 진실의 원천으로 유지한다.
- **목록 구성**: 마일스톤별 나열과 착수 순서 분류를 비교했고, 사용자 선택에 따라 착수 순서(착수 가능 / 결정 대기 / 잔여 검증 / 선행 대기 / 최종 검증)로 나눴다. 마일스톤은 각 표의 열로 남겼다.

## 3. 결정 및 이유

- 일부만 남은 이슈(#10 #14 #17 #28)는 구현이 끝나고 운영 환경 검증만 남아 있어서, task 파일에는 남은 범위만 적고 완료된 부분은 기존 개발 기록 링크로 대신했다.
- 분류는 이슈 본문의 선행 이슈 상태로 판단했다. 마일스톤 단위로 적힌 선행(예: "M4 결제 결과")은 그 결과를 만드는 구체 이슈에 대응시켰다.
- 착수 가능 목록은 후속 작업을 많이 풀어 주는 순서로 정렬했다. #92는 M10 전체와 M15의 선행이라 1순위로 두었다.
- #29는 Infra#2(열림)와 계약을 맞춰야 하지만, Infra#2가 오히려 #29의 실행 이미지를 기다리는 관계라 착수 가능으로 분류했다.
- #103의 선행인 Infra#1은 종료돼 착수 가능으로 분류했다.
