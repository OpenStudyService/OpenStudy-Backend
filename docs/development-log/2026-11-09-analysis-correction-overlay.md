# 2026-11-09 AI 근무시간 분석의 정정 이중 반영 수정 (#197)

## 1. 배경 / 문제

- AI 분석 POC-010("지난주 직원별 근무시간을 비교해줘")은 직원별로 원본 실근무 분(`raw_work_minutes`)과 승인된 정정을 반영한 분(`illustrative_corrected_minutes`), 그 차이를 보여 준다.
- 기존 코드는 정정 승인이 근태를 바꾸지 않는다는 가정 위에 있었다. 그래서 근태 행을 원본으로 보고, 승인된 출퇴근 정정의 `after_*` 값을 덮어써 보정 후를 계산했다.
- #107(PR #196)부터는 승인할 때 근태·휴게 행 자체가 바뀐다. 그 결과 세 가지 문제가 생겼다.
  - 원본이 이미 정정된 값이 된다.
  - 한 근태에 승인된 출퇴근 정정이 여러 건이면, 정렬 없는 질의에서 마지막으로 읽힌 정정 값으로 덮어쓴다.
  - 휴게 정정은 반영하지 않는다.
- #107 작업 중 발견해 범위 밖으로 남겼던 문제다(`2026-11-09-attendance-corrections.md` 6절).

## 2. 검토한 선택지

착수 전에 사용자에게 물었다. 걸림돌은 외부 DomainLens 골든 시드(`openstudy-domainlens-handoff/04_TEST_DATA/seed_data.sql`)였다. 이 시드의 승인된 출퇴근 정정 1건은 `before_*`가 비어 있고 근태 행도 바뀌지 않은, #107 이전 형식이다. 골든 기대값은 이 행으로 5분 차이를 기대한다.

- **원본 복원 + 옛 행 호환**: 보정 후는 현재 근태로 계산한다. 원본은 가장 먼저 승인된 정정의 `before_*`로 복원한다. `before_*`가 없는 옛 승인 출퇴근 정정만 지금처럼 `after_*`를 덮어쓴다. 골든 5분 차이가 유지된다.
- **원본 복원만**: 코드는 단순하다. 하지만 골든 시드와 맞지 않아 골든 기대값이나 외부 시드를 따로 고쳐야 한다.
- **비교 제거**: 원본과 보정 후를 모두 현재 근태로 계산해 차이를 항상 0으로 만든다. 응답 열은 남지만 비교 의미가 사라진다.

## 3. 결정 및 이유

- **원본 복원 + 옛 행 호환**(2026-11-09 사용자 결정, 추천안 채택)
  - #107 이후 정정 행은 `before_*`(신청 시점의 근태 값)를 항상 저장한다. 따라서 가장 먼저 승인된 정정의 `before_*`가 정정 전 원본이다. 승인 순서는 `decided_at`, `id` 오름차순이다.
  - 휴게도 같은 규칙을 따른다. 휴게별로 가장 먼저 승인된 휴게 정정의 `before_break_*`가 원본 구간이다.
  - 옛 행 호환은 출퇴근 정정에만 둔다. 기존 코드가 출퇴근만 덮어썼고, 시드에도 옛 형식 휴게 정정은 없다. 옛 행이 여러 건이면 가장 나중에 승인된 값을 쓴다.
  - 외부 골든 시드와 기대값은 고치지 않는다. 백엔드 저장소 밖의 인계 자료이기 때문이다.
- POC-010의 안내 문구와 상태(`PROVISIONAL_NOT_GOLDEN`, `POLICY_PENDING_ATTENDANCE_CORRECTION_AGGREGATION`)는 바꾸지 않았다. 분석 계약과 골든 비교가 이 값을 쓰므로 이번 범위에서 제외했다.

## 4. 구현 내용

- `OpenStudyAnalyses.executePoc010WeeklyAttendance`
  - 승인된 정정을 종류와 상관없이 승인 순서대로 읽는다.
  - 출퇴근 정정은 원본 출퇴근(첫 `before_*`)과 옛 행 덮어쓰기 값(마지막 `after_*`)으로 나눠 모은다.
  - 휴게 정정은 휴게 ID별 원본 구간(첫 `before_break_*`)으로 모은다.
  - 휴게는 ID와 함께 읽는다. 현재 구간 합계는 보정 후에, 원본 구간 합계는 원본에 쓴다.
  - 원본 = 원본 출퇴근 − 원본 휴게. 보정 후 = 현재 출퇴근(옛 행은 덮어쓰기) − 현재 휴게.
- `CorrectionIntegrationTests`에 POC-010 시나리오 테스트 1개를 더했다.

## 5. 검증 결과

- 새 통합 테스트 `theWeeklyWorkAnalysisComparesTheOriginalAttendanceWithTheApprovedOne`(MySQL Testcontainers)이 통과했다.
  - 정정 API로 출퇴근 2회와 휴게 1회를 승인한 근태: 원본 480분(09:00~18:00, 휴게 60분), 보정 후 570분(08:00~18:00, 휴게 30분), 차이 90분.
  - 옛 형식 승인 정정(`before_*` 없음)이 있는 근태: 원본 480분, 보정 후 485분.
  - 정정 없는 근태: 원본과 보정 후가 같다.
- 수정 전 코드로 같은 테스트를 돌리면 원본이 570분으로 나와 실패했다(480 기대). 테스트가 결함을 잡는 것을 확인했다.
- `CorrectionIntegrationTests` 9개가 모두 통과했다.
- 전체 `./gradlew test`: BUILD SUCCESSFUL(16분 49초). 1,070개 실행, 실패 0, 건너뜀 26(기존과 같은 건너뜀 수, 골든 테스트 포함).

### 검증하지 못한 항목

- 골든 테스트 `OpenStudyGoldenAggregationsIntegrationTests`는 실행하지 않았다. 로컬 AI 모델과 `OPENSTUDY_AI_LOCAL_TESTS`, 3307 포트의 시드 DB가 있어야 실행된다. 옛 행 호환으로 기존 계산(5분 차이)이 유지되도록 했지만 실제 실행으로 확인하지는 않았다.
- 실제 AI 화면에서 질문해 확인하지 않았다.

## 6. 남은 작업 / 보류 사항

- POC-010의 "정정 반영 정책 확정 전" 안내와 `needs_decision`의 "approved clock correction effect on effective attendance" 항목은 M12에서 사실상 결정됐다(승인 때 근태 변경). 안내 문구와 골든 상태를 바꿀지는 별도 판단이 필요하다.
- 외부 골든 시드를 #107 형식(`before_*` 저장, 근태 행 갱신)으로 바꾸면 옛 행 호환 코드를 지울 수 있다.
