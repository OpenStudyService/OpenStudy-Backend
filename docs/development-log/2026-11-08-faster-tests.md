# 2026-11-08 백엔드 테스트 실행 시간 단축

## 1. 배경 / 문제

- 전체 `./gradlew test`(998개)가 40~44분 걸렸다. 다른 세션의 전체 테스트와 겹친 날은 1시간 30분이 걸리고, 테스트 DB 연결이 끊겨 12개 클래스가 연쇄 실패했다(#90 개발 기록).
- 저장소에 CI가 없어 PR마다 로컬에서 전체를 한 번 돌린다. 이 시간이 작업 흐름을 막았다.
- 마지막 실행(2026-11-08, 40분 35초)의 테스트 결과 XML로 시간을 나눠 보았다.
  - 테스트 본문 합계 약 34분, 테스트 하나의 중앙값 1.9초
  - Spring 컨텍스트 기동: 23개, 합계 약 6분
  - `MySqlTestConfiguration`이 MySQL 컨테이너를 컨텍스트별 Bean으로 만들어, 컨텍스트마다 MySQL을 새로 띄우고 마이그레이션을 다시 돌렸다. 23개가 JVM 종료까지 모두 떠 있었다.
- 테스트 본문이 느린 이유는 비밀번호 해시로 판단했다.
  - `PasswordEncoder`가 운영과 같은 BCrypt 강도 12다(1회 약 0.25~0.4초).
  - 픽스처가 테스트마다 직원을 만들며 해시를 만들고(예: 채널 테스트는 9명), 로그인할 때 다시 검증한다.

## 2. 검토한 선택지

- **해시 비용**
  - 테스트 프로필에서만 강도를 낮추는 설정값: 운영 기본값은 그대로이고 테스트 코드는 고칠 필요가 없다.
  - 픽스처에서 미리 만든 해시 상수를 쓰기: 픽스처 파일이 많고(52곳) 로그인 검증 비용은 그대로 남는다.
- **MySQL 컨테이너**
  - JVM 전체에서 컨테이너 1개를 공유: 기동·마이그레이션이 한 번이고 동시 실행 때 자원 부담이 작다. 대신 컨텍스트 사이에 DB를 공유한다.
  - 테스트 병렬 실행(Gradle fork 여러 개): 지금 구조에서는 fork마다 컨테이너가 늘어 자원 문제가 커진다. 이번에는 하지 않았다.

## 3. 결정 및 이유

- 두 가지를 모두 적용했다.
  - 해시: `openstudy.security.bcrypt-strength`(기본 12)를 두고 `application-test.yaml`에서만 4로 낮췄다. BCrypt 해시는 비용을 해시 안에 담고 있어, 어떤 비용으로 만든 해시든 검증된다. 테스트 대상 동작은 바뀌지 않는다.
  - 컨테이너: 정적 컨테이너 하나를 모든 컨텍스트가 쓴다.
    - 같은 컨텍스트 안의 테스트 클래스들은 이미 DB를 공유하고 자기 행을 정리해 왔다. 그래서 컨텍스트 사이 공유도 테스트가 기대하는 조건을 바꾸지 않는다고 판단했다. 실제 전체 실행으로 확인했다(아래).
    - `destroyMethod = ""`로 한 컨텍스트가 닫혀도 컨테이너를 멈추지 않는다. 종료 후 정리는 Testcontainers 리퍼가 한다.
- 자체 컨테이너를 쓰는 테스트(마이그레이션·초기화·인증 등 7개 클래스)는 그대로 뒀다. 빈 DB나 별도 설정이 필요한 테스트다.

## 4. 구현 내용

- `SecurityConfiguration.passwordEncoder`: 강도를 설정값으로 받는다(기본 12).
- `application-test.yaml`: `openstudy.security.bcrypt-strength: 4`
- `MySqlTestConfiguration`: 정적 공유 컨테이너, `@Bean(destroyMethod = "")`
- `CustomerHistoryIntegrationTests`: 응답 전체 문자열에서 방 예약 ID(`7"` 같은 짧은 문자열)를 찾던 단언을, 예약 ID 목록 비교로 바꿨다.
  - 이 단언은 2026-11-07에도 한 번 실패했다(#90 개발 기록).
  - DB를 공유하면 ID 값이 커져 다른 숫자 안에 우연히 걸릴 가능성이 높아졌다. 원래부터 불안정한 단언이라 의도(다른 지점 예약이 없음)대로 고쳤다.

## 6. 남은 작업 / 보류 사항

- 테스트 병렬 실행은 하지 않았다. 공유 DB에서 병렬로 돌리려면 테스트 사이 데이터 격리를 먼저 점검해야 한다.
- CI가 없다. PR마다 GitHub Actions로 전체 테스트를 돌리면 로컬 대기를 없앨 수 있다. 별도로 결정할 일이다.
