# 2026-11-06 · 명시적 화면 갱신 정책 기록

## 배경 / 문제

SSE를 제거하고 화면을 안정적으로 유지하자는 사용자 의사결정을 SRS·설계·인수 조건에 남겨야 했다. 기존 문서와 열린 이슈에는 SSE 재연결·운영 heartbeat·다른 세션 권한 회수 즉시 화면 정리가 필수로 남아 있어 같은 정책으로 해석할 수 없었다.

## 검토한 선택지

SSE 유지, polling 교체, 사용자 행동에 따른 명시적 갱신을 검토했다. 즉시 변경 전파보다 업무 화면 안정성과 연결·타이머 관리 단순성을 우선해 마지막 방법을 확정했다.

## 결정 및 이유

- SSE·화면 상태 polling과 창 포커스/네트워크 복구에 따른 자동 조회를 사용하지 않는다. 메뉴 진입·재클릭·새로고침·사용자 조건 변경으로 서버에서 읽는다.
- 본인 저장 성공은 관련 화면에 반영하고 조건·미저장 입력·마지막 조회 시각을 유지한다. 다른 세션의 변경은 다음 명시적 조회 때 보인다.
- 서버의 현재 계정·권한·소속·세션·CSRF·거래 상태·금액·버전·중복 검증은 유지한다. 권한 회수 다음 API 차단과 감지 후 비공개 상태 정리를 요구하며 요청 없는 화면 즉시 삭제는 보장하지 않는다.
- AI는 JSON 요청·응답을 쓰고 중복·제한 시간·취소 계약·늦은 응답 보호를 유지한다. SMTP 재시도·감사·로컬 시계 등은 별개다.

## 구현 내용

이번 작업은 문서 변경이다. 정책 확정과 실제 코드 제거를 분리하고, 이전 개발 기록·ADR 원문·이슈의 완료 증거는 보존했다. 실행 코드·OpenAPI·생성 타입·DB는 변경하지 않았다. Outbox DROP도 결정하지 않았다.

기존 작업을 건드리지 않도록 최신 원격 main에서 독립 worktree와 `docs/explicit-refresh-policy` 브랜치를 만들었다. 기존 Backend AI 대화 작업과 Frontend의 사용자 파일은 스테이징하지 않는다.

SRS v1.15 POL-52·53과 [ADR-COM-001](../db/ADR-COM-001.md)을 근거로 기반 정책·API·DB·조회 추적·개발 계획, 인증·배포 안내와 M10/M14 후속 결정을 연결했다. 공통 의사결정 등록표와 DB 문서 진입점에서도 새 결정을 찾을 수 있게 했다.

## 검증 결과

- `git diff --check` 통과. 변경은 Markdown 문서만이며 실행 코드·기계 API 계약 변경은 없다.
- 추가한 상대 문서 링크의 실제 대상과 정책·구현 이슈 연결을 확인했다. 기존 SSE 계약은 현재 구현 설명/과거 근거로 구분했다.
- 런타임 테스트·빌드·운영 HTTPS 검증은 실행하지 않았다(문서만 변경).
