# 2026-11-13 생성 경로 질문 의도 분석과 일반 지표 (#232 1단계)

## 1. 배경 / 문제

- 0단계([2026-11-13-domainlens-engine-check.md](2026-11-13-domainlens-engine-check.md))에서 실제 Qwen이 낸 계획("이번 달 지점별 매출")이 맞았는데도 서버가 거절했다. 남은 원인은 상대 기간이었다. 서버 컴파일러는 모델이 계산한 "이번 달" 날짜 범위를 믿지 않고, OpenStudy가 서버 시계로 확정한 기간만 근거로 인정한다. OpenStudy에는 그 분석기(`QueryIntent.Analyzer`)가 없었다.
- 카탈로그 지표 10개는 모두 등록 분석에 묶여 있었다. 그중 `sales.net_sales_krw`(순매출)는 생성 경로에서 결제 금액 단순 합계로 실행돼, 실패한 결제까지 더하고 환불도 빼지 않는 잘못된 수치를 냈다.
- 그 밖에 데모 하드코딩이 남아 있었다. 기간 허용 범위가 2026년 한 해로 고정돼 있었고(`OpenStudyClock.VALID_DATA_RANGE`), 지점 별칭에 데모 지점 이름(강남점 등)과 코드(OSDEMO-*)가 들어 있었다.

## 2. 검토한 선택지

- **순매출을 생성 경로에서 어떻게 다룰지**
  - 순매출 지표에 기본 필터를 붙여 생성 경로에서도 쓴다: 승인 상태는 거를 수 있지만, 환불 차감은 다른 원천(refund)이라 지표 하나로 표현할 수 없다.
  - 등록 분석에 묶인 지표는 생성 경로의 집계로 실행하지 않고, 생성 경로에는 의미가 정확한 일반 지표를 따로 둔다(선택). "매출" 질문은 이미 등록 분석이 먼저 처리한다(2026-11-13 결정: 등록 분석 우선).
- **상대 기간 처리**
  - 모델이 계산한 기간을 그대로 믿는다: 엔진의 원칙(M10-D07, 서버 재검증)에 어긋난다.
  - OpenStudy가 서버 시계로 기간을 확정하고, 모델 계획을 그 값과 대조한다(선택).
- **환불 지표**: 환불(refund)에는 지점 열이 없어 지점 범위 행 필터를 걸 수 없다. 1차에서 제외했다.

## 3. 결정 및 이유

- 등록 분석에 묶인 지표(`implementationRef`가 등록 분석 ID)는 생성 경로의 AGGREGATE 쿼리에서 거절한다(`IrValidator`). 단순 합계가 등록 분석의 정의(환불 차감 등)와 다른 뜻이 되기 때문이다.
- 생성 경로용 일반 지표 3개를 추가했다. 이름과 업무 용어를 계산 내용 그대로 붙였다. "매출" 단독 표현은 등록 분석(순매출)에 남겼다.
  - `sales.approved_amount_krw` 결제 승인액: 승인된 결제 금액 합계
  - `sales.approved_count` 결제 건수: 승인된 결제 수
  - `passes.issued_count` 이용권 발급 수
- 질문 의도 분석기(`OpenStudyIntentAnalyzer`)는 보수적으로 읽는다. 일반 지표는 카탈로그 업무 용어로만 찾고(가장 긴 일치, 동률이면 미확정), 기간 표현이 둘 이상이면 기간을 비운다. 모호하면 채우지 않고 엔진이 확인 질문으로 돌린다.

## 4. 구현 내용

- `OpenStudyIntentAnalyzer`(신규)
  - 지표: 일반 지표의 업무 용어
  - 묶음: 지점별·매장별(지점명), 상품 구분별(결제 항목), 결제 상태별, 이용권 구분·종류별. 지표 원천에서 닿는 항목만
  - 기간: 오늘, 어제, 이번 주, 지난주, 이번 달, 지난달, 올해, 작년, 최근·지난 N일, YYYY년 M월. 서버 시계(KST) 기준. "부터 … 까지" 범위는 엔진 규칙에 맡긴다.
  - 정렬: 많은 순·높은 순 / 적은 순·낮은 순(묶음이 있을 때만)
  - `OpenStudyQueryPipelineFactory`가 파이프라인에 연결한다.
- 카탈로그(`OpenStudyCatalogConfiguration`)
  - 일반 지표 3개와 업무 용어, 지표별 기간 기준 항목(`PERIOD_FIELDS`)
  - `payment.paid_at`을 결제 생성 시각(`created_at`)에서 승인 시각(`approved_at`)으로 옮겼다. 매출 기간은 승인 시점 기준이다.
  - 지점명 별칭에서 데모 지점 이름, 지점 코드 별칭에서 데모 코드를 지웠다.
- 준비 상태(`AiReadiness`): 일반 지표는 등록 분석 연결 대신 기간 기준 항목이 있는지 확인한다.
- `OpenStudyClock.VALID_DATA_RANGE`: 2026년 한 해 → 2020-01-01~2100-01-01
- 엔진 수정
  - `QueryPipeline`: 분석기가 확정한 지표·묶음·기간 항목을 의미 검색의 필수 시드로 넣는다. 이전에는 공식(formula) 레지스트리가 있을 때만 넣어, "이번 달 지점별 결제 금액"에서 결제 승인액 지표가 검색 상위 8개 밖으로 밀렸다.
  - `PlanCompiler`: 기간 대조에서 같은 시각을 다른 표기(+09:00 / Z)로 쓴 값을 같은 값으로 본다. 실제 Qwen은 +09:00으로 썼다.
  - `IrValidator`: +09:00 같은 오프셋 표기 시각을 받는다(이전에는 Z 또는 오프셋 없는 표기만). 등록 분석 지표의 AGGREGATE 사용을 거절한다.
  - `JpaQueryExecutor`: 시각 필터를 `Instant` 매핑 속성에 `Instant`로, 문자열 필터를 enum 매핑 속성(`PaymentStatus`)에 enum으로 바인딩한다. 이전에는 둘 다 실행 시 타입 오류였다.

## 5. 검증 결과

- `DomainLensPipelineIntegrationTests`(11개, live 1개 건너뜀)
  - 실제 Qwen 계획(지점별·이번 달)을 결제 승인액 지표로 바꿔 재생했다. 모델이 쓴 +09:00 기간 그대로도, 기간 없이 서버가 확정한 기간으로도 실행되고, **이번 달 승인 결제만** 지점명별로 합산된다(100일 전 승인 결제·실패 결제 제외). DB 직접 합계와 같다.
  - 녹음된 원래 계획(순매출 지표)은 실행되지 않는다.
  - 등록 분석 지표를 쓴 생성 집계는 거절된다.
- `OpenStudyIntentAnalyzerUnitTests`(9개): 고정 시계(2026-11-13 12:00 KST)에서 기간·지표·묶음·정렬 해석
- `./gradlew test`로 AI·DomainLens·결제·지점·매출 모듈과 JPA 매핑 테스트: 176개 중 실패 0, 건너뜀 25(기존 로컬 픽스처·측정 테스트 24개, live Qwen 1개)
- **이번 변경으로 실제 Qwen을 다시 호출하지 않았다.** 재생 테스트는 0단계에서 기록한 실제 계획을 쓴다.
- 정형 매출 API와의 수치 대조는 하지 않았다. 일반 지표는 DB 직접 합계와 비교했다(#97에서 대조).

## 6. 남은 작업 / 보류 사항

- 실제 Qwen으로 "이번 달 지점별 결제 금액" 왕복 확인(토큰 사용, 사용자 확인 뒤)
- 환불 지표: 환불에 지점 범위를 걸 경로(원결제 조인 기준 행 필터)가 필요하다.
- 분석기 묶음 표현은 몇 가지뿐이다. 일별·월별 추이(날짜 단위 묶음)는 엔진이 날짜 절단 차원을 지원하는지부터 확인해야 한다.
- 업무 용어에 데모 질문 문장(예: "지금 강남점에 빈자리가 얼마나 있어")이 남아 있다. 등록 분석 검색 평가 테스트가 기대하는 값이라 이번에는 두었다.
- AI 채팅 연결은 #233에서 한다.
