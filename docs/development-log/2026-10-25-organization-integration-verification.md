# 조직 API 결합 및 live 브라우저 검증

## 배경 / 문제

B05 지점 API와 B06 직원·권한 API는 병렬 개발했다. 각 작업의 독립 테스트만으로 세션 정책 및 기존 F02 화면과의 결합을 확인할 수 없어 별도 검증 브랜치와 일회용 DB를 사용했다.

## 결정 및 이유

원격 main을 변경하지 않고 main 기반 로컬 `chore/organization-integration-check`에 세션 복구 PR #24, 지점 PR #25의 `469b0bb`, 직원 PR #26의 `f9a9dae`를 합쳤다. migration·OWNER 초기화와 실제 쿠키/CSRF 요청을 확인하기 위해 MySQL 8.4.11 일회용 컨테이너 및 MSW가 꺼진 live 프론트를 실행했다. 사용자 DB와 기존 체크아웃의 변경은 사용하지 않았다.

## 검증 결과

- Java 21에서 `test bootJar` 성공: 전체 103개, 실패·오류·건너뜀 0. 새 두 API와 복구한 세션 변경의 결합은 소스 충돌 없이 빌드됐다.
- 빈 DB의 V1~V3 migration 후 별도 `ownerBootstrap` 명령으로 테스트 OWNER 생성, 실제 브라우저 로그인 성공.
- OWNER가 두 지점을 등록하고 월요일 20:00~익일 02:00 운영시간과 7요일 데이터를 실제 HTTP/DB로 저장·조회했다.
- 테스트 직원·관리자 계정 및 두 지점 소속은 검증용 SQL로 준비했다. 초대 수락으로 생성한 직원이라고 주장하지 않는다.
- F02 직원 상세에서 첫 지점 권한 저장 후 SQL로 첫 지점의 version 증가와 `operations:write`, 두 번째 지점의 기존 version·빈 권한 보존을 확인했다.
- 두 브라우저 화면의 동시 편집에서 낡은 version은 409를 반환했다. 화면의 매출 조회 입력, 오류 요청 ID, 최신 버전 확인 동작이 유지됐다.
- 일반 직원에게 지점 등록/수정 및 직원 관리 메뉴가 제공되지 않았다. OWNER가 한 지점 소속을 회수한 뒤 직원의 해당 지점 새 요청은 접근 차단 화면을 표시했다.
- 계정 전체 상태 제한 후 기존 직원 세션은 로그인 화면으로 이동했다. MANAGER 자신의 권한 수정과 계정 공통 편집은 UI에서 차단됐다. 직접 HTTP 인가 우회·경합은 B05/B06 통합 테스트로 검증했다.

## 발견한 문제 및 후속 작업

같은 직원 상세 창 안에서 소속 저장 후 다른 폼을 저장하면 자기가 저장한 새 계정 version을 공유하지 못해 불필요한 409가 발생했다. 충돌 복구 버튼으로 실제 제한 저장과 세션 차단은 확인했으며, UI 버전 공유 보완은 별도 frontend `fix/employee-editor-versions`에서 추적한다. 외부 화면의 실제 충돌 감지와 미저장 입력 보존은 유지해야 한다.

## 남은 작업 / 보류 사항

lookups·SSE 구현 전이므로 공통 정보 미제공 안내가 표시됐다. B11의 열린 스트림 종료·즉시 캐시 회수 및 프록시/TLS는 이 결과에 포함하지 않는다. 초대·메일·상품 및 전체 V01은 선행 구현 이후 별도 검증한다. 관련 작업 브랜치는 push와 PR로 제공하며 main 병합은 사용자가 수행한다.
