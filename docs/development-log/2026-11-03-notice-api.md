# 2026-11-03 공지 등록·수정·게시 종료와 대상 지점 노출 API

관련: Issue [#80](https://github.com/OpenStudyService/OpenStudy-Backend/issues/80), [계약 문서](../design/foundation/collaboration-api.md), [ADR-M7-001](../db/ADR-M7-001.md) M7-D04, [문의 API 기록](2026-11-03-inquiry-api.md).

## 1. 배경 / 문제

전체·지점 공지를 게시하는 화면이 로컬 샘플로만 동작했다. `modules/notice`가 비어 있었기 때문이다. #74 계약이 병합되고 업무(#75)·시설(#78)·문의(#79)가 구현되어 공지 operation 5개를 구현할 수 있게 됐다.

공지에서 조심한 부분은 두 가지다.

- **대상이 여러 지점**이다. 한 지점의 권한만으로는 관리 여부를 판단할 수 없고, 응답이 다른 지점의 ID를 드러내면 안 된다.
- **게시 상태가 노출을 좌우**한다. 임시 저장·게시 종료 공지가 일반 직원에게 보이거나, 게시 종료된 고정 공지가 목록 위로 오면 안 된다.

## 2. 검토한 선택지

- **여러 지점의 권한 확인**: 기존 `AuthorizedCommands.inBranches`는 호출 전에 지점 집합을 알아야 한다. 수정·상태 변경은 대상 지점을 공지 행을 잠근 **뒤에** 읽어야 최신 값이라, 그 시점에 지점 집합을 받는 `inAnyBranch`(대상 중 하나라도 권한이 있으면 통과, OWNER는 항상 통과)로 가드와 잠금 순서를 얻고, 콜백 안에서 같은 상태로 "대상 **모두**" 규칙을 다시 검사했다. 가드·잠금 순서는 기존 모듈과 같고 공통 코드는 바꾸지 않았다.
- **대상 지점 매핑**: `announcement_branches`를 `@ElementCollection`으로 매핑했다. 별도 엔티티는 행 하나짜리 껍데기가 되고, 목록에서는 어차피 엔티티 컬렉션 대신 한 번의 조회로 대상을 가져온다.
- **목록의 가시성 판단**: 목록과 total이 같은 조건이어야 하므로 문의처럼 한 repository에서 WHERE를 조립했다. 가시성(범위·게시 상태·관리 가능 여부)을 SQL에 넣어 페이지 뒤에서 걸러내지 않는다.
- **알림 전달**: 기존 outbox는 지점 하나당 행 하나이고 스트림은 자기 범위의 지점 행만 받는다. 이 구조를 그대로 써서 대상 지점마다 행을 쌓았다. 전체 공지는 시설 유형·상품 분류와 같은 `invalidateEveryBranch`를 썼다. 새 outbox 구조는 만들지 않았다.

## 3. 결정 및 이유

- **관리 권한**
  - 전체 공지는 OWNER만, 지점 공지는 대상 지점 **모두**에 `notices:write`가 있어야 한다. 등록·수정·상태 변경이 같은 규칙이다. 지점 MANAGER 역할만으로는 부족하고 권한도 필요하다(계약: `notices:write`는 명시한 곳에서만 요구, 공지는 명시됨).
  - `PATCH`가 대상을 바꾸면 현재 대상과 변경 후 대상 **둘 다** 확인한다. 대상이 같으면 한 번만 확인한다.
  - 지점이 운영 중지여도 허용한다(계약: 내부 협업은 신규 운영 거래가 아님).
- **공개 범위**: 요청한 `scope`(기본 전체)의 지점에 닿는 공지만 본다. 닿는다는 것은 전체 대상이거나 대상 지점 중 하나가 scope에 있다는 뜻이다. 그 안에서
  - 게시 중이면 누구나 본다.
  - 임시 저장·게시 종료는 관리할 수 있는 사람만 본다(전체 대상은 OWNER, 지점 대상은 모든 대상 지점에 권한). OWNER는 scope 안의 모든 공지를 본다.
  - 볼 수 없으면 상세·수정·상태 변경이 모두 404다. 게시 중이라 보이지만 관리 권한이 없으면 403이다. 즉 "보이지 않음"이 "권한 없음"보다 먼저다.
  - 가시성은 가드 전에 한 번(404), 잠금 후 최신 권한으로 다시 판단한다. 소속·권한이 회수되면 즉시 반영된다.
- **`branchIds`**: 대상 중 요청자가 읽을 수 있는 지점만 오름차순으로 담는다. 전체 공지는 빈 배열이다. 쓰기 응답과 멱등 재생 응답도 같은 규칙이다. 관리할 수 있는 사람은 모든 대상 지점을 볼 수 있으므로 `PATCH`로 대상을 통째로 교체해도 숨은 지점을 지우지 않는다.
- **상태 전이**: 임시 저장→게시 중, 게시 중→게시 종료, 게시 종료→게시 중만 허용한다. 그 외는 409 `INVALID_STATE`, 같은 상태는 현재 값(버전 변경 없음)이다. 게시할 때 `publishedAt`을 기록하고, 게시 종료는 값을 지우지 않아 목록의 위치를 유지하며, 재게시는 새 시각이다. 등록 때 `status`는 임시 저장·게시 중만 받는다.
- **정렬**: `pinned` → `COALESCE(published_at, created_at)` → `id` 내림차순. 가시성 조건을 WHERE에 넣은 뒤 정렬하므로 일반 직원 목록에서 게시 종료된 고정 공지는 아예 없다. total도 같은 조건이다. 정렬·방향 쿼리 파라미터는 계약에 없어 받지 않는다.
- **검증 순서**: 입력 검증(422) → 가시성(404) → 가드·잠금 → 현재 권한(403) → 새 대상 권한(403) → version(409) → 대상 조합 검증. 권한이 없는 사람이 version 충돌로 공지의 최신 상태를 알아내지 못한다.
- **`PATCH` 규칙**: `version`만 있으면 422(`VALIDATION_FAILED`), `status`가 있으면 422(`IMMUTABLE_FIELD`), 알 수 없는 필드는 422다. 전체 대상에 `branchIds`를 보내거나 전체 공지에 `target=선택 지점`만 보내는 것도 422다. 바뀌는 값이 없는 요청은 버전·감사·알림 없이 현재 값을 돌려준다(시설과 같음).
- **없는 지점 ID**: 권한이 없는 지점과 같은 403이다. OWNER도 같다(소유자 권한 판단이 `branches` 목록 기준이라 없는 지점은 권한 없음으로 평가된다). 지점이 존재하는지가 응답 차이로 드러나지 않는다.
- **멱등 키**: `scopeKey`를 대상과 무관한 고정 값으로 두어, 같은 키에 다른 입력(다른 대상 포함)은 `IDEMPOTENCY_CONFLICT`가 된다. 재생은 권한 확인 **뒤에** 해서 권한을 잃은 요청자가 이전 응답을 받지 못한다.
- **알림**
  - 대상 지점마다 `invalidate` 행 하나(대상이 바뀌면 이전·새 대상의 합집합)이고, 전체 공지는 모든 지점 행이다.
  - 스트림은 이미 요청자가 접근할 수 있는 지점의 행만 보내므로, 다른 지점의 `branchId`는 가지 않는다.
  - **`notices`의 `entityId`는 보내지 않는다.** 임시 저장 공지는 관리자만 볼 수 있는데 알림은 지점의 모든 직원에게 가기 때문이다. 클라이언트는 목록을 다시 읽는다. 시설 유형과 같은 처리다.
  - 임시 저장 공지의 변경도 대상 지점 직원에게 "공지가 바뀌었다"는 신호는 간다. 내용·ID는 없다.
- **감사**: 등록·수정·상태 변경을 `audit_events`에 남긴다. 지점이 하나일 때만 `branch_id`를 채우고, 여러 지점이거나 전체면 null이다.
- **샘플 경로**: `LocalPreviewController`의 `notices` 샘플 경로(목록·상세·쓰기 거부)를 뺐다. 홈 샘플의 `notices` 자원 이름은 M9 홈이 아직 샘플이라 그대로 뒀다.

- `modules/notice`: `Notice` 엔티티(+ 상태·대상 enum), `NoticeRepository`(행 잠금), `NoticeSearchRepository`(가시성 포함 목록·대상 일괄 조회), `NoticeService`, `NoticeInputs`, `NoticeController`, 응답 DTO 3개

  - 상태 전이: 허용 3개와 거부 3개(409 `INVALID_STATE`), 같은 상태, 알 수 없는 상태 422, `publishedAt` 기록·유지·갱신, 감사 행 수

## 6. 남은 작업 / 보류 사항

- Frontend #26~#28: 공지 화면을 이 API에 연결한다. 현재 화면은 샘플 모양이다.
- 계약이 정하지 않아 정한 동작(PR 본문에도 적는다)
  - 목록·상세는 `scope`에 닿는 공지만 보여 준다. OWNER도 `scope`를 지정하면 그 지점 대상이거나 전체 대상인 공지만 본다. `scope=all`이면 모든 공지다.
  - 목록 `q`는 제목만 찾는다(본문은 찾지 않는다). 정렬 파라미터는 받지 않는다.
  - 같은 상태 요청도 `version`을 먼저 확인한다(문의와 같음). 낡은 version이면 같은 상태여도 409다.
  - 없는 지점 ID는 OWNER에게도 403이다.
  - 알림의 `entityId`를 비운다. 이유는 위 결정 참고.
  - 임시 저장 공지의 변경도 대상 지점 직원의 알림 스트림에 "공지 변경" 신호(ID 없음)를 보낸다. 임시 저장일 때 관리자에게만 보내려면 outbox에 수신 조건이 필요해 이번에는 하지 않았다.
- 공지 읽음 확인과 삭제는 범위 밖이다.
- 홈(M9)의 공지 영역은 아직 샘플이다.
