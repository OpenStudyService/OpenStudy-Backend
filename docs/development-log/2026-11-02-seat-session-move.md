# 2026-11-02 이용 중 좌석 이동 API

관련: Issue [#63](https://github.com/OpenStudyService/OpenStudy-Backend/issues/63), [계약 문서](../design/foundation/seat-usage-api.md)의 "좌석 이동", [ADR-M5-001](../db/ADR-M5-001.md)(M5-D06), [입퇴실 기록](2026-11-02-seat-check-in-out.md).

## 1. 배경 / 문제

이용 중인 고객이 자리를 옮길 때 이용 기록·이용권·입실 시각은 그대로 두고 좌석 점유만 바꿔야 한다. 이동 때문에 이용 시간이나 차감이 달라지면 안 되고, 두 좌석의 점유가 따로 바뀌어 한쪽만 반영되는 상태도 없어야 한다. #62가 이동 이력을 읽는 모델과 상세 응답의 `moves`까지 만들어 두었으므로, 이번 범위는 쓰기 operation `POST /seat-sessions/{id}/move` 하나다. 수동 조정·이력 목록(#64)과 지점 간 이동은 구현하지 않았다.

## 2. 검토한 선택지

- **점유를 옮기는 방식**
  - 이용 기록을 닫고 새로 여는 방식: 이용 기록 ID·입실 시각이 바뀌고 이용권에 `USE` 원장이 두 번 생길 수 있어 "이용 시간 이어짐" 조건과 맞지 않는다. 채택하지 않았다.
  - `seat_sessions.seat_id`만 바꾸는 방식: 계약이 정한 방식이다. 점유는 `seat_id`에서 만들어지는 `active_seat_id`의 유일 키가 표현하므로 같은 행 갱신 한 번으로 해제와 점유가 함께 반영된다. 이쪽을 택했다.
- **목적 좌석의 사용 중 판정**
  - 입실과 같이 좌석 행을 잠근 뒤 `existsBySeatIdAndStatus`로 확인하고, 그래도 놓친 경합은 `uk_seat_sessions_1` 위반을 `SEAT_OCCUPIED`로 바꾼다: 입실에서 이미 검증한 패턴이라 이쪽을 택했다.
- **권한 판정 위치**: 입퇴실이 쓰는 `inRecordBranch(READ)`로 "범위 밖·없음 = 404"를 정한 뒤, 같은 guard 아래에서 `WRITE_SEATS`(operations:write)를 요구해 403으로 답한다. 새 `BranchAction`이나 `AuthorizedCommands` 메서드는 만들지 않았다.

## 3. 결정 및 이유

- **잠금 순서는 계약 표를 따른다.** 멱등 잠금 → 이용 기록 잠금 → 목적 좌석 잠금·확인 → `seat_id` 변경 → `seat_session_moves` → 감사 → 이벤트 → 멱등 결과. 한 요청이 좌석 행을 둘 이상 잠그지 않는다. 입실은 좌석 → 고객 → 이용권 순이고 이용 기록 행을 잠그지 않으며, 퇴실은 이용 기록 → 이용권이라 어느 쪽과도 잠금 순서가 맞물리지 않는다. 서로 좌석을 바꾸려는 두 이동도 각자 상대 좌석이 사용 중이라 거절될 뿐 서로를 기다리지 않는다.
- **거절 판정은 오류 표의 순서다.** 종료됨 → 운영 중지 지점 → 목적 좌석(현재 좌석과 같음·없음·다른 지점은 모두 422 `toSeatId`) → 운영 중단 → 사용 중. 권한(403)과 입력 형식(422)은 멱등 조회보다 먼저, 나머지는 잠금 뒤다.
- **차감 계산은 건드리지 않는다.** 이동은 이용 기록의 `seat_id`와 이력 한 행만 바꾸고 입실 시각·이용권·원장을 읽거나 쓰지 않는다. 퇴실의 이용 분은 처음과 같이 입실 시각에서 계산된다.
- **이동 시각은 서버 시각이다.** 요청에 시각 필드가 없고 `seat_session_moves.moved_at`에 마이크로초 단위로 저장한다.

계약이 정하지 않아 판단한 점:

- **사유 처리**: 입실·퇴실과 같다. 없음·공백은 사유 없음, 문자열이 아니거나 500자 초과는 422다. 앞뒤 공백은 지운다.
- **멱등 요청 해시**: 이용 기록 ID, 목적 좌석 ID, 정규화한 사유다. 같은 키로 다른 좌석이나 사유를 보내면 `IDEMPOTENCY_CONFLICT`다.
- **멱등 기록 만료 뒤의 키 재사용**: `request_key`가 같은 해시라 `uk_seat_session_moves_1`이 거절한다. 입실의 같은 경우와 맞춰 409 `IDEMPOTENCY_CONFLICT`로 바꿨다. 이 경로는 실제 MySQL로 시험하지 않았다.
- **이미 종료된 이용 기록에 같은 키로 재요청**: 멱등 조회가 종료 판정보다 먼저라 최초 이동 결과가 그대로 돌아온다. 퇴실과 같은 순서다.
- **감사**: 동작명 `SEAT_MOVED`, 전후 값은 `seatId`만 담는다. 사유는 감사의 사유 열에 남는다.
- **이벤트**: 원래 좌석·목적 좌석의 `seats`와 `seat-sessions`를 각각 한 번씩 보낸다. 모두 이용 지점 기준이다. 이용권 잔량이 바뀌지 않으므로 `passes` 이벤트는 보내지 않는다.
- **응답 `version`**: 이동마다 이용 기록 행의 낙관적 잠금 버전이 올라가므로 API 버전도 오른다.
- **운영 중지 지점**: 계약대로 이동은 새 좌석 배정이라 409 `BRANCH_NOT_ACTIVE`이고 퇴실은 허용한다. 이동하는 쪽 `WRITE_SEATS`는 지점 운영 상태를 요구하지 않으므로, 이 거절은 서비스가 잠금 뒤에 직접 판정한다.

## 4. 구현 내용

- `SeatSessionService.move`와 `SeatSessionController`의 `POST /api/seat-sessions/{id}/move`
- `SeatSessionMove`를 추가 전용 entity로 확장(생성 방식 `IDENTITY`, `request_key` 매핑, `of` 팩토리). 행은 만들기만 하고 바꾸지 않으므로 `@Immutable`을 유지했다.
- `SeatSession.moveTo`: 진행 중인 기록에서만 좌석을 바꾼다.
- `SeatSessionConflicts`: `uk_seat_session_moves_1` 위반을 `IDEMPOTENCY_CONFLICT`로 변환
- OpenAPI `moveSeatSession`을 `implemented`로 바꾸고 소개 문구와 `seat-usage-api.md` 구현 상태 표기를 갱신했다. 계약 내용은 바꾸지 않았다.

마이그레이션은 없다(V1 스키마 그대로). 이용권·차감 코드는 수정하지 않았다.

## 5. 검증 결과

- 신규 `SeatSessionMoveIntegrationTests` 16개를 HTTP와 실제 MySQL(Testcontainers)로 실행해 모두 통과했다. 이동 operation만 실행한 결과다.
  - 이동 후 같은 이용 기록·이용권·고객·입실 시각 유지, `seat_id`와 `active_seat_id` 변경, 이력 행(원래·목적 좌석, 처리자, 사유, 시각, `SMV-` 키), 감사, 이벤트, 좌석 표시 상태(원래 좌석 사용 가능, 목적 좌석 사용 중), 상세의 `moves`와 응답 일치, 비워진 좌석에 다른 고객 즉시 입실
  - 같은 키 재요청이 최초 결과를 돌려주고 행·감사를 늘리지 않음, 같은 키에 다른 좌석·사유는 `IDEMPOTENCY_CONFLICT`, 새 키는 이력이 순서대로 쌓임
  - 권한: operations:write 없는 직원 403, 다른 지점 직원·없는 ID 404, 소유자 가능, 소속 회수 직후 404, 다른 지점 고객의 이용도 이용 지점 직원이 처리
  - 거절: 사용 중·운영 중단 좌석, 다른 지점·없는 좌석·같은 좌석(422, 같은 문구), 거절 뒤 원래 좌석·이력·감사·멱등 기록이 그대로
  - 입력 검증: 누락·형식 오류·허용 외 필드·500자 초과·숫자 사유·키 누락·짧은 키, 500자 사유와 공백 사유
  - 종료된 이용 409, 운영 중지 지점 409와 거절 순서(종료 > 운영 중지 > 입력 오류 > 운영 중단), 운영 중지 지점의 퇴실은 허용
  - 시간권·정액권 각각 두 번 이동한 이용과 이동 없는 이용의 퇴실 결과(이용·차감·초과 분과 금액, 잔량, 원장 증감)가 같음. 이동만으로 원장·잔량·이용권 버전이 바뀌지 않음
  - 서비스 재확인을 spy로 무력화하면 실제 MySQL의 `uk_seat_sessions_1` 위반이 `SEAT_OCCUPIED`가 되고 전체가 롤백됨
- **실제 동시 실행**(요청마다 스레드를 두고 래치로 동시에 출발): 전부 통과했다.
  - 같은 목적 좌석으로 8건 동시 이동 3회: 1건 200, 나머지 `SEAT_OCCUPIED`, 목적 좌석 점유 1건, 패배한 이용은 원래 좌석 유지
  - 같은 키 동시 이동 8건: 모두 같은 결과, 이력·감사 1건
  - 이동과 같은 좌석 입실 12회: 둘 중 하나만 성공
  - 이동과 같은 이용의 퇴실 12회: 퇴실은 항상 성공하고 이동은 성공하거나 `SESSION_ALREADY_CLOSED`, 원장 1행, 차감액과 잔량이 일치
  - 서로 좌석을 바꾸는 이동 5회: 교착 없이 둘 다 `SEAT_OCCUPIED`, 두 좌석 점유 유지
  - 이동과 목적 좌석 운영 중단 12회: 둘 중 하나만 성공
  - 경합 시험의 선후 순서 분포는 이번에 측정하지 않았다. 입실·퇴실·중단 경합은 한쪽을 0~33ms 늦추어 두 순서가 모두 나오도록 했지만 실제 분포는 확인하지 않았다.
- `./gradlew test` 전체: 50개 suite, 415개 테스트(이전 399개 + 신규 16개), 실패·오류·건너뜀 0. Testcontainers MySQL 사용. 수치는 `build/test-results/test/*.xml`을 합산했다.

**한계와 실행하지 않은 것**

- 모든 명령이 공통 guard로 직렬화되므로 동시성 시험의 통과는 주로 guard의 효과다. guard 없이 행 잠금과 유일 키만으로 버티는지는 검증하지 않았다. 유일 키 방어선은 spy로 검사 결과를 무력화하는 시험으로만 확인했다.
- 이동 이벤트가 SSE로 실제 전달되는지는 시험하지 않았다. 아웃박스 행까지만 확인했다.
- 실제 서버 실행, Frontend 연결, 인프라 서버 검증, 부하 측정은 하지 않았다.
- 멱등 기록이 만료된 뒤 같은 키를 쓰는 경로(`uk_seat_session_moves_1`)는 시험하지 않았다.

## 6. 남은 작업 / 보류 사항

- #64: 입퇴실 이력 목록, 수동 조정, 구매·사용 내역.
- 지점 간 이동은 계약상 제외 범위다.
- `AuthorizedCommands` guard를 나누게 되면 이동의 목적 좌석 잠금과 사용 중 확인(일반 읽기)을 다시 봐야 한다. 지금은 guard 아래에서 처리되고 `uk_seat_sessions_1`이 마지막 방어선이다.
- 이동 횟수 제한이나 이동 사유 필수화는 계약에 없어 두지 않았다.
