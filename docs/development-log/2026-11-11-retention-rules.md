# 2026-11-11 개인정보 익명화·정리 규칙과 처리 기록 (#100)

## 1. 배경 / 문제

- 보존 기간이 정해지면 설정만 바꿔 자동 파기·정리가 동작하도록 규칙 구조와 처리 기록이 필요했다(ADR-M11-001 M11-D01·D05).
- #99에서 일부 기간이 확정되었다(ADR-M11-002, PR #224). 사용자 지시: **#100은 확정된 정책만 구현한다.** 미결정 항목(거래·문의·근태·일반 감사·퇴사 직원)은 임의로 구현하지 않는다.

## 2. 검토한 선택지

| 항목 | 선택지 | 결과 |
| --- | --- | --- |
| 규칙 활성화 방법 | 운영자가 문서 절차(백업 → 대상 수 확인 → SQL)로 켬 / OWNER 전용 API | 문서 절차(2026-11-11 사용자 결정). 코드가 가장 적고 실수로 켜질 위험이 낮다. 잘못된 설정은 DB 제약이 막는다 |
| 고객 삭제 요청(정보주체 요청 즉시 익명화) | 이번에 OWNER API로 / 별도 이슈 | 별도 이슈(사용자 결정) |
| 재설정·초대 처리 이력 범위 | 끝난 발송 작업 + 가입하지 않은 초대 / 발송 작업과 재설정 링크만 | 앞쪽(사용자 결정). 수락·승인된 초대는 직원 가입 기록이라 남긴다 |
| 미결정 정보 종류 | 규칙 행만 두고 처리 코드 없이 / 규칙 자체를 두지 않음 | 규칙을 두지 않는다. 처리 코드 없는 규칙을 켜면 아무 일도 하지 않아 오해를 만든다. 확정되면 그때 규칙과 처리를 함께 더한다 |
| 감사 이벤트 정리 | 이슈 인수 조건이라 처리는 구현하고 기간 없이 비활성 / 구현하지 않음 | 구현하고 비활성. 기간 없음, 법정 최소 1,095일(접속기록 1년, 권한 이력 3년이 섞여 있어 큰 쪽) |
| 규칙 설정 저장 | DB 표 / 애플리케이션 설정 | DB 표(M11-D05가 정한 위치). CHECK 제약으로 기간 없는 활성화와 법정 최소 미만 설정을 막는다 |

## 3. 결정 및 이유

- **모든 규칙은 비활성으로 시작한다**(이슈 인수 조건). 확정 항목은 기간 값을 미리 넣어 두되, 운영자가 백업 뒤에 하나씩 켠다.
- **고객 익명화**
  - 행을 지우지 않는다. 이름은 `파기된 고객`으로 바꾸고, 연락처·이메일·메모·상태 사유는 비운다(M11-D05).
  - 회원번호와 모든 참조는 남긴다. 그래서 M9 집계는 그대로다.
  - 진행 중인 사용(이용권·입실·사물함·스터디룸·문의·결제 대기)이 있으면 대상에서 뺀다(ADR-M11-002 D01의 예외).
- **처리 기록**
  - 남기는 것: 규칙, 기간, 기준 시각, 시작·종료 시각, 대상 수, 처리 수, 결과, 오류 종류
  - 오류 메시지는 남기지 않는다. 메시지가 지우던 값을 담을 수 있기 때문이다.
  - 실패 기록은 별도 트랜잭션으로 남긴다.
- **SQL 위치**
  - 다른 모듈의 표를 다루므로 엔티티 대신 새 `retention` 모듈의 repository에서 native SQL로 처리한다.
  - 다른 모듈을 import하지 않아 모듈 경계 규칙을 지킨다.
- **알려진 남는 정보**: 감사 이벤트의 변경 전후 값에는 익명화 전 고객 값이 남을 수 있다. 일반 감사 기간이 미정이라 그때까지 남는다. 처리 기준 문서에 명시했다.

## 5. 검증 결과

- 새 `RetentionIntegrationTests` 5건 통과
  - 기본값 비활성, 꺼진 규칙은 아무것도 안 하고 기록도 없음
  - 기간 없는 활성화와 법정 최소 미만 설정을 DB 제약이 거부
  - 비활성 고객 익명화
    - 식별 필드가 비고, 회원번호·결제 참조는 유지된다.
    - M9 매출 집계가 익명화 전후 같다.
    - 결제 대기 고객과 최근 고객은 제외된다.
    - 처리 기록에는 개인정보가 없다.
    - 두 번째 실행은 다시 처리하지 않는다.
  - 오래된 AI 대화(실행 포함), 만료 멱등 기록, 끝난 재설정 링크, 가입하지 않은 초대는 삭제되고, 최근 대화·살아 있는 기록·수락한 초대는 남는다.
  - 감사 정리는 기간이 지난 이벤트만 삭제한다.
- 새 `RetentionServiceUnitTests` 3건 통과
  - 실패는 오류 종류만 기록하고 메시지는 남기지 않는다.
  - 꺼진 규칙과 기간 없는 규칙은 실행하지 않는다.
  - 법정 최소 미만이면 삭제 전에 거부한다.
- 마이그레이션 테스트
  - `FoundationMigrationTests`: 새 V19 테스트 포함
  - `OwnerBootstrapTests`, `DatabaseInitializationTests`: V19·표 79개로 갱신
- 실행(`-PtestForks=1`): 마이그레이션 3종, 아키텍처·계약, retention, customer 테스트 21개 클래스 170건 통과, 실패 0건
  - `FoundationMigrationTests` 26건, `OwnerBootstrapTests` 10건, `DatabaseInitializationTests` 4건
  - customer 모듈 테스트로 `anonymized_at` 열 추가가 고객 기능을 깨지 않는 것을 확인했다.
- 실행하지 않음
  - 전체 `./gradlew test`: 마일스톤 검증(#104) 때 실행한다.
  - 실제 운영 데이터의 대상 수, 정기 작업이 실제 시각에 도는지 확인
- `graphify update .`: 이 worktree에 `graphify-out`이 없어 실행하지 않았다.

## 6. 남은 작업 / 보류 사항

- 운영에서 규칙을 켜는 일은 운영자가 문서 절차로 한다. 이 PR은 아무 규칙도 켜지 않는다.
- 미결정 항목(#99)이 확정되면 규칙과 처리를 더한다.
- 고객 삭제 요청 처리: 별도 이슈
- 인스턴스가 여러 대가 되면 정기 작업 실행 주체를 하나로 정해야 한다.
- 이 PR은 ADR-M11-002(PR #224)를 참조한다. #224를 먼저 병합해야 문서 링크가 맞는다.
