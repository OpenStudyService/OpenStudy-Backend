# 초대 미리보기·수락·최종 승인

관련 이슈: [Backend #15](https://github.com/OpenStudyService/OpenStudy-Backend/issues/15). 작업 계획: [이슈 댓글](https://github.com/OpenStudyService/OpenStudy-Backend/issues/15#issuecomment-6434399949).

## 1. 배경 / 문제

#13(초대 관리, PR #34)과 #14(발송 worker, PR #36)가 병합되어 초대 생성부터 메일 링크 발송까지는 동작했다. 그러나 링크를 받은 직원이 초대를 확인·수락하고 관리자가 최종 승인하는 API가 없어 초대 흐름이 끝나지 않았고, M2와 #18 통합 검증도 진행할 수 없었다. 본인 승인 상태 조회(`GET /invitations/approval-status`)는 이미 main에 있었다.

작업 시작 시 원래 Backend 체크아웃에는 V1 통합 스키마·OWNER 초기화 관련 미커밋 변경이 있었다. 원격 main `2310785`에서 별도 worktree와 `feature/invitation-acceptance`를 만들어 분리했고 그 변경은 포함하지 않았다.

## 2. 검토한 선택지

- **수락의 잠금 경로**: 수락은 인증된 작업자가 없는 공개 명령이라 기존 `AuthorizedCommands.inBranches`를 쓸 수 없다. 초대 행만 잠그는 방법과 기존 잠금 순서(가드 → 직원 → 지점 → 초대 → 소속)를 그대로 따르는 방법을 비교했다. 초대만 잠그면 신규 계정 생성·소속 변경이 관리 명령(승인·반려·소속 수정)과 다른 순서로 잠금을 잡아 교착 위험이 생긴다. 그래서 같은 순서를 쓰되 인가 대신 토큰을 검증하는 `publicCommand`를 추가했다.
- **승인의 위치**: 별도 서비스로 분리할지, 기존 관리 서비스의 `change` 흐름(가시성 확인 → 가드·부모 잠금 → 현재 대상 역할 검사)에 넣을지 검토했다. 반려·취소와 같은 인가·version·반복 명령 규칙을 공유해야 하므로 기존 관리 서비스에 추가했다.
- **수락 후 CSRF 교체**: 계약의 "수락 뒤 CSRF 다시 조회"를 서버 교체로 강제할지 검토했다. 기존 직원의 업무 세션에서 교체하면 열린 다른 화면이 다음 저장에서 CSRF 오류를 겪고, 세션 ID가 바뀌지 않으므로 보안상 이득도 없다. 서버 교체 없이 화면이 다시 조회하는 기존 계약을 유지했다.

## 3. 결정 및 이유

- 링크 실패는 원인과 관계없이 하나의 422 응답으로 통일한다. 링크 보유자가 토큰의 존재·만료·사용 여부를 구별하지 못하게 하기 위해서다. 수락 이메일 불일치도 같은 응답이다.
- 신규 계정 수락은 익명 세션에서만, 기존 계정 수락은 같은 계정의 업무 세션에서만 허용한다. 신규 계정이 다른 사람의 세션에 붙지 않게 하고, 기존 계정 비밀번호를 수락 API로 받지 않기 위해서다(Q1).
- 비싼 BCrypt 해시는 잠금 밖에서, 링크가 유효한지 먼저 확인한 뒤에만 계산한다. 가드 잠금 보유 시간을 늘리지 않고, 틀린 링크로 CPU를 쓰게 하지 않는다. 잠금 안에서 해시·상태·만료를 다시 확인한다.
- 승인은 PENDING 계정만 활성화한다. SUSPENDED·LEFT 계정을 초대로 되살리지 않는다는 Q3·Q11과 DB 설계를 따른다.
- 제한 세션은 승인 후에도 자동 승격하지 않는다(Q10). 기존 `requiresLogin=true` 동작을 그대로 쓴다.

## 4. 구현 내용

- 공개 API `POST /invitations/preview`, `POST /invitations/accept`와 관리 API `POST /invitations/{id}/approve`.
- `AuthorizedCommands.publicCommand`: 작업자 없는 명령용 동일 잠금 순서.
- 직원 공개 서비스: 초대 계정 생성, PENDING 소속 생성·회수 소속 재사용, 승인 시 소속·계정 활성화와 권한 복사. 직원 감사·권한 이벤트를 같은 트랜잭션에 기록한다.
- 보안 설정: 두 링크 경로를 익명 허용(CSRF는 유지). 제한 세션의 미리보기 허용. 지점 관리 권한을 요구하던 공통 인터셉터에서 두 링크 경로를 제외했다. 링크 명령은 토큰과 본인 세션으로 검증하는 본인 명령이기 때문이다. 이 제외가 없으면 people:manage가 없는 기존 직원의 수락이 403이 되었다.
- 초대 조회 쿼리 수정: 부모 행을 읽는 RowMapper 안에서 권한·발송 상태를 조회하던 구조를, 부모를 먼저 읽고 자식을 순차 조회하도록 바꿨다. 트랜잭션 밖에서는 요청마다 연결 두 개를 동시에 잡아, 승인·반려를 동시에 보내는 시험에서 테스트 풀(4개)이 고갈되어 두 요청이 모두 500이 되었다. 기존 관리 명령에도 해당하는 문제였다.
- OpenAPI: 미리보기·수락·승인·승인 상태 조회 4개 operation의 `x-implementation-status`만 `implemented`로 바꿨다. schema·계약 버전은 그대로다.
- [구현 계약 문서](../design/foundation/invitation-acceptance-api.md)와 설계 README 갱신.

## 5. 검증 결과

### 신규 통합 시험 (`InvitationAcceptanceIntegrationTests`, 7개)

Testcontainers MySQL과 실제 HTTP 서버로 실행했다. 토큰은 시험에서 발송 worker처럼 해시를 붙여 구성했다. 실제 메일 수신으로 얻은 링크는 아니다.

| 인수 조건 / 위험 | 확인 결과 |
| --- | --- |
| 신규 계정만 비밀번호 생성 | NEW_ACCOUNT로 PENDING 계정·소속 생성, 비밀번호는 BCrypt로만 저장, 세션 미발급 |
| 기존 계정은 같은 이메일 세션으로 수락 | 미로그인 401, 다른 계정 403, 로그인 상태의 NEW_ACCOUNT 403, 기존 계정에 NEW_ACCOUNT 409, 본인 수락 후 비밀번호 불변 |
| 미리보기 token body | body로만 전달, 응답에 토큰·권한·revision 없음, no-store·no-referrer, CSRF 없으면 403 |
| 링크 오류 동일 응답 | 틀림·만료·취소·형식 오류(짧음·초과 길이·허용 외 문자)의 422 본문이 requestId 외 동일, 이메일 불일치도 같은 코드 |
| 승인 반복·반려/제한 우회 없음 | 반복 승인은 낡은 version으로도 현재 결과 반환, PENDING·REJECTED 승인 409, 낡은 version 409, STAFF 403, SUSPENDED 계정 승인 409·상태 유지 |
| 본인 대기 조회 | 제한 세션에서 승인 대기 → 승인 후 `requiresLogin=true`, 업무 API는 계속 403(자동 승격 없음), 재로그인 후 업무 세션 |
| 기존 직원 추가 지점 | 수락 후에도 기존 지점 업무 유지·새 지점 거부, 승인 후 같은 세션의 다음 요청부터 새 지점 허용 |
| 회수 소속 복구·MANAGER 복구 | 같은 소속 행 재사용, 지점 관리자의 MANAGER 초대 승인 403, OWNER 승인 성공 |
| 이중 수락·경합 | 같은 링크 8건 동시 수락 중 1건만 성공(나머지 422), 계정·소속 1건. 승인·반려 동시 요청은 1성공/1충돌이며 결과 상태가 일관됨 |
| 원자성 | 수락·승인을 외부 트랜잭션에서 롤백하면 계정·소속·권한·초대 상태·감사가 모두 원래대로 |
| 비밀값 | 감사 행과 서버 로그에 토큰·비밀번호 없음(OutputCapture) |


- 프론트 수락·승인 화면 연동: Frontend 이슈.

## 6. 남은 작업 / 보류 사항

- 승인 대기(PENDING) 계정이 다른 지점 초대를 추가로 받으면 업무 세션이 없어 첫 승인 전에는 수락할 수 없다. 허용 여부는 정책 결정이 필요하다.
- 링크 명령에는 별도 요청 제한을 두지 않았다. 토큰 엔트로피(256비트)와 링크 확인 후 해시 계산으로 위험을 낮췄지만, 운영 트래픽 기준 판단은 남아 있다.
- #15 인수 조건의 실제 두 브라우저·메일 흐름은 #18 결과로 확인해야 한다.
