# 2026-11-11 메일 발송이 꺼진 상태의 비밀번호 초기화 거부

## 1. 배경 / 문제

- 관리자 비밀번호 초기화(`POST /employees/{id}/password-reset`, #119)는 한 트랜잭션에서 다음을 처리한다.
  - 기존 비밀번호를 바로 무효로 한다(M14-D11).
  - 모든 세션을 끊는다.
  - 재설정 메일 발송 작업을 예약한다.
- 발송 worker(`PasswordResetWorker`)는 `openstudy.invitation-mail.enabled=true`일 때만 만들어진다. 기본값은 꺼짐이다.
- 그래서 메일이 꺼진 환경에서 초기화를 요청하면 다음 상태가 된다.
  - 기존 비밀번호는 이미 무효다.
  - 링크 메일은 나가지 않는다.
  - 발송 작업은 대기 상태로 영원히 남는다.
  - 결과적으로 직원은 로그인할 수 없다.
- 계약 문서도 이 동작을 "요청은 받지만 발송 작업이 대기 상태로 남는다"로 적고 있었다.
- 2026-11-11 저장소 감사에서 가장 먼저 고칠 항목으로 꼽았고, 사용자가 이 작업을 먼저 진행하기로 정했다.

## 2. 검토한 선택지

| 선택지 | 내용 | 판단 |
| --- | --- | --- |
| 메일이 꺼져 있으면 초기화를 거부 | 503 응답만 돌려주고 아무것도 바꾸지 않는다 | 채택 |
| 메일이 꺼져 있으면 기존 비밀번호를 유지하고 요청만 저장 | 직원이 잠기지는 않는다. 하지만 M14-D11(즉시 무효)과 어긋나고, 언제 보낼지 알 수 없는 작업이 쌓인다 | 채택하지 않음 |

## 3. 결정 및 이유

- 보낼 수 없는 초기화는 받지 않는다. 응답은 503 `PASSWORD_RESET_MAIL_DISABLED`다.
  - 기능은 있지만 지금 쓸 수 없는 상태다. AI 카탈로그 준비 전(`AI_NOT_READY`)과 같은 503 규칙을 따랐다.
- 이 거부는 대상 조회·권한·계정 상태 검사 뒤에 한다.
  - 권한이 없는 사용자는 지금처럼 404·403·409를 받는다.
  - 설정 상태를 권한 없는 사용자에게 먼저 알리지 않는다.
- worker bean이 있는지로 판단한다. 설정값을 따로 읽지 않는다.
  - 발송 가능 여부를 정하는 조건이 `PasswordResetMailConfiguration` 한 곳에 남는다.

## 4. 구현 내용

- `AccountCredentialService`
  - `Optional<PasswordResetWorker>`를 주입받는다.
  - 비어 있으면 `requestReset`이 비밀번호·세션·링크·감사를 건드리지 않고 503을 던진다.
- 계약
  - `account-collab-api.md`: 오류 코드 표, 권한과 대상 표, 설정 설명(메일이 꺼진 경우)을 바꿨다.
  - `openapi.json`: `requestPasswordReset`에 503 응답과 `PASSWORD_RESET_MAIL_DISABLED`를 추가했다.
  - 버전은 올리지 않았다. 기존 operation의 오류 하나만 바뀌었기 때문이다.
- 테스트
  - `AccountCredentialUnitTests`: 메일이 꺼져 있으면 503이고, 아무것도 바뀌지 않는다는 테스트를 추가했다.
  - `AccountContractTests`: 503 응답이 있는지 확인한다.

## 6. 남은 작업 / 보류 사항

- Frontend 직원 관리 화면은 이 503을 받으면 "메일 발송이 꺼져 있어 초기화할 수 없음"으로 안내해야 한다. M14 프론트엔드 작업(#43, PR #92)과 맞춰야 한다.
- 2026-11-11 감사의 나머지 항목(멱등 기록 정리, 직원 목록 N+1, 감사 시각 인덱스, 비밀번호 규칙 중복, 쓰이지 않는 DomainLens 코드)은 이 작업에 포함하지 않았다.
