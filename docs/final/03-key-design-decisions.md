# 3. 핵심 설계 결정

DB 설계 결정 기록(ADR)은 17건이 있다([docs/db](../db/)). 이 문서는 그중 면접·발표에서 설명할 가치가 큰 6가지를 **문제 → 검토한 선택지 → 결정 → 결과** 순서로 정리했다. 동시성·정합성 장치(멱등성 키, 관리자 0명 방지, 잠금 순서)는 [5. 정합성과 동시성](05-integrity-and-concurrency.md)에 따로 정리했다.

| # | 결정 | 한 줄 요약 |
|---|---|---|
| D1 | 거래는 구매 당시 조건을 고정한다 | 상품 가격이 바뀌어도 과거 구매·금액은 변하지 않는다 |
| D2 | "활성 상태는 하나만"을 생성 컬럼 + UNIQUE로 강제 | MySQL에 없는 부분 유일 인덱스를 대신한다 |
| D3 | 스터디룸 이중 예약을 시간 슬롯 행으로 막는다 | 겹침 검사를 UNIQUE 하나로 바꾼다 |
| D4 | AI 분석 결과를 저장하지 않는다 | 질문과 실행 명세만 남기고, 열 때 현재 권한으로 다시 실행한다 |
| D5 | 계산할 수 있는 값은 저장하지 않는다 | 판매 수 카운터 대신 집계, 좌석 점유율은 뷰 |
| D6 | 지우지 않고 상태와 이력으로 남긴다 | 상품·고객은 물리 삭제 대신 상태 변경, 개인정보는 익명화 |

## D1. 거래는 구매 당시 조건을 고정한다

**문제.** 상품의 가격·제공 시간은 운영 중에 바뀐다. 이용권(`passes`)이 상품의 현재 값을 참조하면 가격을 올리는 순간 과거 구매의 금액과 남은 시간이 함께 바뀐다.

**검토한 선택지.**

- 상품 테이블만 참조: 단순하지만 과거 거래가 소급해서 바뀐다.
- 거래 행에 조건을 복사: 거래가 스스로 조건을 갖지만, 어느 상품 버전에서 왔는지 추적이 약하다.
- 상품 변경 이력 + 거래 스냅샷을 함께 저장 **(채택)**

**결정.**

- 상품을 바꿀 때마다 `product_revisions`에 전체 조건을 JSON 스냅샷으로 남긴다. 이력 행은 수정하지 않는다.
- 이용권은 구매 당시 revision을 `(purchase_product_revision_id, product_id)` 복합 FK로 가리키고, 가격·이름·분류·제공량을 `snapshot_*` 컬럼에 복사한다.
- 스터디룸 예약과 사물함 요금은 시간당·4주당 요금을 복사하고, `amount_krw = 요금 × 시간` 관계를 CHECK로 강제한다.

**결과.** 가격을 바꿔도 기존 구매의 금액·조건이 변하지 않는다. 상품 물리 삭제 API는 두지 않고 판매 중지로 운영한다.

근거: [기반 DB 설계 - products, product_revisions](../design/foundation/database.md), `ck_room_reservations_10`, `ck_locker_assignment_charges_5`

## D2. "활성 상태는 하나만"을 생성 컬럼 + UNIQUE로 강제한다

**문제.** 좌석 하나에는 진행 중인 이용이 하나만 있어야 하고, 고객 한 명도 동시에 두 좌석을 쓸 수 없다. 끝난 이용 기록은 여러 개 쌓여야 한다. PostgreSQL이라면 `WHERE status = 'ACTIVE'` 부분 유일 인덱스로 끝나지만, MySQL에는 부분 인덱스가 없다.

**검토한 선택지.**

- 애플리케이션에서 조회 후 삽입: 동시 요청 두 개가 모두 "없음"을 보고 둘 다 삽입할 수 있다.
- 비관적 잠금으로 직렬화: 가능하지만 모든 경로가 같은 잠금을 지켜야 한다.
- 상태에 따라 값이 생기는 생성 컬럼에 UNIQUE **(채택)**

**결정.** 활성일 때만 값을 갖고 아니면 NULL인 `STORED` 생성 컬럼을 만들고 UNIQUE를 건다. MySQL UNIQUE는 NULL을 여러 개 허용하므로 끝난 행은 제약에 걸리지 않는다.

```sql
`active_seat_id` bigint unsigned GENERATED ALWAYS AS
  (CASE WHEN `status` = 'ACTIVE' THEN `seat_id` ELSE NULL END) STORED,
UNIQUE KEY `uk_seat_sessions_1` (`active_seat_id`)
```

같은 패턴을 6곳에 썼다.

| 테이블 | 생성 컬럼 | 보장하는 규칙 |
|---|---|---|
| `employees` | `owner_slot` | OWNER는 한 명 |
| `employee_invitations` | `active_invitation_slot` | 지점·이메일당 진행 중인 초대는 하나 |
| `seat_sessions` | `active_seat_id`, `active_customer_id` | 좌석당·고객당 진행 중인 이용은 하나 |
| `attendance_records` | `active_employee_id` | 직원당 근무 중 기록은 하나 |
| `locker_assignment_charges` | `initial_assignment_slot` | 사물함 배정당 첫 결제는 하나 |

**결과.** 동시 요청이 몰려도 DB가 하나만 통과시킨다. 통합 테스트가 두 연결로 동시에 실행해 승자가 하나인지 확인한다(예: `OwnerBootstrapTests.concurrentCommandsCreateOnlyOneOwnerWithoutOverwritingWinner`).

## D3. 스터디룸 이중 예약을 시간 슬롯 행으로 막는다

**문제.** 예약 시간 구간이 겹치는지 검사하는 것은 "범위 겹침" 조건이라 일반 UNIQUE로 표현할 수 없다.

**결정.**

- 예약 하나가 차지하는 1시간 칸마다 `room_reservation_slots` 행을 하나씩 만든다.
- `UNIQUE (room_id, slot_start_at)`이 같은 방의 같은 칸을 두 예약이 갖지 못하게 한다.
- 처음에는 30분 단위였는데, V4에서 1시간 단위로 바꿨다. 정시에 맞지 않는 기존 예약이 있으면 마이그레이션이 아무것도 바꾸기 전에 실패하게 해서 데이터를 조용히 반올림하지 않았다.

**결과.** 겹침 검사가 슬롯 삽입의 UNIQUE 위반 하나로 바뀌었다. 취소하면 슬롯을 지워 다시 예약할 수 있다.

근거: [V4 마이그레이션](../../src/main/resources/db/migration/V4__room_hourly_and_cross_branch_permission.sql), [ADR-M6-001](../db/ADR-M6-001.md)

## D4. AI 분석 결과를 저장하지 않는다

**문제.** 자연어 분석(DomainLens)은 매출·고객 수치를 보여 준다. 결과를 저장하면 다음 문제가 생긴다.

- 권한이 회수된 직원이 저장된 대화에서 과거 수치를 계속 볼 수 있다.
- 결과 행 자체가 보존·파기 대상 개인정보가 된다.

**검토한 선택지.**

- 결과 저장: 다시 열 때 빠르지만 위 두 문제가 남는다.
- 질문과 검증된 실행 명세만 저장 **(채택, 사용자 선택)**

**결정.**

- 대화·실행에는 질문, 검증된 `QuerySpec`/`ViewSpec`, 상태, 기준 시각만 남긴다.
- 다시 열면 저장된 명세를 현재 권한·지점 범위로 다시 검증해 실행한다. 이때 모델(LLM)은 다시 부르지 않는다.
- V8에서 이미 저장된 결과 값을 지웠고, V17에서 사용자가 고친 기간·상품 조건을 명세에 추가했다.
- V22의 계획 캐시도 같은 원칙을 따른다. 같은 뜻의 질문에 대한 **계획**만 재사용하고 결과는 저장하지 않는다.

**결과.** 권한 회수가 저장된 대화에도 즉시 적용된다. AI 테이블은 파기 대상 데이터를 거의 갖지 않는다. 진단용 질문 원문만 30일 뒤 지운다.

근거: [ADR-M10-002 M10-D12](../db/ADR-M10-002.md), [V8](../../src/main/resources/db/migration/V8__ai_execution_spec_without_results.sql), [V22](../../src/main/resources/db/migration/V22__ai_plan_cache.sql)

## D5. 계산할 수 있는 값은 저장하지 않는다

**문제.** 집계 값을 컬럼으로 저장하면 원본과 어긋날 수 있다. 예를 들어 판매 수 카운터는 환불·동시 판매 때 원본 결제와 달라질 수 있다.

**결정과 사례.**

| 사례 | 저장하지 않은 값 | 대신 쓰는 방법 |
|---|---|---|
| 상품 판매 한도 (V13) | 판매 수 카운터 | 판매 시점에 상품 잠금 아래에서 승인·미환불 결제를 센다 |
| 좌석 혼잡도 (V20) | 시간대별 점유 샘플 테이블 | 입퇴실 기록에서 계산하는 뷰 `seat_occupancy_samples` |
| 매출 통계 (M9) | 일별 매출 집계 테이블 | 결제·환불 원장에서 직접 집계 + 인덱스 ([4. 인덱스 튜닝](04-index-tuning.md)) |

**예외.** 일별 마감(V15)은 그날 매출을 JSON 스냅샷으로 저장한다. 마감은 "그 시점에 확정한 숫자"를 남기는 것 자체가 업무 목적이기 때문이다. 마감 뒤 환불은 스냅샷을 고치지 않고 조정 행(`daily_closing_adjustments`)으로 남긴다.

**결과.** 원본과 집계가 어긋날 여지가 없고, 수집 배치 작업이 필요 없다. 대가는 조회 시 계산 비용이며, 측정해서 필요한 곳에만 인덱스를 추가했다.

## D6. 지우지 않고 상태와 이력으로 남긴다

**문제.** 운영 데이터는 서로 강하게 연결돼 있다. 고객이나 상품을 지우면 결제·이용권·예약의 FK가 깨지거나 기록이 사라진다. 반면 개인정보는 보존 기간이 지나면 지워야 한다.

**결정.**

- **상품**: 물리 삭제 API가 없다. 판매 중지·재개로 운영하고, 거래 FK는 `RESTRICT`로 유지한다.
- **고객 병합**(V14): 흡수된 고객을 지우지 않는다. `MERGED` 상태와 병합 대상을 남기고, 결제·이용권은 원래 고객을 계속 가리킨다. 조회할 때 흡수된 고객을 함께 읽는다. 병합 이력은 수정·삭제하지 않는다.
- **상태 변경 이력**: `customer_status_events`, `pass_balance_events`, `shift_events`, `inquiry_events`처럼 현재 상태 테이블 옆에 이벤트 테이블을 둔다.
- **개인정보 보존**(V19): 정보 종류별 보존 규칙 테이블을 두고, 고객은 행을 지우지 않고 식별 필드만 익명화한다(`anonymized_at`). 규칙은 모두 꺼진 상태로 시작하고, 법정 최소 기간보다 짧게 설정할 수 없게 CHECK로 막는다.

**결과.** 참조 무결성과 감사 추적을 유지하면서 개인정보 파기 요구도 충족할 구조를 갖췄다. 실제 보존 기간 중 거래·문의·근태는 아직 결정하지 않아 규칙을 두지 않았다.

근거: [V14](../../src/main/resources/db/migration/V14__customer_merge.sql), [V19](../../src/main/resources/db/migration/V19__retention_rules.sql), [ADR-M11-001](../db/ADR-M11-001.md), [ADR-M13-001](../db/ADR-M13-001.md)
