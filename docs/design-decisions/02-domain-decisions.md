## NEXT-01 초대 메일의 토큰과 재시도

**확정 결정:** 2026-10-18 사용자가 B를 선택했다. outbox에는 초대 ID를 저장하고 발송 worker가 매 발송 시 새 토큰을 생성한다. 검증용 토큰은 해시로 저장하고 원문/복호화 가능한 발송
payload는 DB에 보관하지 않는다. 재시도 시 이전 링크는 무효화되므로 가장 최근 발급 링크를 사용하도록 안내한다. 발송 revision·수락·재시도의 경합을 제어하고 수락/취소/만료된 초대는 발송하지 않는다.
최초 초대 기준 24시간은 자동 재시도로 연장하지 않는다. 메일 도착 순서가 발급 순서와 다를 수 있으므로 최신 유효 링크 판정은 서버 revision을 따른다. API/worker 구현과 실제 메일 검증은 후속
작업이다.

결정 시점: M2 초대 구현 전. 관련 근거: 운영 API의 초대/메일 outbox 규칙, 착수 계획 C05.

**왜 선택이 필요한가:** 토큰은 비밀번호처럼 링크를 가진 사람이 사용할 수 있는 비밀값이다. 현재 문서는 DB에 해시만 저장하라고 하면서, 서버가 꺼졌다 켜져도 메일 outbox를 재시도하라고 한다. 해시는
원문으로 되돌릴 수 없으므로 발송 worker가 링크를 어떻게 얻을지 정해야 한다.

| 선택   | 무엇을 말하나                                                                                                         | 얻는 점                                                                 | 감수할 점                                                                                                                           |
|--------|-----------------------------------------------------------------------------------------------------------------------|-------------------------------------------------------------------------|-------------------------------------------------------------------------------------------------------------------------------------|
| A 권장 | 초대 검증 테이블에는 해시만, 발송 대기 payload에는 링크를 단기 암호화 저장. 복호화 키는 DB 밖 서버 비밀 설정으로 관리 | 재시도에도 같은 링크를 보내 수신자가 혼란을 덜 겪고 재기동 후 발송 가능 | ‘DB에는 해시만’ 규칙에 발송용 암호문 예외가 필요. 키 관리·payload 제거·접근 제한 구현 필요                                          |
| B      | outbox에는 초대 ID만 저장하고 worker가 발송 시 새 토큰 생성. 재시도 시 토큰도 교체하고 원문은 메모리/메일에서만 사용  | 토큰 원문/복호화 가능한 payload를 DB에 보관하지 않음                    | 메일이 도착했지만 성공 기록 전에 장애가 나면 다음 시도가 이전 링크를 무효화할 수 있음. 발송 revision/수락/재발급 경합 제어가 복잡함 |

**사례:** 메일이 도착한 직후 서버가 꺼져 발송 완료 기록이 없으면 A는 같은 링크를 재전송할 수 있다. B는 다시 발송하며 앞 메일 링크가 무효가 될 수 있어 ‘가장 최근 메일 사용’ 안내가 필요하다.

**권장 이유:** 수신자가 안정적으로 같은 링크를 사용하는 A를 제안한다. 평문 토큰 저장은 하지 않는다. B도 가능한 설계지만 재발송에 따른 이전 링크 폐기를 사용자가 이해해야 한다.

**공통 조건:** TTL은 최초 초대 기준 24시간을 유지하며 자동 발송 재시도로 연장하지 않는다. 수락/취소/만료된 초대는 다시 발송하지 않고 이전 revision은 거부한다. 재발급은 별도 명령이다. 메일 중복
전달을 완전히 없앴다고 주장하지 않는다. 실제 수신·더블 검증도 구분한다.

**계약 영향:** A는 비밀 저장 정책의 암호문 예외·보존/삭제 규칙, B는 발송 재시도에 따른 링크 교체 정책을 명시해야 한다. 목록·상세·감사에서 토큰 미노출은 두 옵션 모두 유지한다.

**통과 증거:** 발송 실패/성공 기록 유실/재기동/재발급/수락 동시 요청, 원문 토큰 로그 누출 없음, 실제 메일함 수신 후 1회 수락.

선택: `B 확정` / 이유·조건: `발송 재시도마다 새 토큰 발급·이전 링크 무효화. DB에는 원문/복호화 가능한 payload를 보관하지 않음. 2026-10-18 사용자 선택.`

## NEXT-02 직원 소속·권한의 편집 단위

**확정 결정:** 2026-10-18 사용자가 한 지점씩 저장하는 A와 역할별 자주 쓰는 권한을 일괄 설정하는 프리셋 제공을 선택했다. 다른 지점 소속에는 영향을 주지 않는다. 후속 선택은 프리셋 관리 B (기본
프리셋 + 사장님의 사용자 정의 프리셋 생성·수정), 적용 방식 A (적용 시 권한 복사)다. 적용 후 직원별 권한을 조정할 수 있고 프리셋 수정은 기존 직원에 자동 반영하지 않는다. 기존 직원은 명시적으로
재적용해야 변경된다. 프리셋은 권한 선택을 돕는 기능이며 적용 요청도 서버의 지점·역할·행동 권한 검사를 통과해야 한다. owner 부여나 승인 우회 수단으로 사용할 수 없다. 정확한 권한 조합과 API/화면/DB
설계는 후속 구현 Task다.

**프리셋 검증 조건:** 사장님만 사용자 정의 프리셋을 생성·수정할 수 있다. 적용 전후 권한과 선택한 지점을 확인하고 직원 version 충돌을 검사한다. 프리셋 수정 후 기존 직원의 권한이 유지되는지, 재적용과
개별 권한 변경의 경합, 적용 시 서버 권한 검사가 유지되는지 확인한다. 프리셋 복사/직원 변경의 감사 기록과 트랜잭션을 설계한다. 실제 테스트는 아직 실행하지 않았다.

결정 시점: M2 직원 관리 구현 전. 관련 근거: `/employees/{id}/permissions`, 착수 계획 C06.

**왜 선택이 필요한가:** 배열을 저장할 때 ‘보내지 않은 지점은 유지’와 ‘내가 관리하는 지점은 새 배열로 교체’가 다르게 동작한다. 실수로 다른 소속을 지우지 않도록 편집 화면과 API의 단위를 맞춘다.

| 선택   | 무엇을 말하나                                                  | 얻는 점                                              | 감수할 점                                                                                 |
|--------|----------------------------------------------------------------|------------------------------------------------------|-------------------------------------------------------------------------------------------|
| A 권장 | 실제 지점을 scope로 명시해 한 지점의 배정/역할/권한만 저장     | 한 번의 변경 범위가 작고 삭제 의도가 명확함          | 두 지점을 바꾸려면 각각 저장. 두 변경을 모두 성공/실패시키는 단위는 아님                  |
| B      | scope=all에서 현재 관리 가능한 지점의 편집 결과를 한 번에 저장 | 여러 지점 배정을 한 화면에서 원자적으로 바꿀 수 있음 | 누락된 관리 지점의 삭제 의미를 명확히 해야 함. 저장 전 추가/변경/해제 차이를 보여 줘야 함 |

**사례:** 강남/성수 관리자에게 강남 변경만 보내면 A는 강남만 수정한다. B의 교체 집합에서 성수가 빠졌다면 성수 해제로 해석될 수 있으므로 명시적 변경 미리보기가 필요하다.

**권장 이유:** A가 권한 관리 실수를 줄이고 화면/테스트도 단순하다. 어떤 옵션이든 관리 범위 밖 소속은 요청 누락으로 지우지 않고, 전달됐으면 기존값과 같은 경우에만 허용한다.

**공통 조건:** owner 변경·승인 대기 계정의 approve 우회·중복 소속 금지. 실제 소속 제거와 필드 누락을 구분한다. 버전 충돌 시 최신 소속을 확인하고 다시 저장한다.

**계약 영향:** 기존 경로는 유지할 수 있다. scope와 memberships 교체 범위, 해제 표현을 문서·타입·폼에서 명시한다. M1에 최소 권한 편집을 넣는 M1-01 A를 택했다면 NEXT-02도 그
부분의 구현 전에 먼저 결정한다.

**통과 증거:** 관리자 범위 변경/회수, 타 지점 보존, 한 직원의 두 지점 동시 저장, 계정 공통 정보 변경 권한과의 구분.

선택: `지점별 저장 A / 프리셋 관리 B / 적용 방식 A 확정` / 이유·조건:
`기본 및 사장님 사용자 정의 프리셋. 적용 시 권한 복사 후 개별 조정 가능. 프리셋 수정은 기존 직원에 자동 반영하지 않음. 2026-10-18 사용자 선택.`

## NEXT-03 이용 시간 정정과 이용권 잔량

**확정 결정:** 2026-10-18 사용자가 A를 선택했다. 고객의 정상 퇴실 기록 실패 등으로 관리자가 확인 후 이용 시간을 정정하면 기존 차감과 정정된 사용량의 차이를 이용권 원장에 함께 반영한다.
원본·사유·처리자·시각을 보존하고 시간 정정·보정 원장·잔량 변경을 하나의 트랜잭션으로 처리한다. 구매 당시 요율과 반올림을 적용하며 중복 정정은 한 번만 반영한다. 실제 사용 이력과 미사용 환불 제한은 유지한다.
만료 연장이나 환불권 재활성화를 하지 않으며 원결제/매출은 바꾸지 않는다. 정정 명령/API/프론트·실DB 경합 검증은 후속 구현이다.

**입퇴실 주체:** 정상 입퇴실은 고객 QR 등 직접 행동, 직원은 정상 처리 실패 시 예외
지원이다. [입퇴실 정책](../../../docs/revised/2026-10-18/customer-checkin-checkout-policy.md)을 따른다. 고객 화면/QR 연동은 후속 범위다. 서버 처리
지연과 고객 퇴실 기록 실패를 구분하며 기준 시각의 계약은 후속 구체화한다.

결정 시점: M4 고객·이용권·좌석 구현 전. 관련 근거: OS-SEAT-005의 정정 이력, 착수 계획 C09.

**왜 선택이 필요한가:** 고객이 퇴실을 시도했지만 정상 기록되지 않아 직원/관리자가 확인 후 잘못된 이용 시간을 정정할 때, 기록만 고칠지 남은 이용권도 보정할지다. 실제 입실 이력을 삭제하거나 이미 사용한 권을
미사용으로 만드는 선택은 허용하지 않는다.

| 선택   | 무엇을 말하나                                                                                | 얻는 점                                                | 감수할 점                                                                   |
|--------|----------------------------------------------------------------------------------------------|--------------------------------------------------------|-----------------------------------------------------------------------------|
| A 권장 | 관리자가 원본을 보존하고 정정된 시간/요금과 기존 차감의 차이를 이용권 원장에 반영            | 잘못 차감된 시간/잔액을 고객에게 바로 돌려줄 수 있음   | 이후 이용·만료·잔량과 연결돼 잠금/재계산/보정 원장이 복잡해짐               |
| B      | 원본과 정정 표시값·사유를 보존하되 차감량은 자동 변경하지 않음. 잔량은 별도 관리자 조정 명령 | 시간 기록과 잔량 조정의 책임/사유를 따로 검토하기 쉬움 | 정정과 조정을 두 번 처리해야 하고 누락 시 정정 시간과 차감량이 다를 수 있음 |

**사례:** 30분 이용으로 차감했지만 실제 20분이면 A는 차이 10분을 원장으로 복원한다. B는 시간 정정 후 기존 이용권 조정 기능으로 별도 보정하며 두 기록을 연결한다.

**권장 이유:** 운영자가 한 번에 정확한 결과를 만드는 A를 제안한다. 금액 계산은 구매 당시 요율과 정해진 반올림을 사용한다. 원승인액이나 매출은 바꾸지 않는다.

**공통 조건:** 원본 version/관리자 권한/사유·처리자·시각 보존, 동일 요청 1회 반영, 잔량 음수 금지·초과량 별도 처리, 실제 사용 후 미사용 환불 금지는 유지한다. 만료권의 잔량이 복원돼도 유효기간이
자동 연장되지 않는다. 환불권을 정정으로 재활성화하지 않는다.

**계약 영향:** 현재 usage는 읽기 전용이다. A는 정정 명령·원본/유효값·보정 원장 계약을 추가한다. B도 시간 정정 명령과 기존 adjust의 연결 참조를 추가하고 화면에 차감 미반영 여부를 표시한다.

**통과 증거:** 시간권/정액권·0분·만료·소진·후속 이용·중복 정정·퇴실/조정과의 경합, 일반 매출이 소비 정정으로 변하지 않음.

선택: `A 확정` / 이유·조건: `예외 상황의 이용 시간 정정과 차감 차이의 원장 보정을 함께 처리. 원본·실제 사용 이력 보존. 2026-10-18 사용자 선택.`

## NEXT-04 스터디룸 운영시간 설정

**확정 결정:** 2026-10-18 사용자가 B를 선택했다. 룸마다 월~일의 운영 구간과 휴무를 구조화해서 설정한다. 서버는 예약 전체 구간이 운영시간 내인지 검증하고 KST·자정 경과·24시간 운영·요일 경계를
처리한다. 기존 확정 예약과 충돌하는 운영시간 변경을 검사하며 예약을 조용히 삭제하지 않는다. 공휴일 자동 계산·특정 날짜 임시 휴무는 이번 B에 포함하지 않는다. 정확한 DTO/ERD와 API/폼 변경·경계/경합

DomainLens는 같은 원장·지표·기준 시각을 사용한다. 최소 원장 DTO/API·화면·권한/합계 검증은 후속 구현이며 실제 엔진 결과 비교는 엔진 연동 후 별도로 수행한다.

결정 시점: M8 일반 매출 구현 전. 관련 근거: OS-SALE-001/004, sales:read와 payments:read 분리, 착수 계획 C15.

**왜 선택이 필요한가:** 매출 합계를 볼 수 있는 직원이 고객 개인정보가 포함된 결제 상세까지 볼 수 있는지는 별개의 문제다. 합계의 구성 근거를 제공하면서도 권한을 넓히지 않는 방법을 선택한다.

| 선택   | 무엇을 말하나                                                                             | 얻는 점                                          | 감수할 점                                                                  |
|--------|-------------------------------------------------------------------------------------------|--------------------------------------------------|----------------------------------------------------------------------------|
| A 권장 | sales:read에 매출 검증용 최소 원장 제공. 거래 식별자·지점·상품·승인/환불 시각·금액만 포함 | 결제 상세 권한 없이도 합계 근거를 대사할 수 있음 | 매출용 DTO/API·허용 필드 정책을 별도 관리해야 함                           |
| B      | 집계는 sales:read, 구성 거래/상세는 payments:read가 있는 지점만 열람                      | 기존 결제 API와 권한을 재사용하기 쉬움           | 매출만 보는 직원은 직접 원장 확인이 제한됨. 화면에 접근 제한을 표시해야 함 |

**사례:** 순매출 -100,000원을 보고 A는 ‘전월 승인/이번 달 환불’의 비식별 근거를 바로 볼 수 있다. B는 payments:read가 없으면 구성 거래 화면에 들어갈 수 없다.

**권장 이유:** 매출 권한과 결제 상세 권한을 구분하면서 집계 근거를 보여 주는 A를 제안한다. A여도 고객 이름/연락처·직원 비공개 사유·승인 비밀값은 포함하지 않는다. 전체 결제 상세를 열 때는 별도
payments:read를 검사한다.

**공통 조건:** 허용 지점의 교집합, 원결제 지점 귀속, processed/original 두 환불 기준, 일/주/월·상품 필터, 동일 원장/기준 시각을 일반 매출과 DomainLens에 적용한다. 소비 차감은
새 매출이 아니다.

**계약 영향:** A는 최소 근거 원장 계약 추가, B는 원장 연결의 복합 권한·거절 UX 명시. 두 옵션 모두 현재 `/sales`에 부족한 집계/필터 계약 보완은 필요하다.

**통과 증거:** sales만 있는 사용자/양쪽 권한 사용자/타 지점 직접 호출, 최소 원장 total·합계·기간 경계 일치, 실제 엔진 결과와의 별도 비교.

선택: `A 확정` / 필요한 근거 필드: `거래 식별자·지점·상품·승인/환불 시각·금액. 고객 개인정보 제외, 전체 결제 상세는 별도 payments:read 검사. 2026-10-18 사용자 선택.`

## 나머지 계약 보완은 어떻게 처리하나

여기에 선택지가 없는 누락이 없어지는 것은 아니다. 문의 접수 경로·답변자/시각, 점검 이력·위치, 사물함 연장 사유, 명시적 검색 필터·페이징, 실제 룸 이용 시각, 홈 기준 시각은 기존 요구를 충족하기 위한 보완
작업으로 추적한다. 값을 정해야 하는 지점이 새로 발견되면 근거·옵션·영향을 추가한다.

DM/지점 채널은 현재 활성 계정·참여자·유효 지점 정책을 REST/SSE에 적용한다. 지점 권한 회수 후에도 과거에 참가했다는 사실만으로 지점 채널 접근을 허용하지 않는다. 공통 지점이 사라진 기존 DM의
재접근처럼 엔진/채팅 구현 전에 세부 확인이 필요한 사례는 권한표·수용 테스트에 명시하고 미확정 상태로 추적한다.

실제 DomainLens의 버전·MySQL 호환성·DTO는 선호도 설문으로 확정할 수 없으므로 [안내의 외부 확인 목록](README.md)을 따른다.
