## 2026-10-22 디렉토리 구조 변경

사용자가 익숙한 Spring Boot 계층 이름과 코드 탐색의 편의성을 위해 구조 변경을 요청했다. 모듈별 api/presentation/application/domain/infrastructure를 controller/service/repository/entity/dto(request·response)로 변경하고 최상위 bootstrap/shared/platform을 config/common으로 정리했다. common/exception 외의 공통 세부 패키지는 필요한 기능 구현 시 추가한다.

M1-02의 단일 빌드·기능별 패키지와 M1-04의 JPA 업무 엔티티·별도 DTO는 유지한다. 모듈 간 계약 위치는 api 전용 패키지에서 명시적으로 공개한 service 진입점과 DTO로 변경한다. 다른 모듈 Entity/Repository 직접 접근과 모듈 순환은 계속 금지한다. ArchUnit은 아직 미구현이다. [현재 설계](../architecture/directory-structure.md)와 [변경 기록](../development-log/2026-10-22-simplify-backend-package-layout.md)을 따른다.

## 별도 조건과 충돌 조정

설계 대화는 2026-10-18 사용자 요청에 따라 다음 질문부터 3개 항목씩 묶어서 진행한다. 각 항목의 의미·선택지·trade-off·권장 이유를 설명하고, 묶음 제시가 일괄 승인으로 해석되지 않도록 실제 답변만
확정한다.

M1-11의 저장소 분리와 공통 문서 위치는 확정했다. 공통 정본은 별도 openstudy-docs 저장소로 관리하고 코드와 문서 버전을 연결한다. 백엔드 전용 설계 문서는 backend docs에 둔다. 실제 문서
이동은 경로와 링크·생성 스크립트 참조를 함께 정리하는 후속 Task로 수행한다.

2026-10-18 대화에서 개발 진행 방식을 확정했다. Task는 하나의 관찰 가능한 동작과 완료 조건·검증 방법을 갖는 작은 단위로 나눈다. 공통 ERD/API/모듈 경계와 선행 관계를 먼저 정리하고, 독립적인
Task만 병렬 배정한다. 주 에이전트가 결과를 검토·통합하고 마일스톤에서 실DB·서버·프론트 연결을 검증한다. 이는 M1-01 A/B 중 하나를 선택하거나 다른 미정 설계·서버 구현 착수까지 승인한 것으로 해석하지
않는다.

## 답변 예시

아래는 **형식 예시이며 사용자 선택이 아니다**.

```text
M1-01=A
M1-02=A
M1-03=B (Gradle 사용 경험이 있어서)
M1-05=A (서버를 다시 켜도 로그인 유지)

```

권장안을 일괄 채택하려면 그 의사를 명시하면 된다. 그때도 외부 미검증 항목은 통과로 바꾸지 않고, 모순되는 추가 조건이나 계약 개정은 먼저 정리한다.
