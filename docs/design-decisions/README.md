# OpenStudy 백엔드 설계 선택 안내

작성일: 2026-10-18 KST. 상태: 진행 방식 및 기존 설계 선택지 확정, 첫 마일스톤 Task 범위·상세 설계·계약 동기화·실행 검증은 후속 작업. 대상: 1인 개발·교육 시연·취업 포트폴리오.

이 문서는 백엔드 구현을 시작하기 전에 사람이 선택할 설계를 설명한다. 권장안은 현재 범위·기존 프론트·DomainLens 연결 조건을 고려한 제안이다. 권장안 표시가 선택 완료를 뜻하지 않는다. 이 문서 작성으로
서버·DB·기존 API 정본이 변경되지는 않았다.

대화로 확정한 진행 방식은 **작은 Task의 서브에이전트 배정 → 주 에이전트 검토·통합 → 마일스톤 연결 검증**이다. M1의 정확한 범위는 Task 분해 과정에서 조정하며, M1-01의 A/B 중 하나를 확정한
상태는 아니다. M1-02는 **A: 한 빌드 프로젝트 안의 기능별 패키지와 ArchUnit 경계 검사**, M1-03은 **B: Gradle Wrapper + Groovy DSL (`build.gradle`)**,
M1-04는 **A: 모듈 내부 JPA 업무 모델과 별도 요청·응답 DTO**로 확정했다. M1-05는 **A: Spring Session JDBC로 MySQL에 세션 저장**, M1-06은 **B: 유휴
60분·최대 12시간**이다. M1-07은 **A: 일반 권한 변경 시 로그인 유지+즉시 재평가, 계정 제한/비활성화 시 강제 종료**로 확정했다. 나머지 선택은 별도로 검토한다. 현재
결정은 [선택 기록표](decision-register.md)를 따른다.

## 읽는 순서

M1-08은 최신 사용자 결정으로 **로그인 이메일 ID 변경 금지**다. 이전 이메일 변경/비밀번호 재확인 선택을 철회했다. 선택 대상에서 제외하며 닉네임/사진만 수정할 수 있다. 본인과 관리자 모두 이메일을
수정할 수 없고 최초 계정 생성/초대의 입력은 유지한다. [정책 개정](../../../docs/revised/2026-10-18/email-login-id-policy.md)이 v1.0의 이메일 수정 표현보다
우선한다.

M1-09는 **A: 프로필과 직원 정보가 기존 직원 version 공유**로 확정했다. 오래된 version은 409로 거절하고 작성 입력을 보존한다. 관련 API·프론트 개정과 실제 DB 경합 검증은 후속 구현
대상으로 남긴다.

M1-10은 **A: 명시적인 전용 초기화 명령으로 최초 사장님 생성**으로 확정했다. 일반 서버 기동과 분리하며 비밀번호 노출·중복 생성·기존 비밀번호 덮어쓰기를 방지한다. 명령 구현과 실제 MySQL 검증은 후속
작업이다.

M1-11은 **B: Organization 아래 멀티 레포 관리**로 확정했다. 공통 요구사항/API/개발 기록은 별도 openstudy-docs 저장소로 관리한다. 원격 주소·공개 범위는 별도로 정한다. 문서
이동과 저장소 생성은 아직 수행하지 않았다. 설계 질문은 사용자 요청에 따라 3개 항목씩 묶어서 진행한다.

후속 선택에서 공통 정본 위치는 **별도 openstudy-docs 저장소 (A)**로 확정했다. 백엔드 전용 문서는 backend docs에 유지한다. NEXT-02는 **지점별 저장 (A) + 기본/사장님 사용자
정의 프리셋 (B) + 적용 시 권한 복사 (A)**다. 프리셋 수정은 기존 직원에 자동 반영하지 않는다. M1-12는 2026-10-19 사용자 결정으로 **Docker 전용 MySQL 8.4 테스트 DB (A)**로 변경했다. 자동 테스트는 Testcontainers로 관리하고 CRUD 롤백과 HTTP/경합/커밋 후 정리를 병행한다. 개발 DB 오접속을 차단하고 테스트 컨테이너 자원만 정리한다. V1 SQL 및 Testcontainers·프로필·앱/DB 기반 32개 검증을 완료했다. 업무별 경합과 Debian 운영 검수는 후속이며 현재 결과는 [검증 보고서 v1.0](../verification/database-initialization-v1.0.md)을 따른다.

NEXT-01은 **B: 초대 메일 재시도 시 새 토큰 발급**, NEXT-04는 **B: 룸별 요일별 운영시간/휴무**로 확정했다. NEXT-03은 **A: 이용 시간 정정과 잔량 보정 동시 처리**,
NEXT-05는 **B: 최대 10분 조기 시작·추가 과금 없음·예약 종료 유지**, NEXT-06은 **A: 직원/연도별 공통 휴가 잔량**으로 확정했다. 정상 입퇴실은 고객 QR 등 직접 행동이며 직원은 실패 시
예외 지원한다. [입퇴실 정책](../../../docs/revised/2026-10-18/customer-checkin-checkout-policy.md)을 따른다.

NEXT-07은 **A: 휴가 기간+총일수·전기간 유효 부여 사용**, NEXT-08은 **A: sales:read에 개인정보 없는 최소 거래 근거 제공**으로 확정했다. 기존 도메인 선택지는 모두 답변을 받았다.
확정값을 ERD·모듈 책임·상태/트랜잭션·API/프론트 계약에 반영하고 첫 마일스톤을 작은 Task로 나누는 작업이 남아 있다. 실제 엔진 DTO/의존성·MySQL 호환성과 서버/DB 실행은 별도 검증 대상이다.
Git 저장소·공통 문서 이동 역시 아직 수행하지 않았다.

M1-01에서 권한 편집까지 포함하는 A를 선택하면 NEXT-02의 ‘소속·권한 저장 단위’도 M1 구현 전에 함께 결정한다. M1을 작게 나누는 B라면 해당 항목은 조직 관리 단계까지 보류할 수 있다.

답변은 `M1-01=A, M1-02=A, M1-05=B`처럼 보내거나 기록표의 빈 칸을 직접 채우면 된다. 일부만 골라도 되고, 이해가 안 되는 항목은 `설명 필요`, 나중 항목은 `보류`로 남길 수 있다. 새
조건이 있으면 A/B 대신 조건을 적어도 된다. 빈 칸과 무응답은 승인으로 취급하지 않는다.

Java 21·Spring Boot 4.1.1·WebMVC는 앞선 분석의 **기술 제안**이며 사용자 확정 DB와 구분한다. 한 빌드 안의 기능별 패키지 구조 (M1-02 A), Gradle Groovy DSL
(M1-03 B), 모듈 내부 JPA 업무 모델과 별도 DTO (M1-04 A)는 사용자 선택으로 확정했다. 실제 엔진 의존성과 빌드해 보기 전에는 호환성 검증이 완료된 것으로 기록하지 않는다.

기능·정책은 [개정 요구사항](../../../docs/revised/2026-10-17/OpenStudy_요구사항_명세서_v1.2.docx), HTTP
계약은 [운영 API](../../../docs/api/README.md)를 따른다. 선택안이 기존 계약을 바꾸는 경우 각 항목의 ‘계약 영향’에 표시했다. 선택이 확정되면 관련
OpenAPI·생성기·compatibility·프론트·테스트를 함께 수정하며, 이 선택 문서만으로 기존 정본을 대체하지 않는다.

## 사람이 고를 필요가 없는 기술 기본 작업

선택 개수를 늘리지 않기 위해 다음은 구현 담당자가 책임질 작업으로 둔다. 필요하면 검토할 수 있지만, 기능을 켜고 끄는 설문 항목으로 만들지 않는다.

- 요청 DTO와 DB 엔티티를 분리하고 비밀번호·세션·토큰·불필요한 개인정보를 응답/로그에서 제외한다.
- 외부 요청의 작성자·권한·금액·승인 상태를 신뢰하지 않는다. 비밀번호는 검증 가능한 안전한 해시로 저장한다.
- 알 수 없는 필드, 필수 본문 누락, 잘못된 enum/날짜/정수와 허용되지 않은 PATCH를 검사한다. 명령 32개의 본문 필수 표기 누락 등 계약 결함을 고친다.
- DB 정수 금액·정확한 반올림·UTC 저장/KST 업무 날짜·불투명 식별자·정렬 안정성을 구현한다.
- MySQL 활성 키 유일성·부모 행 잠금·version·멱등 기록으로 중복 부작용을 막고, 실제 두 연결 테스트로 증명한다.
- 성공 변경·감사·outbox·멱등 완료를 함께 커밋한다. 메일/SSE는 커밋 뒤 전달하며 재전송을 고려한다.
- 마지막 사장님 제거·owner 위조·승인 대기 우회·타 지점 소속 삭제를 차단한다.
- 프로필/권한 version의 구체 매핑, 세션 만료 구현, DB 인덱스/잠금 순서는 선택된 정책에 맞춰 설계·테스트한다.
- 보호된 소속·행동 권한은 현재 DB 상태로 검사한다. 미구현 메뉴에 가짜 성공 응답을 넣지 않는다.

## 선택으로 해결할 수 없는 외부 확인 사항

| 확인할 사실                                   | 필요한 증거                                         | 아직 없을 때의 처리                                  |
|-----------------------------------------------|-----------------------------------------------------|------------------------------------------------------|
| DomainLens의 실제 배포 좌표·버전·DTO·정책 SPI | 공개 산출물과 compile/startup/계약 테스트           | 경계와 더블만 준비, AI readiness 비활성              |
| 엔진의 MySQL 업무 DB 지원                     | 실제 JPA 질의·권한·날짜/금액·매출 오라클 비교       | 호환 완료 표시 금지, 엔진 측 지원 확인               |
| 엔진 자체 저장소의 DB 요구                    | 실제 설정·마이그레이션·운영 계약                    | PRD의 PostgreSQL 샘플을 OpenStudy DB로 복사하지 않음 |
| MySQL의 정확한 패치·Debian 버전               | 실제 DB 버전, `/etc/os-release`, 패키지/이미지 정보 | `8.4.x`/Debian 계열만 확정, 세부 값은 미핀           |
| 실제 초대 이메일 수신                         | SMTP 설정 및 수신함의 링크로 수락/승인              | 더블/로컬 수신기 결과로만 기록                       |

예를 들어 ‘엔진이 MySQL을 지원하는 것으로 선택’한다고 호환성이 생기지 않는다. 사람이 결정할 정책과 실행으로 확인할 사실을 구분한다. 인프라나 모델 키가 없어도 M1의 업무 구현을 진행할 수 있지만, 필요한
실제 검증은 미완료로 남긴다.

## 선택 후 확정 절차

1. 기록표에 선택·이유·미정 조건을 남긴다.
2. 서로 맞지 않는 선택을 조정한다. 예: 인메모리 세션 선택과 재기동 후 로그인 유지 요구는 함께 충족되지 않는다.
3. ERD·권한표·상태/트랜잭션 표·API 변경 목록에 반영한다.
4. 성공·거절·동시 변경·재시도 테스트를 인수 조건으로 확정한다.
5. ‘선택 미확정’ 항목과 외부 미검증 항목을 구분하고 M1을 구현한다. 나중 선택은 해당 도메인 착수 전에 마무리한다.

결정을 바꿀 때는 기존 결정을 지우기보다 새 결정과 이유를 기록한다.
이전 [아키텍처 계획](../../../docs/development-log/2026-10-18-backend-architecture-plan.md)은 초기 제안의 근거이며, 이번 문서의 권장값 역시 사용자 선택
전에는 확정 정책이 아니다.

## 용어를 처음 접한다면

| 용어                | 이 프로젝트에서의 뜻                                                                    |
|---------------------|-----------------------------------------------------------------------------------------|
| 모놀리스            | 서버 프로그램 하나로 빌드·배포하는 구조                                                 |
| 모듈러              | 기능마다 소유 데이터와 공개 호출 경계를 정하고 서로의 내부 구현을 함부로 쓰지 않는 방식 |
| DTO                 | API에서 주고받는 데이터 모양. DB 객체를 그대로 노출하는 것과 다름                       |
| JPA 엔티티          | Java 객체와 DB 테이블을 연결하는 저장 모델                                              |
| port/adapter        | 필요한 기능의 약속과 실제 구현을 분리하는 경계. 예: 메일 발송 약속과 SMTP 구현          |
| 세션                | 서버가 보관하는 로그인 상태. 브라우저 쿠키에는 이를 찾는 식별자를 둠                    |
| CSRF                | 다른 사이트가 사용자 쿠키를 악용해 변경 요청을 보내지 못하도록 검증하는 장치            |
| version/낙관적 잠금 | 읽은 뒤 다른 사람이 수정했는지 번호로 확인하고 덮어쓰기 대신 충돌을 알리는 방식         |
| 트랜잭션            | 여러 DB 변경을 전부 성공시키거나 전부 취소하는 단위                                     |
| 멱등성              | 같은 사용자 요청을 재전송해도 결제·발급·승인을 중복 실행하지 않는 성질                  |
| outbox              | 업무 변경과 함께 ‘발송할 일’을 DB에 저장한 뒤 나중에 처리하는 방식                      |
| 테스트 더블         | 실제 메일/엔진 대신 성공·실패를 통제하는 시험용 구현. 실제 연동 성공의 증거는 아님      |
