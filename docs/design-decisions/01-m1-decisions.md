## M1-01 첫 마일스톤의 완성 범위

**대화에서 정한 진행 방식:** 작은 Task를 서브에이전트에 배정하고 주 에이전트가 검토·통합한다. 마일스톤은 전체 연결을 검증하는 단위로 유지한다. 정확한 첫 범위는 Task 분해 과정에서 조정하고 배정 전에
명시한다. 아래 A/B는 범위 후보로 남기며 아직 선택하지 않았다.

**무엇을 정하나:** 처음 개발해 사용자에게 보여 줄 완성 흐름의 크기다. 작은 M1도 권한·변경 충돌·테스트·live 연결을 생략하지 않는다.

| 선택   | 무엇을 만드는가                                                  | 얻는 점                                                                             | 감수할 점                                                                   |
|--------|------------------------------------------------------------------|-------------------------------------------------------------------------------------|-----------------------------------------------------------------------------|
| A 권장 | 인증·프로필·허용 지점 조회/등록/수정·최소 소속/권한 변경까지     | 다지점 보안과 업무 변경의 기반을 실제로 검증한다. 다음 초대/업무 기능이 바로 이어짐 | 계정·지점·소속과 감사/멱등까지 필요해 첫 완료까지 작업량이 큼               |
| B      | 첫 M1은 인증·프로필만 완성하고 지점·권한 편집은 다음 단계로 분리 | 쿠키·CSRF·로그인 화면 연결을 더 빨리 확인                                           | 실제 지점 운영 권한 시연은 뒤로 감. 후속 마일스톤 번호/선행을 재조정해야 함 |

**사례:** A는 ‘직원 A가 강남 관리자지만 성수 일반 직원이면 성수 설정 변경은 거절’을 첫 시연에서 보여 준다. B는 로그인·프로필 수정·만료/거절을 먼저 보여 주며 역할 차이는 시드 계정과 직접 호출로
확인한다.

**권장 이유:** 지점별 권한은 OpenStudy의 핵심이므로 A가 초기 설계 오류를 빨리 드러낸다. 첫 실행 환경의 준비 부담이 크면 B도 가능하다. B도 서버의 현재 계정/소속 검사와 프로필 version
경합을 포함한다.

**계약 영향:** 최종 기능 범위는 줄이지 않는다. B를 고르면 M1의 미구현 API를 가짜 성공으로 제공하지 않고 다음 완료 단위로 명시한다.

**다른 선택과의 연결:** A를 고르면 [NEXT-02](02-domain-decisions.md)의 소속·권한 저장 단위도 M1 해당 기능 구현 전에 결정한다. B를 고르면 조직 관리 단계까지 보류할 수 있다.

**통과 증거:** 선택된 흐름의 실제 HTTP·MySQL·live 브라우저 결과와 권한 거절·재시도·충돌 테스트.

선택: `범위 보류·진행 방식 확정` / 이유·조건: `서브에이전트에 배정할 작은 Task와 마일스톤 통합 검증을 구분한다. 정확한 범위는 Task 분해 과정에서 조정한다.`

## M1-02 모듈을 나누는 강도

**확정 결정:** 2026-10-18 사용자가 A를 선택했다. 한 빌드 프로젝트 안의 기능별 패키지로 모듈을 분리하고 ArchUnit으로 경계를 검사한다. 서브에이전트 Task에는 수정 가능한 모듈/파일과 공개
호출 경계를 명시한다. 빌드 도구는 M1-03에서 Gradle Groovy DSL, 업무/JPA 모델은 M1-04 A로 확정했다.

**무엇을 정하나:** ‘업무 모듈이 직원 모듈 내부 저장소를 직접 쓰면 안 된다’ 같은 경계를 무엇으로 지킬지다. 두 옵션 모두 하나의 서버로 배포하는 모듈러 모놀리스다.

| 선택   | 무엇을 말하나                                                                                                          | 얻는 점                                                                      | 감수할 점                                                                                               |
|--------|------------------------------------------------------------------------------------------------------------------------|------------------------------------------------------------------------------|---------------------------------------------------------------------------------------------------------|
| A 권장 | 하나의 빌드 프로젝트 안에서 identity/organization/work/chat 등 패키지를 나누고 ArchUnit으로 내부 접근·순환 의존을 검사 | 설정과 실행이 단순하고 변경을 빠르게 옮길 수 있음                            | 같은 프로젝트이므로 검사 규칙을 쓰지 않으면 경계를 쉽게 침범함                                          |
| B      | 모듈별 Maven/Gradle 하위 프로젝트를 만들고 명시한 의존성만 연결                                                        | 선언하지 않은 프로젝트 의존을 컴파일 단계부터 막고 모듈별 빌드 구성이 명확함 | 공개 API 분리·공통 모듈·빌드 설정과 테스트 조합이 늘어남. 모듈 안 클래스의 공개 범위 검사도 여전히 필요 |

**사례:** 결제 모듈이 고객을 확인할 때 공개 조회 서비스를 호출하는 것은 허용하지만 고객 Repository를 가져와 직접 수정하는 것은 막는다. A는 아키텍처 테스트, B는 프로젝트 의존 선언과 아키텍처
테스트를 함께 사용한다.

**권장 이유:** 혼자 개발하는 초기 단계에는 A가 적합하다. 모듈 폴더만 만드는 것으로 끝내지 않고 실제로 실패하는 의존성 검사를 작성한다. B가 마이크로서비스를 의미하거나 자동으로 좋은 경계를 보장하는 것은
아니다.

**계약 영향:** HTTP 변경 없음. ‘단일 빌드 안의 기능별 패키지’를 채택한다. 실제 패키지와 의존성 검사 구현은 후속 Task로 수행한다.

**통과 증거:** 다른 모듈 내부 접근과 순환 의존을 일부러 넣었을 때 빌드 검사가 실패한다.

선택: `A 확정` / 이유·조건: `한 빌드 프로젝트의 기능별 패키지, ArchUnit 경계 검사, Task별 수정 범위 명시. 2026-10-18 사용자 선택.`

## M1-03 서버 기술 제안과 빌드 도구

**확정 결정:** 2026-10-18 사용자가 `build.gradle` 방식을 선택했다. B를 **Gradle Wrapper + Groovy DSL**로 확정한다. 최초 제안의 Kotlin DSL에서 사용자
선호에 맞게 바꿨으며 `build.gradle.kts`와 `pom.xml`을 병행 관리하지 않는다. 정확한 Wrapper 버전·서버 의존성·엔진 호환성은 실제 빌드로 확인한다. 이번 선택은 빌드 도구/설정 문법에
대한 결정이며 M1-04의 모델 설계나 미검증 라이브러리 호환성까지 확정하지 않는다.

**무엇을 정하나:** Java 코드를 컴파일하고 의존성을 내려받고 테스트를 실행하는 도구다. 공통 제안은 Java 21·Spring Boot 4.1.1·WebMVC·JPA이며, 아래 두 옵션의 차이는 빌드 도구다.
공통 제안 자체에 다른 요구가 있으면 별도 조건을 적는다.

| 선택   | 무엇을 말하나                                             | 얻는 점                                                             | 감수할 점                                                                           |
|--------|-----------------------------------------------------------|---------------------------------------------------------------------|-------------------------------------------------------------------------------------|
| A 권장 | Maven Wrapper, pom.xml                                    | DomainLens PRD의 예제와 맞고 XML의 의존성·빌드 단계를 따라가기 쉬움 | 설정이 장황할 수 있고 복잡한 빌드 로직은 다루기 번거로움                            |
| B      | Gradle Wrapper, Groovy DSL (`build.gradle`) — 사용자 확정 | 빌드 설정을 코드처럼 작성하고 작업 구성을 유연하게 다룰 수 있음     | Gradle/Groovy DSL과 플러그인 호환성을 함께 익혀야 함. 엔진의 Maven 예제를 옮겨야 함 |

**사례:** A는 Windows에서 `mvnw.cmd verify`, B는 `gradlew.bat check`를 프로젝트가 제공한 Wrapper로 실행한다. 개발자 컴퓨터마다 다른 전역 빌드 도구를 설치하는 차이를
줄인다. 명령은 구현 후 제공할 계획이며 현재 실행 성공을 뜻하지 않는다.

**권장 이유:** 엔진 연결과 학습 부담을 줄이는 A를 제안한다. 이미 Gradle 사용 경험이 많다면 B가 더 편할 수 있다. 어느 쪽도 일반 API가 더 빨라지는 선택은 아니다.

**계약 영향:** HTTP 변경 없음. Boot의 하위 의존성 버전을 임의로 각각 올리지 않고 BOM과 실제 dependency 결과를 기록한다. 실제 엔진 산출물 수령 후 호환성을 확인한다.

**통과 증거:** JDK 21로 깨끗한 환경에서 의존성 해결·컴파일·테스트·서버 기동. 선택하지 않은 빌드 설정을 병행 관리하지 않음.

선택: `B 확정 (Groovy DSL)` / 공통 기술 제안에 대한 조건:
`Gradle Wrapper + build.gradle. 2026-10-18 사용자 선택. 서버 의존성/실제 엔진 호환성은 빌드 검증 대기.`

## M1-04 업무 모델과 JPA 저장 모델

**확정 결정:** 2026-10-18 사용자가 A를 선택했다. 모듈 내부의 JPA 엔티티가 업무 상태·규칙과 DB 저장을 함께 담당한다. API 입력과 출력은 별도 요청/응답 DTO를 사용한다. 사용자는 Task를
저장 객체로 사용하고 DTO를 별도로 만드는 구조인지 확인한 뒤 채택했다.

**무엇을 정하나:** `Employee` 같은 Java 객체가 업무 규칙과 DB 매핑을 함께 가질지, 별도 객체 두 벌로 나눌지다. 두 옵션 모두 API DTO는 따로 두고, 다른 모듈이 저장 엔티티를 직접
수정하지 못하게 한다.

| 선택   | 무엇을 말하나                                                                       | 얻는 점                                               | 감수할 점                                                                                                      |
|--------|-------------------------------------------------------------------------------------|-------------------------------------------------------|----------------------------------------------------------------------------------------------------------------|
| A 권장 | 모듈 내부의 JPA 엔티티에 상태 변경 규칙을 두고 서비스가 여러 원본의 트랜잭션을 조율 | 객체 변환과 중복 코드가 적어 1인 개발에 수월함        | 업무 모델이 JPA 매핑 조건의 영향을 받음. controller에 엔티티를 노출하거나 setter로 규칙을 우회하지 않도록 주의 |
| B      | 순수 업무 객체와 JPA 엔티티를 분리하고 adapter가 서로 변환                          | 업무 규칙을 저장 기술과 독립적으로 읽고 시험하기 좋음 | 객체·매핑·version 동기화가 늘고 단순 기능에도 보일러플레이트가 생김                                            |

**사례:** A는 직원 엔티티의 `restrict()` 같은 메서드로 제한 상태를 바꾼다. B는 순수 Employee를 변경한 뒤 저장 어댑터가 JPA 엔티티에 반영한다. 어느 쪽이든 권한 검사와 감사 기록은
필요하다.

**권장 이유:** 지금 규모에는 A로 시작하되 복잡한 계산·정책은 별도 클래스로 분리하는 편이 실용적이다. B를 선택해도 DomainLens가 읽을 실제 JPA 메타모델은 제공해야 하며 엔진 내부를 복제하지
않는다.

**계약 영향:** HTTP 변경 없음. 모듈 내부 구조와 테스트 형태가 달라진다.

**통과 증거:** 상태 변경 우회 금지, 엔티티의 민감 필드 미노출, 업무 규칙 단위 테스트와 JPA 매핑 통합 테스트.

**구현 흐름:** `CreateTaskRequest/UpdateTaskRequest → Service → Task 생성·변경/DB 저장 → TaskResponse`. Task의 상태 변경은
`complete()` 같은 의도를 드러내는 메서드를 사용하고, 여러 원본의 권한 검사·트랜잭션·감사는 서비스에서 조율한다. 엔티티를 controller의 요청/응답으로 직접 사용하지 않는다. 복잡한 계산·정책은
필요에 따라 별도 클래스로 분리한다.

선택: `A 확정` / 이유·조건: `모듈 내부 JPA 엔티티와 별도 API 요청·응답 DTO. 2026-10-18 사용자 선택.`

## M1-05 세션 저장 위치

**확정 결정:** 2026-10-18 사용자가 A를 선택했다. Spring Session JDBC로 로그인 세션을 MySQL 8.4에 저장한다. MySQL용 세션 DDL·만료 정리와 유효 세션의 재기동 후
유지·폐기된 세션의 접근 거절을 구현/검증한다. 세션 유효시간은 M1-06 B, 권한 변경 후 로그인 처리는 M1-07 A로 확정했다.

**무엇을 정하나:** 쿠키가 가리키는 로그인 상태를 서버 메모리에 둘지 MySQL에 둘지다. 쿠키에는 비밀번호나 전체 권한 목록을 넣지 않는다.

| 선택   | 무엇을 말하나                      | 얻는 점                                                                        | 감수할 점                                                                |
|--------|------------------------------------|--------------------------------------------------------------------------------|--------------------------------------------------------------------------|
| A 권장 | Spring Session JDBC로 MySQL에 저장 | 서버 재기동 때도 유효한 세션을 유지할 수 있고 세션을 영속적으로 조회/폐기 가능 | 세션 테이블·만료 정리·DB 접근과 직렬화 호환성 관리가 필요                |
| B      | 서버 프로세스 메모리에 저장        | 초기 설정이 단순하고 세션 때문에 DB에 접근하지 않음                            | 서버 재기동 시 전원 재로그인. 프로세스 여러 개로 확장하면 별도 대책 필요 |

**사례:** 서버를 재기동하면 A는 만료되지 않은 로그인을 유지할 수 있고 B는 다시 로그인해야 한다. A도 로그아웃/계정 제한으로 폐기한 세션이 살아나는 것은 허용하지 않는다.

**권장 이유:** 별도 Redis 구축 없이 재기동 시연까지 다루기 쉬운 A를 제안한다. 단일 프로세스·재로그인을 명시한 시연이면 B도 가능하다. A가 무중단 배포나 모든 버전 간 세션 호환을 자동 보장하지는
않는다.

**계약 영향:** HTTP·HttpOnly 쿠키·CSRF 방식은 유지한다. B면 기존 계획의 ‘세션 JDBC 검증’을 제거하고 ‘재기동 시 세션 만료’를 기대값으로 고친다. 거래/멱등/감사 기록은 B여도 DB에
보존한다.

**통과 증거:** 재기동·로그아웃·유휴 만료·회수 시험. sessionStore에 저장된 권한을 현재 DB 권한 대신 신뢰하지 않음.

선택: `A 확정` / 이유·조건: `Spring Session JDBC + MySQL 저장. 2026-10-18 사용자 선택. 실제 저장/재기동/만료 동작은 구현 후 검증.`

## M1-06 세션 유효시간

**확정 결정:** 2026-10-18 사용자가 B를 선택했다. 유휴 60분, 인증 후 최대 12시간 중 먼저 도달한 시점에 세션을 만료한다. 실제 서버 Clock으로 판단하며 서버 재기동으로 기존 세션의 인증

| 선택   | 의미                    | 얻는 점                                               | 감수할 점                                                   |

| A      | 유휴 30분, 최대 8시간   | 공유 PC를 방치했을 때 접근 가능한 시간을 더 짧게 제한 | 쉬었다 돌아오는 직원이 자주 로그인할 수 있음                |

**사례:** 09시에 로그인하고 10시에 마지막으로 사용한 뒤 자리를 비우면 A는 10:30, B는 11:00, C는 12:00에 유휴 만료한다. 계속 사용해도 최대 시간은 별도로 적용한다.

**권장 이유:** B를 시작값으로 두고 실제 시연/근무 흐름에 따라 조정한다. 이 값은 성능 목표나 법정 기준이 아니다. SSE heartbeat·자동 재접속/백그라운드 요청만으로 무기한 로그인 연장이 되지 않게

**계약 영향:** 만료 시 기존 401·로그인 복귀·캐시 정리 흐름 유지. 환경 설정값과 사용자 안내를 추가한다. 요청 당시 이미 인증/권한을 통과한 실행의 취소 여부는 별도 업무 상태 규칙을 따른다.

**통과 증거:** 제어 가능한 Clock으로 각 경계 직전/정각/직후, 활동/비활동, SSE만 열린 상태, 최대 시간 경과를 검사한다.

## M1-07 권한 변경 후 사용자 경험

**확정 결정:** 2026-10-18 사용자가 A를 선택했다. 일반 소속/행동 권한 변경은 로그인 상태를 유지하고 현재 DB 권한을 즉시 재평가한다. 회수 커밋 후 권한 검사를 받는 새 요청·SSE 전달·저장 AI
결과 재조회에 변경을 적용한다. 권한 밖 캐시/화면과 스트림은 정리하고, 남아 있는 허용 지점 업무는 계속할 수 있다. 계정 제한·퇴사·비활성화는 세션과 스트림을 폐기한다.

**무엇을 정하나:** 관리자가 직원의 지점/행동 권한을 바꿨을 때 직원의 로그인도 끊을지다. 모든 옵션에서 회수 커밋 후 새로 권한 검사를 받는 요청은 즉시 새 정책을 적용한다. 계속 열린 SSE와 저장 AI
결과도 재평가한다.

| 선택   | 의미                                                             | 얻는 점                                                        | 감수할 점                                                                      |
|--------|------------------------------------------------------------------|----------------------------------------------------------------|--------------------------------------------------------------------------------|
| A 권장 | 계정은 로그인 상태를 유지하고 현재 권한으로 화면·API를 다시 판단 | A지점 권한이 바뀌어도 B지점의 허용 업무를 계속할 수 있음       | 프론트의 권한/캐시 갱신과 스트림 종료·재연결을 꼼꼼히 구현해야 함              |
| B      | 해당 직원의 모든 로그인 세션을 폐기하고 재로그인 요구            | 사용자에게 보이는 권한 전환이 명확하고 오래된 화면 정리가 단순 | 작은 권한 추가/회수에도 여러 기기에서 업무가 끊기며 작성 중 입력을 보존해야 함 |

**사례:** 성수점 결제 권한만 회수하면 A는 강남 업무를 계속하되 성수 결제 요청이 거절되고, B는 전 기기에서 로그인부터 다시 한다.

**권장 이유:** 다지점 업무에 맞는 A를 제안한다. 계정 제한·퇴사·비활성화는 옵션과 무관하게 보호 업무를 차단하고 세션/스트림을 폐기한다. 화면 갱신이 늦어도 서버가 회수 권한을 허용해서는 안 된다.

**계약 영향:** 확정한 A에 맞춰 현재 OpenAPI 쿠키 설명/생성기의 ‘권한 변경 시 회전’을 일반 권한 변경의 로그인 유지+즉시 재평가 정책으로 정리해야 한다. 로그인 시 세션 ID 회전과 계정
제한/비활성화 시 세션 폐기는 유지한다. 이번에는 선택 문서를 갱신했으며 API 정본/생성기 개정과 구현은 후속 작업으로 추적한다. 이미 진행 중인 변경과 회수가 경합하는 경우도 서버의 권한 검사/트랜잭션 경계로
정의한다.

**통과 증거:** 로그인된 두 브라우저에서 회수·직접 API·SSE·캐시·다른 허용 지점 동작을 함께 확인한다.

선택: `A 확정` / 이유·조건: `로그인 유지+즉시 권한 재평가. 계정 제한·퇴사·비활성화는 강제 종료. 2026-10-18 사용자 선택.`

## M1-08 로그인 이메일 ID 변경 금지

**최신 확정 결정:** 2026-10-18 사용자가 이메일을 로그인 ID로 사용하며 변경 기능을 제공하지 않도록 명시했다. 이전 A (이메일 변경 전 비밀번호 확인)와 B (최근 인증 재사용)는 모두 철회하고 선택
대상에서 제외한다.

**적용 범위:** 최초 계정 생성 후 사장님·관리자·직원 모두 로그인 이메일을 변경할 수 없다. 설정에서 ID를 읽기 전용으로 표시하고 관리자 직원 수정에서도 입력을 제거한다. 로그인·초대 생성·수락의 이메일
입력과 조회 응답은 유지한다. 고객 원장의 연락용 이메일은 로그인 ID가 아니므로 이 제한을 확대하지 않는다.

**사례:** 본인이 프로필 요청에 다른 이메일을 넣거나 관리자가 직원 수정 요청에 email을 넣어도 거절한다. 같은 이메일을 보내는 경우도 허용하지 않는다. 닉네임/사진과 직원 이름/재직 상태는 기존 권한에 따라
변경할 수 있다.

**계약 영향:** 프로필 요청은 nickname/avatar만 허용하고 직원 PATCH에서도 email을 제외한다. email이 들어온 요청은 422 VALIDATION_ERROR로 거부하며 다른 필드도 부분
저장하지 않는다. 이메일 변경·재인증·확인 메일 기능을 추가하지 않는다. 기존 v1.0의 수정 허용
문구는 [최신 정책](../../../docs/revised/2026-10-18/email-login-id-policy.md)이 대체한다.

**통과 증거:** 본인/관리자 직접 변조와 동일값 전송 거절, 원본 계정/다른 입력 필드 보존, 닉네임/이름의 정상 수정, 설정 읽기 전용 표시. 프론트/MSW 시험과 실제 백엔드/DB 검증을 구분한다.

선택: `변경 금지 확정` / 이유·조건: `로그인 이메일을 변경 불가 ID로 사용. 이전 A/B와 관련 변경 기능 철회. 2026-10-18 사용자 최신 결정.`

## M1-09 프로필 수정의 충돌 검사

**확정 결정:** 2026-10-18 사용자가 A를 선택했다. 프로필 수정에도 기존 직원 version을 사용한다. 프로필 전용 profileVersion은 추가하지 않는다. 직원 정보 변경으로 인한 충돌 가능성을
수용하며 오래된 version은 409로 거절하고 작성 입력을 보존해 최신 정보 확인 후 재저장하도록 한다. 이메일은 M1-08에 따라 변경 불가다. API/프론트 개정과 실제 DB 동시 수정 검증은 후속 구현
작업이다.

**무엇을 정하나:** 두 화면이 같은 프로필을 수정할 때 이전 입력으로 최신 값을 덮어쓰지 않도록 검사할 번호다. 충돌 감지 자체는 유지하고 번호의 단위를 선택한다.

| 선택   | 의미                                                     | 얻는 점                                             | 감수할 점                                                                 |
|--------|----------------------------------------------------------|-----------------------------------------------------|---------------------------------------------------------------------------|
| A 권장 | `/me`의 기존 직원 version을 프로필 변경에도 전달         | DTO/테이블 추가가 적고 일반 변경과 같은 사용법      | 관리자가 소속을 바꿔도 직원 version이 오르면 닉네임 저장이 충돌할 수 있음 |
| B      | 프로필에 별도 profileVersion을 두고 프로필끼리 충돌 검사 | 소속 변경과 프로필 변경이 서로 불필요하게 막지 않음 | 버전 필드·모델·응답/타입 매핑이 추가되고 의미를 구분해야 함               |

**사례:** 직원이 사진을 고르는 동안 관리자가 지점 배정을 바꾸면 A는 최신 상태를 다시 확인하도록 할 수 있고 B는 사진 수정을 그대로 저장할 수 있다. 계정 상태와 수정 권한 검사는 두 방식 모두 별도로
수행한다.

**권장 이유:** A로 시작해 불필요한 충돌이 실제로 잦으면 B로 분리하는 것이 단순하다. 로그인 조회만 했다고 직원 version을 올리지는 않는다.

**계약 영향:** 현재 프로필 PATCH에 version이 없으므로 어느 옵션이든 요청/응답과 프론트 변경이 필요하다. A는 version 필수화, B는 profileVersion 노출과 필수화다. 409에서 입력
보존·최신값 확인 후 재저장을 지원한다.

**통과 증거:** 두 브라우저의 같은 프로필 수정, 소속 변경과 동시 수정, 오래된 version 재전송과 멱등 응답 재생을 구분한다.

선택: `A 확정` / 이유·조건: `기존 직원 version 재사용. 불필요한 충돌 가능성을 수용하고 구조를 단순하게 유지. 2026-10-18 사용자 선택.`

선택: `A 확정` / 이유·조건: `전용 초기화 명령으로 최초 사장님 생성. 일반 서버 기동과 분리하고 중복 생성·기존 비밀번호 덮어쓰기 금지. 2026-10-18 사용자 선택.`

## M1-11 Git 저장소 단위

**확정 결정:** 2026-10-18 사용자가 Organization을 이용한 멀티 레포 관리를 선택했다. B를 Organization 아래 프론트/백엔드 저장소를 분리하는 방식으로 확정한다. 후속 선택으로 공통
요구사항·API 정본·개발 기록은 별도 openstudy-docs 저장소에 관리하고 백엔드 전용 문서는 backend docs에 유지한다. Organization/원격 주소·공개 범위와 실제 이동 절차는 별도
결정이다. 이번에는 원격 저장소 생성과 문서 이동을 수행하지 않았다.

**무엇을 정하나:** 현재 확인된 Git 저장소가 없으므로 어떤 폴더를 변경 이력의 단위로 삼을지다. 이 문서 작성 중에는 Git을 초기화하지 않았다.

| 선택   | 의미                                                              | 얻는 점                                                 | 감수할 점                                                                                |
|--------|-------------------------------------------------------------------|---------------------------------------------------------|------------------------------------------------------------------------------------------|
| A 권장 | OpenStudy 루트 한 저장소에 frontend/backend/공통 docs를 함께 관리 | API 변경·프론트 수정·문서가 한 PR/커밋 흐름으로 추적됨  | 변경량이 함께 보이므로 작업 단위와 불필요한 산출물 제외 규칙을 잘 관리해야 함            |
| B      | backend를 별도 저장소로 관리                                      | 백엔드 빌드/배포/포트폴리오 이력을 독립적으로 보기 쉬움 | 루트 API 문서·프론트와 버전이 어긋날 수 있어 기준 문서 버전/동기화 책임을 따로 정해야 함 |

**사례:** 프로필에 version을 추가할 때 A는 정본·Java·React 변경을 함께 검토한다. B는 각 저장소의 변경과 호환 버전을 연결해서 기록한다.

**권장 이유:** 이미 공통 요구사항/API/프론트가 한 루트에 있으므로 A가 편하다. B를 택하면 현재 루트의 개발 기록도 어느 저장소가 추적할지 확정한다. Git 원격 주소·공개 범위는 이 선택만으로 정해지지
않는다.

**계약 영향:** HTTP 변경 없음. 사용자 선택 후 초기화 또는 실제 기존 원격 연결을 수행하며 main 직접 작업 금지 지침을 적용한다. 별도 DomainLens 저장소를 OpenStudy 안에 복제한다는
뜻이 아니다.

**통과 증거:** 선택 범위가 추적되고 비밀값·node_modules·빌드/테스트 산출물은 제외된다. 기능 작업 브랜치 규칙을 적용할 수 있음.

선택: `B 확정 (Organization 멀티 레포)` / 원격·문서 추적 조건:
`추가로 공통 문서 A(별도 openstudy-docs 저장소) 확정. 백엔드 전용 설계는 backend docs 유지. 원격 주소·공개 범위 및 실제 문서 이동은 후속 작업. 2026-10-18 사용자 선택.`

## M1-12 실제 MySQL 자동 테스트 환경

**확정 결정 변경 (2026-10-19):** 사용자 요청에 따라 기존 B안(같은 서버의 전용 테스트 DB)에서 **A안: Docker 전용 MySQL 8.4 테스트 DB**로 전환한다. 자동 DB 테스트는 Testcontainers로 수명주기와 접속 정보를 관리하고, 수동 SQL 검증도 별도 Docker 컨테이너에서 수행한다. 개발·시연 DB로 자동 대체하지 않으며 테스트가 생성한 컨테이너·볼륨·데이터만 정리한다. MySQL 8.4(Debian)/InnoDB 운영 기준은 유지하고 컨테이너 이미지의 실제 OS·DB 버전·digest를 기록해 Debian 운영 환경 검수와 구분한다.

같은 테스트 트랜잭션의 기본 CRUD는 롤백한다. HTTP 서버 스레드·독립 연결·경합·커밋 후 outbox 검증은 별도 격리와 정리를 병행한다. V1 SQL의 Docker MySQL 8.4.11 적용·42개 수동 검증 이후 Testcontainers·테스트 프로필·Flyway 재실행·앱/세션 기반 통합 검증 32개도 통과했다. 현재 결과와 후속 범위는 [검증 보고서 v1.0](../verification/database-initialization-v1.0.md)에 기록했다. Docker가 없으면 관련 검증은 미실행/실패로 남긴다.

**이전 결정:** 2026-10-18 B안을 선택했으나 2026-10-19 사용자 결정으로 대체했다. 검토 당시의 선택지는 아래에 보존한다.

**무엇을 정하나:** 마이그레이션·잠금·두 연결 경합을 확인할 시험용 MySQL을 어떻게 확보할지다. H2나 MSW만으로 통과시키는 옵션은 없다.

| 선택   | 의미                                                                                   | 얻는 점                                           | 감수할 점                                                                          |
|--------|----------------------------------------------------------------------------------------|---------------------------------------------------|------------------------------------------------------------------------------------|
| A 권장 | Testcontainers로 격리된 MySQL 8.4를 띄워 시험하고, 지정 Debian 환경에서 별도 실행 검수 | 테스트끼리 데이터가 섞이지 않고 새 DB 재현이 쉬움 | Docker 엔진이 필요하고 컨테이너 기동 시간·이미지 관리가 추가됨                     |
| B      | 지정된 Debian/MySQL 8.4의 전용 테스트 DB를 사용                                        | Docker 없이 실제 지정 환경을 직접 검증            | 격리·초기화·동시 실행·테스트 전용 계정을 관리해야 하며 환경에 따라 재현성이 달라짐 |

**사례:** 같은 좌석을 두 연결이 동시에 배정하는 테스트를 반복할 때 A는 격리된 컨테이너에서, B는 별도 테스트 DB에서 수행한다. B는 개발 데이터·실제 운영 데이터가 있는 DB를 초기화 대상으로 쓰면 안
된다.

**변경 이유:** Docker 엔진 실행과 격리 컨테이너의 V1 SQL 검증을 확인했다. 반복 가능한 독립 DB 생성·정리가 가능한 A안을 채택한다. 컨테이너의 MySQL 8.4 표기만으로 Debian 기반이라고 주장하지 않고 실제 OS·DB 버전을 확인한다.

**계약 영향:** HTTP 변경 없음. 인프라 구축 프로젝트를 추가하는 선택이 아니라 개발 검증 환경의 선택이다. 실제 DB를 실행하지 못하면 관련 검증은 미실행으로 남기고 M1 완료로 표시하지 않는다.

**통과 증거:** migrate/seed·두 연결 경합·롤백·데드락/재시도·UTC·collation 확인. 실제 버전과 실행 명령을 기록하며 코드/더블 시험과 구분한다.

선택: `A 확정 (2026-10-19 변경)` / 실제 테스트 환경 조건:
`Docker 전용 MySQL 8.4/InnoDB, 자동 테스트 Testcontainers. CRUD 롤백과 HTTP/경합/커밋 후 정리 병행. 개발 DB 오접속 차단, 이미지/OS/digest 기록, Debian 운영 검수 별도. 자동 테스트 기반 연동 검증 완료; 업무별 경합은 후속.`
