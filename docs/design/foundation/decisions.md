### Q1. 승인 대기 인증과 기존 직원의 추가 지점 초대

- 검토한 논점: FR-AUTH-02는 활성 계정에만 세션을 발급한다고 정의하지만 FR-AUTH-04·INV-08은 승인 대기자가 상태 확인·로그아웃을 할 수 있어야 한다. FR-INV-06의 승인 전 업무 금지를 기존 직원의 다른 유효 소속에도 적용할지는 명시하지 않았다.
- 확정: 신규 `PENDING` 직원에는 `APPROVAL_ONLY` 제한 세션을 발급한다. 상태 조회·CSRF·로그아웃만 허용하고 `/me`도 업무 정보 없이 제한된 본인 정보만 반환한다. 업무 세션과 승인 조회용 제한 세션을 구분한다.
- 승인 후 재로그인은 초기 구현 선택이었고, 후속 답변 Q10에서 사용자 정책으로 확정했다. 재로그인으로 업무 세션을 발급하고 세션 ID·CSRF를 교체하며 자동 승격은 제공하지 않는다.
- 기존 `ACTIVE` 직원은 자기 계정으로 로그인한 뒤 추가 지점 초대를 수락한다. 해당 소속만 `PENDING`이고 기존 유효 지점 업무는 유지한다. 승인 조회는 본인 초대만 반환한다.
- 검토한 대안(미선택): 별도의 승인 조회 자격을 사용하거나, 초대 승인 전 모든 업무를 막는다. 후자는 기존 활성 직원의 유효 지점 업무도 중단시킨다.
- 반영 대상: 제한 세션 분류, login/me/accept/approval-status, 계정·소속 활성화 조건. 원본 SRS 문구 동기화 대상은 아래에 정리한다.

### Q2. 기간권의 시작일·종료일 결정 시점

- FR-PROD-02는 기간권의 유효 시작·종료 및 기간 검증을 요구하지만 상품에 고정 날짜를 두는지, 발급 시 정하는지 명확하지 않다.
- 확정: 상품에는 `period_days`를 저장하고 실제 시작일·종료일은 구매·발급 때 결정한다. ‘30일권’은 구매자마다 시작일이 다를 수 있다. 이번 상품 API에는 고정 시작·종료일을 받지 않는다.
- 구현 선택: 시작일을 `valid_from`, 종료를 `valid_from + period_days`의 배타 경계로 표현한다. 발급 시 시작일 입력·기본값과 실제 만료 시각 계산은 후속 발급 설계에서 구체화한다.
- 검토한 대안(미선택): 상품에 고정 `valid_from`·`valid_until` 날짜를 저장한다. 이 경우 기간·날짜 일치 CHECK와 판매 가능한 시점 검증, 상품 요청·응답 필드 및 이력 스냅샷이 추가로 필요하다.
- 시간권·정액권의 `validDays=null`은 무기한이며 0으로 대신하지 않는다. 실제 발급·차감·만료 계산의 상세 정책은 발급 이용권 요구사항 검토 때 확정한다.
- 반영 대상: 상품 유형 스키마·DB CHECK·프론트 폼. 후속 발급 설계는 확정한 ‘상품 일수·발급 시 날짜 결정’ 정책을 따른다.

### Q3. 여러 지점에 영향을 주는 직원 공통 정보 변경

- FR-STAFF-03은 관리자의 이름·계정 상태 변경을 허용하지만, 지점 관리자가 다지점 직원의 계정 전체를 정지시킬 수 있는지 명확하지 않다.
- 확정: 이름·전역 계정 상태 변경은 `OWNER`만 허용한다. 지점 관리자는 자기 관리 지점의 소속·역할·행위 권한만 변경한다. 계정 전체 상태와 한 지점의 소속 회수는 별도 명령으로 구분한다.
- 검토한 대안(미선택): 대상 직원의 모든 소속 지점에 관리 권한이 있을 때 공통 정보 변경을 허용한다. 이 경우 대상 소속 추가·회수와 공통 수정의 경합을 같은 잠금 규칙으로 처리해야 한다.
- 반영 대상: 직원 PATCH 권한, UI 편집 가능 여부, 전역 상태 변경의 세션 폐기. 권한 부족은 403, 로그인 이메일·owner 필드 수정 시도는 422.

| ID | 질문 | 확정 내용 |
| --- | --- | --- |
| Q4 | 지점 관리자의 권한 위임 범위 | 지점 관리자는 자기 관리 지점의 일반 직원만 관리한다. 지점 관리자 임명·권한 변경·승인은 OWNER만 처리한다. 지점 관리자는 자기 권한을 직접 변경하거나 전역 소유권을 부여할 수 없다. |
| Q5 | 최초 기본 권한 프리셋 | 일반 직원 기본 프리셋의 행위 권한은 빈 집합. 지점·상품 기본 조회만 가능하며 결제·매출·AI 등은 자동 허용하지 않는다. 지점 관리자 기본 프리셋은 담당 지점의 9종 업무 권한 전부다. OWNER는 사용자 정의 프리셋과 직원별 권한을 조정할 수 있다. |
| Q6 | 상품 업무 권한 | 운영 변경 권한이 있는 일반 직원도 상품 등록·가격·구성을 수정할 수 있다. 지점 신규 등록·공통 상품 분류 코드 관리는 OWNER만, 판매 중지·재개·적용 지점 변경은 해당 관리자 권한으로 처리한다. |

### 적용 경계

- Q4의 대상 역할은 **변경 전과 변경 후 모두** 검사한다. 지점 관리자가 다른 MANAGER를 STAFF로 낮춘 뒤 권한을 바꾸거나, STAFF를 MANAGER로 승격하는 우회를 허용하지 않는다. 대상 지점에서 MANAGER인 소속은 회수도 OWNER만 수행한다. 다른 지점의 역할은 현재 지점 판단에 사용하지 않으며 타 지점 소속을 변경하지 않는다.
- 지점 관리자는 `people:manage`와 유효 관리 소속을 가져야 일반 직원 소속·권한을 변경할 수 있다. OWNER 계정은 지점 관리자의 일반 직원 관리 대상이 아니다. 계정 이름·전역 상태는 앞서 확정한 Q3대로 OWNER만 변경한다.
- MANAGER로 초대하는 생성·재발급·취소·반려·최종 승인은 OWNER만 수행한다. 지점 관리자는 STAFF 초대만 처리한다. 승인·소속 수정 시 현재 대상 소속을 다시 확인해 초대 당시 역할만으로 Q4를 우회하지 못하게 한다. 읽기 목록의 기존 지점 범위는 유지한다.
- Q5의 기본 프리셋은 초기 seed이며 저장된 모든 직원의 권한을 매번 자동으로 덮어쓰는 규칙이 아니다. 기존의 ‘적용 시 복사·개별 조정·명시적 재적용’ 결정을 유지한다. 일반 직원의 기본 조회에는 결제·매출·AI 조회를 포함하지 않는다.
- Q6의 업무 권한과 상품 공유·삭제·유형 정책은 별개이며, 후속 답변으로 아래 Q7~Q9를 확정했다.
- 원본 SRS 동기화 시 FR-STAFF-04/10, FR-INV-02/07에 대상 역할 제한·초기 프리셋을 명시하고 FR-BR-03·FR-PROD-02~07에 업무별 권한을 연결한다.

| Q10 | 최종 승인 후 업무 진입 | 신규 직원은 다시 로그인한 뒤 업무 화면에 진입한다. 승인 조회용 세션을 자동 업무 세션으로 전환하지 않는다. |
| Q11 | 회수한 지점 소속 복구 | 기존 계정·비밀번호로 재초대 → 본인 수락 → 최종 승인을 거친다. 관리자 역할의 복구는 OWNER만 처리한다. |
| Q12 | 수동 재발급의 초대 기한 | 수동 재발급 시점부터 새24시간을 부여한다. 자동 메일 재시도는 기존 만료 시각을 유지한다. 수락이 끝난 승인 대기는 별도 기한 없이 유지한다. |

Q11은 계정 전체의 SUSPENDED/LEFT 상태를 초대만으로 되살리는 경로가 아니다. 필요한 계정 상태 변경은 Q3의 OWNER 전역 명령으로 분리한다. Q12의 재발급은 미수락 PENDING 또는 EXPIRED에 한하며, 만료 초대를 다시 유효하게 만들 때도 동일 이메일·지점의 다른 진행 초대가 없어야 한다. 수락·승인·취소·거절 상태는 재발급할 수 없다.

## 이번 설계의 기술 선택

| ID | 선택 및 이유 |
| --- | --- |
| D1 | 기존 V1과 식별자를 보존하고 후속 Flyway로 확장한다. 이미 기동한 개발 DB와 미래 참조를 깨뜨리지 않기 위해 V1을 다시 쓰지 않는다. |
| D2 | ID는 JSON 문자열, DB는 BIGINT UNSIGNED. API `version = DB version + 1`을 유지하고 쓰기 시 역변환한다. 현재 프론트의 양수 version 및 JS 정밀도를 고려한다. |
| D3 | API 상태·역할은 현재 화면의 한국어 상태와 `admin/staff`를 유지한다. DB의 ENUM과 DTO 경계를 명시한다. 상품 입력은 기존 범용 amount/days 대신 유형별 단위를 명시한다. |
| D4 | 확정 정책 Q7에 따라 상품은 공유 원본 + 판매 지점 연결 테이블로 관리한다. 조회 시 허용 지점만 반환하고 공유 원본 수정에는 현재·변경 후 모든 적용 지점 권한을 요구한다. 일부 지점 권한으로 타 지점 상품을 수정하는 우회를 막는다. |
| D5 | 상품 변경은 별도 불변 revision에 전체 조건·적용 지점·분류를 기록한다. 일반 감사 로그의 보존 정책과 상품 이력 조회·구매 스냅샷의 수명을 분리한다. |
| D6 | 초대는 이메일·지점별 진행 건 유일성, 일회성 해시·revision, 행 잠금으로 제어한다. 메일 전송과 DB 트랜잭션은 outbox로 분리하며 발송 성공을 승인으로 취급하지 않는다. |
| D7 | 관리자 보호 변경은 고정된 관리자 가드 행을 먼저 잠근다. 서로 다른 계정에 대한 동시 회수로 관리자 0명이 되는 쓰기 편향을 막는다. OWNER도 활성 계정이어야 유효 관리자다. |
| D8 | 등록 재전송에는 영속 멱등 저장소, 초대 승인·취소 등에는 버전·상태 전이를 사용한다. 인증·인가·CSRF 재검증 후에만 저장된 결과를 재사용한다. 비밀번호·토큰 요청/응답은 저장하지 않는다. |
| D9 | SSE는 데이터 본문을 전달하지 않는 무효화 알림이다. 커밋과 같은 트랜잭션의 outbox, 전달 직전 현재 권한 검사, 재연결 전체 재조회로 유실·회수에 대응한다. 이벤트 재생 보장은 제공하지 않는다. |
| D10 | 지점 선택은 URL의 `scope=all 또는 지점 ID`다. 세션의 영구 선택값을 바꾸는 API는 추가하지 않는다. 새 요청마다 허용 범위를 계산한다. |

수치·길이·기본 정렬 등 SRS가 정하지 않은 구현 한도는 OpenAPI의 제약값을 1차 제안으로 사용한다. 새 법적 보존 기간, 운영 SMTP 제공자, 비밀번호 재설정 정책은 이 설계에서 임의 확정하지 않는다.
