# GitHub 등록 후 AI 개발 운영

기준: foundation 0.1.2-design / DB V3 / SRS 8개 중분류·61개 요구사항. 이 문서는 운영 방식이며, 이번 전달 작업에서 실제 하위 에이전트를 실행하거나 GitHub 마일스톤·이슈를 등록하지 않았다.

## 역할과 작업 단위

- 사람: 정책·우선순위와 PR의 최종 승인. 확정된 Q1~Q12는 매 이슈마다 다시 질문하지 않는다.
- 주 담당 AI: 이슈 분해, 선행 관계·계약·스키마 소유권 조정, PR 통합과 검증 결과 확인. Codex와 Claude Code 중 한 작업에 주 담당 하나를 정한다.
- 작업 AI/하위 에이전트: 관찰 가능한 완료 조건이 있는 이슈 또는 그 내부의 한 작업을 수행한다. 처음에는 독립 작업 2개 정도로 시작하고 통합이 안정된 뒤 늘린다. 같은 이슈를 두 도구에 동시에 맡기지 않는다.

각 작업은 하나의 브랜치·격리된 checkout/worktree·PR을 사용한다. 한 작업 폴더를 여러 AI가 동시에 수정하지 않는다. 저장소 AGENTS.md의 브랜치 이름·관련 변경만 커밋·개발 로그 규칙을 적용한다. DB migration 번호와 OpenAPI 변경은 주 담당이 순서를 정하고 한 PR씩 통합한다.

## 착수 순서

1. 이 패키지 PR을 검토·병합해 모든 작업의 공통 기준 커밋을 정한다. 실제 이슈에는 그 커밋/PR과 패키지 manifest를 연결한다.
2. 마일스톤 3개와 등록 초안 16개를 검토해 GitHub에 등록한다. B02는 이미 이 전달에서 완료했으므로 새 구현을 지시하지 않는다. 완료 이력용으로 등록 후 증거를 연결해 종료하거나 등록에서 제외한다.
3. 첫 작업은 backend B01의 공통 처리와 frontend F01의 계약 타입/오류/캐시 처리다. 프론트는 고정한 OpenAPI와 MSW 계약 fixture를 사용하고 mock 검증을 live 연동 완료라고 기록하지 않는다.
4. B03/B04 인가·인증 기반을 검증한 뒤 B05/B06와 F02로 첫 사용자 흐름을 끝낸다. M1부터 세션 회수·최소 outbox 갱신 부분을 구현하며 B11 전체가 M3라는 이유로 보안 처리를 미루지 않는다.
5. M2는 초대 명령 → worker → 수락/승인 → 화면 순서, M3는 상품 → 갱신 → 통합 검증 순서다. 공유 테이블·계약을 바꾸는 작업은 선행 PR 통합 후 새 main에서 시작한다.
6. 작업 AI가 PR을 만들면 주 담당은 계약/범위/변경 이력과 테스트 결과를 확인한다. 별도 검토자가 취약한 인가·경합·빈 데이터 경로를 확인하고 사람의 승인 후 병합한다.
7. 마일스톤은 이슈 개수가 아니라 실제 사용자 흐름·거부 시나리오의 검증 증거로 종료한다. 실패·미검증·운영 환경 확인을 구분한다.

## 이슈에 첨부할 작업 지시

```text
대상 저장소와 로컬 이슈 ID: <예: backend / B05>
기준: foundation 0.1.2-design, DB V3, 패키지 PR/기준 커밋 <등록 시 기입>
선행 PR: <병합된 실제 PR 링크>
읽을 문서: 이슈 본문의 범위, OpenAPI, database.md, decisions.md, 요구사항 추적표
작업: 본문의 완료 조건과 거부 시나리오를 구현·검증한다.
작업 규칙: AGENTS.md를 적용하고 main 기준 작업 브랜치와 격리 checkout을 사용한다.
완료: 관련 변경만 커밋, 실제 검증 결과·미검증 항목·개발 로그를 남기고 PR을 만든다.
범위 변경: 후속 요구사항을 임의 확정하지 말고 필요한 계약 변경과 영향 범위를 설명한다.
```

GitHub 이슈는 실행 지시와 검증 증거를 모으는 단위이고 SRS·정책·DDL·OpenAPI는 각자의 정본으로 유지한다. 엑셀은 OpenAPI에서 재생성하는 사람이 읽는 사본이다.
