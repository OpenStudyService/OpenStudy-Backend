# 초대 미리보기·수락·최종 승인

Backend [#15](https://github.com/OpenStudyService/OpenStudy-Backend/issues/15)의 구현 범위다. 요청·응답 모델은 기존 [OpenAPI](openapi.json)를 그대로 사용하며 계약 버전은 바꾸지 않았다. 관리 명령은 [초대 관리 API](invitation-management-api.md), 링크 발송은 [발송 계약](invitation-delivery.md)을 따른다.

## 제공 범위

| API | 세션 | 동작 |
| --- | --- | --- |
| `POST /invitations/preview` | 익명·제한·업무 | 유효 링크의 이름·이메일·지점·역할·만료·수락 방식 반환 |
| `POST /invitations/accept` | NEW_ACCOUNT는 익명, EXISTING_ACCOUNT는 같은 계정의 업무 세션 | 링크 소비, PENDING 소속 생성, 초대 ACCEPTED |
| `POST /invitations/{id}/approve` | 업무(OWNER 또는 지점 MANAGER + people:manage) | 계정·소속·권한·초대 상태를 한 트랜잭션으로 활성화 |
| `GET /invitations/approval-status` | 제한·업무 | 기존 구현 유지. 본인이 수락한 초대 상태만 반환 |

세 링크 명령 모두 CSRF 토큰이 필요하다. 익명 사용자는 `GET /auth/csrf`로 먼저 받는다.

## 링크 검증

- token은 JSON body로만 받는다. 서버는 원문의 SHA-256으로 초대를 찾고 원문은 요청 메모리에만 둔다.
- 틀린 토큰·형식 오류·만료·사용됨·취소된 링크는 모두 같은 422 `INVITATION_LINK_INVALID`를 반환한다. 수락 요청의 이메일이 초대 이메일과 다른 경우도 같다.
- 미리보기와 수락 응답에는 `Cache-Control: no-store`와 `Referrer-Policy: no-referrer`를 붙인다.
- 수락 방식은 같은 이메일 계정의 존재 여부로 정한다. 링크를 가진 본인에게 어떤 방식으로 수락할지 안내하기 위한 값이며, 다른 계정 정보는 반환하지 않는다.

## 수락

수락은 해시로 후보를 찾은 뒤 기존 잠금 순서(가드 → 직원 → 지점 → 초대 → 소속)로 잠그고 해시·상태·만료를 다시 확인한다. 동시에 같은 링크를 제출해도 하나만 성공하고 나머지는 422를 받는다.

- **NEW_ACCOUNT**: 로그인한 세션에서는 403. 비밀번호는 8자 이상·UTF-8 72바이트 이하이며 공백을 제거하지 않는다. PENDING 계정(이름은 초대 이름)과 PENDING 소속을 만든다. 세션은 발급하지 않으며 응답의 `nextAction`은 `LOGIN_FOR_APPROVAL_STATUS`다. 같은 이메일 계정이 이미 있으면 409 `INVALID_STATE`다.
- **EXISTING_ACCOUNT**: 미로그인 401, 다른 계정·제한 세션 403. 계정 비밀번호는 바꾸지 않는다. 회수된 소속은 같은 행을 PENDING으로 되돌리고(Q11) 이전 권한 행을 지운다. 해당 지점에 활성 소속이 있으면 409 `DUPLICATE_MEMBERSHIP`. 기존 지점 업무는 그대로 유지한다(Q1). `nextAction`은 `REFRESH_APPROVAL_STATUS`다.

수락 시 초대는 ACCEPTED·수락 계정·시각을 기록하고 해시를 지우며, 남은 발송 작업은 생략 처리한다. 발송 중이던 worker의 늦은 완료는 해시 불일치로 상태를 덮어쓰지 못한다. 감사(작업자는 수락한 본인)와 관리 화면 무효화 이벤트를 같은 트랜잭션에 남긴다.

수락 후 CSRF 토큰은 서버에서 교체하지 않는다. 다음 상태 변경 전에 화면이 `GET /auth/csrf`를 다시 호출하는 기존 계약을 따른다.

## 최종 승인

기존 관리 명령과 같은 인가·잠금·version 검사를 사용한다. 지점 관리자는 STAFF 초대만 승인할 수 있고 MANAGER 초대와 관리자 복구는 OWNER만 처리한다(Q4·Q11).

- ACCEPTED만 새로 전이한다. 수락 계정이 현재 대상 계정과 같고, 해당 지점 소속이 PENDING이며 역할이 초대 역할과 같아야 한다. 아니면 409 `INVALID_STATE`.
- 계정이 SUSPENDED·LEFT면 409로 거부하고 계정 상태를 바꾸지 않는다. 계정 복구는 OWNER의 계정 명령(Q3)으로만 한다.
- 예정 권한은 현재 코드 사전·역할 정책으로 다시 검증한 뒤 소속 권한으로 복사한다.
- PENDING 계정만 ACTIVE로 바꾸고, 소속은 ACTIVE·승인자·승인 시각을 기록한다. 초대는 APPROVED·승인자·시각을 기록한다. 직원 권한 변경 이벤트와 초대 무효화 이벤트를 함께 남긴다.
- 이미 APPROVED면 현재 인가를 다시 확인한 뒤 현재 결과를 반환한다. REJECTED 등 다른 종료 상태는 409다.

승인으로 기존 제한 세션을 업무 세션으로 바꾸지 않는다(Q10). 제한 세션의 승인 상태 조회는 `requiresLogin=true`를 반환하고, 다시 로그인하면 업무 세션을 받는다. 이미 업무 세션을 가진 기존 직원은 다음 요청부터 새 지점이 반영된다.

## 승인 대기 계정의 추가 초대

승인 대기(PENDING) 계정은 첫 초대가 승인되기 전에는 다른 지점의 초대를 수락할 수 없다. 2026-10-27 사용자가 이 동작을 정책으로 확정했다. 승인 대기 세션은 업무 세션이 아니므로 EXISTING_ACCOUNT 수락의 본인 확인 조건을 충족하지 않는다. 첫 승인 후 업무 세션으로 로그인하면 남은 초대를 수락할 수 있다. 추가 초대의 링크 기한(24시간)이 그 전에 지나면 관리자가 재발급한다.

## 알려진 제한과 후속 범위

- 링크 명령에는 별도 요청 제한이 없다. 토큰은 256비트 난수라 추측 공격은 현실적이지 않고, 비싼 비밀번호 해시는 유효한 링크를 확인한 뒤에만 계산한다.
- 실제 메일 링크로 진행하는 두 브라우저 전체 흐름과 운영 프록시 검증은 #18, 프론트 수락 화면은 Frontend 이슈에서 다룬다.
