# 개인정보 처리 기준

#100(ADR-M11-001 M11-D01·D05, ADR-M11-002)의 개인정보 처리 기준이다. 서버가 다루는 개인정보의 수집 목적, 항목, 접근 권한, 열람 추적, 파기 기준, 법정 보존 예외를 정리한다. 보존 기간과 그 근거는 [ADR-M11-002](../db/ADR-M11-002.md)가 정본이다. 이 문서는 그 결정을 서버 동작과 운영 절차로 옮긴다.

- 이 문서는 법률 자문이 아니다. 법령 적용 여부가 확인되지 않은 항목은 "미정"으로 둔다.
- 기간이 "미정"인 정보는 자동 파기 규칙이 없거나 비활성이다. 임의 기간을 적용하지 않는다.

### 익명화(고객)

- 바뀌는 것
  - 이름은 `파기된 고객`이 된다.
  - 연락처, 이메일, 메모, 상태 사유는 비운다.
  - `anonymized_at`에 처리 시각을 남기고 `version`을 올린다.
- 남는 것: 고객 행, 회원번호, 결제·이용권·입실·사물함·스터디룸·문의의 참조
  - M9 매출 집계는 익명화 전후가 같다.
- 마지막 이용일: 다음 중 가장 늦은 날
  - 등록, 입실·퇴실, 승인된 결제, 이용권 만료, 사물함 종료, 스터디룸 종료, 문의 변경
- 대상에서 빠지는 경우: 아래 중 하나라도 진행 중이면 그 사유가 끝날 때까지 기다린다.
  - 사용할 수 있는 이용권, 입실, 사물함, 스터디룸 예약, 처리 중인 문의, 결제 대기
- 남는 개인정보
  - 감사 이벤트의 변경 전후 값에는 익명화 전 고객 값이 남을 수 있다.
  - 이 값은 감사 이벤트 규칙(일반 감사 기간 미정)에 따라 정리된다. 기간이 정해질 때까지 남아 있음을 알고 운영한다.

### 법정 보존 예외

- 법령이 보존을 요구하는 정보(거래 기록, 근태, 접속기록, 권한 이력)는 기간이 확인될 때까지 지우지 않는다.
- 규칙 표(`retention_rules.legal_minimum_days`)에 최소 기간을 둔 규칙은 그보다 짧게 설정할 수 없다(DB 제약 `ck_retention_rules_2`). 서버도 실행 전에 한 번 더 확인한다.

## 2. 규칙 동작

- 규칙 표 `retention_rules`
  - 열: 코드, 설명, 활성 여부, 기간(일), 법정 최소 기간(일)
  - **모든 규칙은 비활성으로 시작한다.**
  - 기간 없이 켤 수 없다(`ck_retention_rules_1`).
- 매일 04:00(Asia/Seoul) 정기 작업이 켜진 규칙을 차례로 실행한다(`RetentionScheduling`).
  - 꺼진 규칙은 아무 일도 하지 않고 기록도 남기지 않는다.
  - 작업 자체를 끄려면 `openstudy.retention.schedule-enabled=false`
- 처리 기록 `retention_runs`
  - 규칙 실행마다 한 행: 규칙, 기간, 기준 시각, 시작·종료 시각, 대상 수, 처리 수, 결과(SUCCESS·FAILED), 실패 시 오류 종류
  - 파기한 값과 오류 메시지는 남기지 않는다(메시지가 지우던 값을 담을 수 있다).
- 규칙마다 따로 트랜잭션으로 실행한다. 큰 집합은 500건씩 나눠 처리한다.
- 인스턴스가 여러 대가 되면 정기 작업을 한 대에서만 돌리도록 바꿔야 한다.

## 3. 규칙을 켜는 절차 (운영자)

**파기는 되돌릴 수 없다. 반드시 아래 순서를 지킨다(POL-03).**

1. **수동 백업**
   - #103의 수동 백업 절차로 DB를 백업한다.
   - 백업 파일 이름과 시각을 기록한다. 백업은 30일 보관이다.
2. **기준 확인**: ADR-M11-002에서 그 규칙이 "확정"인지 확인한다. 미정 항목은 켜지 않는다.
3. **대상 수 확인**
   - 아래 조회로 처리될 수를 미리 본다.
   - 예상보다 크게 많으면 멈추고 원인을 확인한다.

   ```sql
   -- 규칙 상태
   SELECT code, enabled, period_days, legal_minimum_days FROM retention_rules;
   -- CUSTOMER_IDENTITY 대상 수는 서버의 정의(RetentionRepository.INACTIVE_CUSTOMERS)와 같은 조건이다.
   -- 간단 확인: 365일 넘게 쓰지 않은 것으로 보이는 고객 수(예외 조건 전)
   SELECT COUNT(*) FROM customers WHERE anonymized_at IS NULL AND registered_at < NOW(6) - INTERVAL 365 DAY;
   SELECT COUNT(*) FROM ai_conversations WHERE updated_at < NOW(6) - INTERVAL 365 DAY;
   SELECT COUNT(*) FROM idempotency_records WHERE expires_at < NOW(6);
   ```

4. **켜기**: 한 번에 한 규칙씩 켠다.

   ```sql
   UPDATE retention_rules SET enabled = 1 WHERE code = 'IDEMPOTENCY_RECORD';
   ```

5. **결과 확인**: 다음 정기 실행(04:00) 뒤 처리 기록을 본다. 실패하면 규칙을 끄고 오류 종류와 서버 로그(요청 ID 없음, `Retention rule` 문구)를 확인한다.

   ```sql
   SELECT rule_code, started_at, target_count, processed_count, result, error_code
   FROM retention_runs ORDER BY id DESC LIMIT 20;
   ```

6. **끄기**: `UPDATE retention_rules SET enabled = 0 WHERE code = '...';`
7. **복원 뒤**: 백업에서 복원하면 이미 파기한 정보가 되살아날 수 있다.
   - 복원된 행은 익명화 표시(`anonymized_at`)가 없으므로, 다음 정기 실행이 켜진 규칙으로 다시 처리한다.
   - 그때까지 되살아난 개인정보를 업무에 쓰지 않는다.
   - 바로 처리해야 하면 정기 작업 시각(`openstudy.retention.cron`)을 앞당겨 다시 띄운다. 수동 실행 API는 두지 않았다.

## 4. 미정 항목
